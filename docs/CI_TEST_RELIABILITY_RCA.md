**CI test reliability: root-cause analysis and permanent-fix plan — 2026-09-12**

The recurring failures are substantially a test-isolation and synchronization problem. A passing run currently means that one execution order, one scheduler interleaving, and one inherited configuration happened to satisfy the tests. An unrelated change can alter those conditions and expose an existing defect in a test. The history also contains deterministic stale expectations, genuine implementation issues, and infrastructure failures; treating every red run as a flake would conceal useful failures.

This is an investigation and proposed implementation plan. No application code, repository tests, workflows, or GitHub settings were changed. Source analysis and diagnostic copies use local `dev` at `713ebcc7`; pre-existing test edits were preserved. Remote fixes on other branches are identified below so implementation can reconcile them rather than duplicate them.

**1. Global state escapes the test that changes it. Confidence: confirmed, with a new reproduction.**

`Application` configuration, system environment variables, named processes, registries, and some stubs live beyond an individual test. `async: false` prevents overlap with other ExUnit cases; it does not reset state between cases or stop independently spawned work. The umbrella's apps share that state.

The current `Management.SecretsTest` provides a concrete example. Its plugin-token test writes an Eden token through the real settings path, but `@core_keys` excludes `:plugin_secrets`. Cleanup resets the stub and restores other settings while leaving the Eden entry in application configuration. `Plugins.ConfigTest` also omits that key from its baseline. Its Discord-deletion test then scans the entire saved TOML for `@keyring`. CI's allegedly undeleted secret is actually `eden = "@keyring"`; its preceding Discord-specific assertions passed. [Failure, seed 916103](https://github.com/tezra-io/fermix/actions/runs/34665940174/job/103477717292), [producer](../apps/fermix_core/test/fermix_core/management/secrets_test.exs), [consumer](../apps/fermix_core/test/fermix_core/plugins/config_test.exs).

Controlled verification in fresh test VMs: run only the producer, let its cleanup finish, then run only the consumer. The producer passed, the remaining key list was `["eden"]`, and the consumer failed with CI's exact assertion. Adding `:plugin_secrets` to the producer's restoration list in a temporary copy left `[]`; both tests then passed against unchanged production code. This confirms a sufficient producer-to-consumer mechanism, without claiming to reconstruct every process scheduled in the historical CI run.

This is the same family as the routing leak fixed in `ed8f23f3`: `AdminToolsTest` changed `:routing`, failed to restore it, and a later LiveView saved an OpenAI Codex model against the inherited OpenRouter provider. [CI error](https://github.com/tezra-io/fermix/actions/runs/34658540940/job/103456033303). June's route-resolver issue was already documented in `2168fbc7`. Repetition across unrelated settings explains why repairing only the latest failing consumer has not converged.

There is also indirect leakage: management protocol/router tests injected only part of an auth-import operation. The remaining real calls started permanent token managers and wrote configuration. Three `AuthCompletionTest` cases then rejected an already-running manager: 36 assertion occurrences across nine runs. Fixes `902e480b` and `0a75aad2` addressed two separate producers. Keep the consumer's empty-registry precondition; clearing the leaked manager there would hide the cause. [Example](https://github.com/tezra-io/fermix/actions/runs/34055877841/job/101547564537).

Remaining source-level hazards include `ComputerUse.ConfigTest` changing both `:computer_use` and `:sandbox` while `async: true`, and `ComputerHistory.SupervisorTest` changing `:computer_history` asynchronously and deleting it instead of restoring its previous value. These are verified isolation defects in the source, not yet attributed to particular historical failure occurrences.

**2. Tests observe an intermediate event as though it proves completion. Confidence: confirmed.**

The current proxy test spawns caller A, spawns caller B, waits for queue length one, kills B, and assumes it killed the queued caller. Spawn order does not establish admission order. B can be in flight while A is queued; the product is then entitled to dispatch A. [Post-merge failure, seed 826494, max_cases 6](https://github.com/tezra-io/fermix/actions/runs/34670754115/job/103491533358), [test](../apps/fermix_core/test/fermix_core/capabilities/mcp/remote/proxy_test.exs).

A temporary diagnostic held A before its call, let B reach the in-flight slot, then released A. The original final assertion reproduced CI exactly: two dispatches rather than one. Releasing A and proving its admission before starting B made the assertion pass. The permanent version should additionally hold the first fake dispatch behind an explicit release message, so the test owns the sequence instead of renting a two-second sleep window. This experiment establishes the test-order defect; it is not a proof of every possible production cancellation interleaving.

Other members of this family are already patched individually:

- Draft rotation tests assumed a final seal or text push would beat a 1 ms flush timer. Waiting for the legitimate second-bubble open made the expected write sequence explicit (`4580c375`, `ed8f23f3`). [Example](https://github.com/tezra-io/fermix/actions/runs/34658540940/job/103456033264).
- RTMS forwards a roster before stamping its clock-derived state. Advancing a fake clock on receipt of the roster could change the timestamp being recorded. A same-server state barrier establishes completion of that callback (`4580c375`). Such a barrier does not automatically wait for work delegated to another process.
- MCP discovery, doctor probes, browser-download cleanup, and durable persistence have failed when tests observed a notification or elapsed sleep before the relevant registry, filesystem, or second async task had settled.

**3. Exit observation and cleanup are not owned from the start. Confidence: confirmed.**

`SidecarSourceTest` starts a source whose continuation immediately refuses the launch, then installs a monitor and expects a `:normal` exit. If the source is already dead, the monitor reports `:noproc`; waiting longer cannot produce the expected message. Four full-log occurrences include [this failure](https://github.com/tezra-io/fermix/actions/runs/34676939395/job/103508398845).

A temporary copy with a 50 ms delay before monitoring failed with the exact `:noproc` mailbox. Trapping exits before `start_link` and observing its spawn-time link passed with the same delay. The existing remote patch `c9385572` implements that direction; it is absent from the local `dev` snapshot. Similar monitor mistakes were patched in meetings sessions (`e4b0484c`) and MCP owners (`9148869c`). Where a test controls the terminating trigger, install the monitor before that trigger. Where termination can occur during startup, use an observation mechanism established at startup.

Separate teardown failures occurred in CLI tests and `CommandHostStreamTest`: `on_exit` attempted to stop a process already shutting down, and an exception could prevent later environment restoration. `DistVerifierStub.cleanup` also attempted to delete an ETS table after its owner died. These require resource ownership and cleanup ordering, not assertion timeout changes. [CLI example](https://github.com/tezra-io/fermix/actions/runs/29160848722/job/86565567106), [stream example](https://github.com/tezra-io/fermix/actions/runs/30161921253/job/89688523126).

**4. Tests confuse a behavioral guarantee with host speed or timer resolution. Confidence: confirmed for the assumptions; exact runner delays are not always known.**

Examples include a 1 ms staleness threshold against second-resolution file mtimes; reading a timer reference after it may have fired; sleeping 150 ms between keepalives inside a 500 ms grace; checking a nonblocking scheduler with `duration_ms < 100`; and one-second rendering budgets inside a concurrent correctness suite. A loaded or differently provisioned runner changes the results without changing the behavior being tested. [Lock example](https://github.com/tezra-io/fermix/actions/runs/34175270956/job/101903310589), [keepalive example](https://github.com/tezra-io/fermix/actions/runs/34674810135/job/103502646922).

The 2,000 ms default receive budget is already present in all five test helpers (`ff56a1d6`). It removes many accidental 100 ms deadlines, but explicit bounds, wrong messages, and incorrect barriers remain independent problems. WSS connection establishment also had a two-second setup budget; its logged timeout is confirmed, but the exact contribution of TLS, scheduling, or socket setup was not measured. Do not infer a networking defect from that log alone.

Intel macOS amplifies some of these issues: in the PR #70 sample its core async phase took 127.6 seconds versus 49.9 seconds on Linux x64. This is observational context, not a controlled benchmark. Failures also occurred on Linux and ARM macOS; removing Intel macOS or globally serializing everything would leave demonstrated causes intact.

**5. Telemetry and mocks can observe another test's activity. Confidence: confirmed from failure payloads and corrective history.**

A telemetry handler name unique to a test does not make the event stream private. Examples include a CLI channel event satisfying a Telegram assertion, `memory_recall` satisfying an `echo` tool assertion, and a previous stream's successful provider span reaching a consumer-death test expecting an error. Tests must filter on a unique session/run/event identity, or the emitting process when the operation actually executes there, and await terminal work before detaching. [Agent-loop example](https://github.com/tezra-io/fermix/actions/runs/30601266308/job/91064261580), [stream example](https://github.com/tezra-io/fermix/actions/runs/33440133019/job/99646030823).

`Req.Test` shared mode was set from an async dispatcher case, putting unrelated media-download tests into `:not_shared_owner` failures. `929c23af` corrected the caller and added an invariant. That invariant currently scans the channels test tree only and uses file-level text matching; extend the same prevention principle across the umbrella with module-aware checks. Prefer private ownership and explicit allowances for child processes. [Failure](https://github.com/tezra-io/fermix/actions/runs/31065307473/job/92501677821).

Other workflow failures need separate ownership. CI includes a corrupted setup-uv action SHA, dependency downloads failing DNS, real checksum mismatches/404s, and a transient curl reset. **Why prior fixes did not permanently solve this.** Many commits repaired one observer or one leaked setting, then validated one local suite run. The same unguarded pattern remained elsewhere. The suite also combines pure unit assertions with disk, process, database, TLS, and full settings operations under similar scheduling assumptions. Existing guardrails are mostly prose or local to one app. The source scan found 179 `Process.sleep` sites in 77 test files and application-env writes/restores in 203 files; these are review candidates, not 179 or 203 proven bugs. Manual review already identified two genuine async global mutators beyond the newly reproduced leak.

There is a separate enforcement gap. The GitHub branch endpoint reports `main` requires only `compile · format · credo · test (linux-x64)`, `(linux-arm64)`, and `(macos-arm64)`, with `non_admins` enforcement. `dev` reports no required checks; the repository ruleset listing returned none. The full protection-detail endpoint returned 404, so the complete bypass configuration was not established. The workflow comments claim that the aggregate is the single required check, which does not match the reported contexts. Its aggregate also omits `checksum-integrity` from `needs`. [Main branch metadata](https://api.github.com/repos/tezra-io/fermix/branches/main), [dev metadata](https://api.github.com/repos/tezra-io/fermix/branches/dev), [workflow](../.github/workflows/ci.yml).

Finally, `mix compile --warnings-as-errors` does not cover the later loading of `.exs` tests. The workflow uses plain `mix test`, and actual logs contain an `IdleSource` missing a behavior callback and unused fixture helpers. The installed Mix help confirms that `mix test --warnings-as-errors` is the separate gate for those warnings. Fix the existing warnings before turning that gate on; do not suppress them.

For P1, use one small shared fixture helper for the genuinely global cases: declare the settings being changed, establish a known baseline, and restore it after owned workers stop. Add a serial audit of environment differences to identify the producer that leaked state. Do not reset the entire VM after every test to make the consumer pass: that would hide missing ownership. An async-test check must reason about each module, not reject a file merely because it contains one async module and a separate synchronous module. The current `ReqTestOwnershipInvariantTest` is a useful starting point, not justification for a new test framework.

Give each test invocation its own temporary home and derive its database, prompt, and bootstrap paths from that root before introducing parallel test VMs. `config/test.exs` currently contains fixed temporary names such as `fermix-test-memory.db`; several services are disabled by default, but those names are not a sound isolation boundary for a future stress runner. Preserve the deny-by-default secret/provenance stubs and the compile-time Opik test gate.

For P2, timers that are the behavior under test keep real bounded timer coverage in a small integration test. State-machine cases can deliver the relevant timer event explicitly and verify cancellation, epoch changes, and stale-message handling. A final notification is a completion barrier only if the source contract says it is final. A `:sys.get_state` call orders work from the same sender to the same server, not arbitrary work in other processes. Fake transports should expose a start/release handshake rather than sleep until the host is expected to catch up.

The source audit also found a direct `File.rm_rf!` in `apps/fermix_opik/test/fermix_opik/trace_file_test.exs:93`, outside the shared safe-delete helper. Include it in the test-resource sweep and enforce the existing repository rule across every umbrella app. This was not attributed to a historical CI failure, and was not changed during this investigation.

P0 and P3 should align the local quality command with CI's test environment. The hook currently runs compile/Credo in their default environment before `mix test`; CI sets `MIX_ENV=test` for the whole job. Preserve separate development/build checks if needed, but use the same test-env checks to claim CI parity. Keep real release compiler and packaging checks; do not recategorize their failures as flakes.

**Validation contract for the implementation.**

1. Retain the three deterministic reproductions described above: leaked Eden config, late sidecar monitor, and reversed proxy admission. Each original assumption must fail; its corrected variant must pass without production changes. Add corresponding focused regression coverage before applying the implementation.
2. Run compile with warnings as errors, formatting, strict Credo, the full umbrella with test warnings as errors, and the existing Python harness/release-script checks. Tests must use isolated homes and stubbed secret writers; no host keychain or live provider calls. Check one cold build and one normal cache restore on each platform when validating the CI changes. There is no evidence here that cache corruption caused the reproduced assertion failures; this check verifies build reproducibility separately.
3. Run the repaired modules in fresh VMs at five recorded seeds (`208879`, `916103`, `826494`, `600105`, `587472`) with `--max-cases 1` and `8`. Record `ERL_FLAGS`, the actual runtime scheduler count, and toolchain. Seed alone does not reproduce the OS scheduler. Do not use `--trace` for the concurrency proof: installed Mix help says it forces `max_cases: 1` and disables the normal test timeout.
4. Add a daily full-umbrella stress run on Linux x64 and Intel macOS using five recorded, changing seeds per platform. Also run the repaired subset for at most 20 same-VM repetitions to expose retained state. A repeated run remains diagnostic; its first failure stays red. Keep all four ordinary platform legs on PRs. Measure Intel concurrency before changing it; compare the same seeds at four and eight cases if contention remains.
5. Accept the repair after the deterministic regressions pass, the full four-platform matrix passes, and 20 consecutive required CI runs plus the first seven daily stress batches have zero unexplained first-attempt test failures and zero test-compilation warnings. Any new flake resets this observation window and receives a producer/ordering reproduction. This is a finite acceptance criterion, not a guarantee that no future test can ever be flawed.

Do not use skip tags, broad exception catches, automatic rerun-until-green, relaxed correctness assertions, a single permanently fixed seed, or dropping a platform as the repair. Raising a receive or connection bound is appropriate only when it bounds waiting for an already-defined event; it cannot repair a wrong event, leaked state, missing callback, or invalid fixture.

**Implementation status — 2026-09-12.** This plan was verified claim by claim against the source and then implemented on `dev`. Read this section before using the tables above as a work list: four of the six timing sites, three of the four telemetry examples, the CLI teardown and `CommandHostStreamTest` were already repaired before this report was written, and the `DistVerifierStub.cleanup` claim did not reproduce — a 2,000-trial probe shows the named table is always already gone by the time `on_exit` runs. The mechanism of every remaining claim held, and each family contained members this report did not list.

`dev` was first rebased onto `main`, which carried three test fixes it lacked (`c9385572` sidecar link-exit, `c0a1a0b2` command-tool spawn race, `9f88355b` RTMS grace timer plus the suite-wide receive bound). Their absence from `dev` is why merges kept re-meeting failures that `main` had already fixed.

What landed, all of it in tests, CI and the hook — no production code changed: the `:plugin_secrets` and `:oauth` producer leak and the consumer's own baseline; six modules made synchronous or given exact restore-on-absent; two teardowns split so a fallible process stop can no longer strand a temporary `FERMIX_HOME`; proxy admission identity established before the second caller exists; the browser download barrier moved onto the call that performs the delete; MCP discovery scripted per call instead of flipped mid-flight; eleven late monitors converted to a link established before the trigger; four wall-clock budgets replaced by reductions, a release handshake or a controlled clock; three unfiltered telemetry handlers pinned to their own identity; four stale fixtures bound to their canonical source; and the test-compilation warnings fixed so `mix test --warnings-as-errors` could be turned on in CI.

Two of this report's prose rules became mechanical gates, because a rule nothing checks is a rule the next test breaks. `test_safety_test.exs` was scanning zero files — its glob was cwd-relative and `mix test` runs each child app from its own directory, so the SafeRm rule had never been enforced anywhere; it is now anchored on `__DIR__`, asserts its corpus is non-empty, and also forbids `Application` env writes from `async: true` modules. The `Req.Test` ownership invariant was widened from 85 of the umbrella's 606 test files to all of them and now reads `async:` per module off the AST rather than per file. Both were proved by injecting an offender in a third app (red) and a legitimate synchronous use (green).

Every repaired test was mutation-checked: the production behaviour it covers was broken and the test was required to go red. Seven checks, seven reds, each naming the intended test. Run mutations with `warnings_as_errors: false`, or an unused-function warning fails the compile and reads as a passing check.

One finding is larger than this report stated and remains open, because it is a repository setting rather than a file: `main` requires the three matrix leg contexts directly, not the `gate` aggregate the workflow comments describe, so `macos-x64`, `checksum-integrity`, `harness`, `release-scripts` and `disclaim-shim` gate nothing today — fifteen of the seventy-nine most recent red runs were red only in jobs `main` does not require — and `dev` carries no protection at all. `gate` now depends on `checksum-integrity`, but until protection points at that single context the workflow edits change nothing about what can merge.
