# Milestone 29 — ACP Agent Surface: Fermix under any ACP client (Buzz custom harness first)

**Design principle for this milestone: simplest correct integration.** Every problem the rev-1 review confirmed is fixed here by *removing* surface or *reusing* an existing seam, not by adding machinery. Three deliberate simplifications carry most of the weight: no slash commands on this surface (closes the daemon-admin hole without a third trust tier), model-owned reply posting at exact parity with every other Buzz agent (no Fermix-side Nostr/delivery machinery), and `request_cwd` reuse (no new workspace concept).

## 1. Summary

ACP (Agent Client Protocol, agentclientprotocol.com — JSON-RPC 2.0 over stdio between a host "client" and a spawned "agent" subprocess) is the lingua franca for embedding coding agents: Zed and JetBrains natively, a 38-agent registry, and — the trigger here — **Buzz v0.5.x "bring your own harness" (BYOH)**: any ACP-speaking binary can be added as a first-class Buzz agent from the settings UI. No upstream patch, no catalog entry.

This milestone makes Fermix a native ACP **agent**:

1. **A `fermix acp` CLI verb** — a stdio⇄UDS pipe into the running daemon: one hello line, one ack line, then raw bytes. All protocol logic lives daemon-side.
2. **An `acp` channel** in `fermix_channels` — its transport child is a UDS listener at `<FERMIX_HOME>/acp.sock` (the `realtime.sock` pattern). Each ACP session becomes an ordinary gateway conversation: Fermix's system prompt, tools, sandbox, durable memory, compaction, telemetry.

The pitch: under Buzz, claude/codex are amnesiac subprocesses; Fermix-over-ACP is a window onto a persistent daemon. The harness owns identity, queueing, and replies (accepted for this role, §3); Fermix keeps memory, tool policy, sandbox, and observability.

Two research facts dominate the design (§2.4): Buzz never posts the agent's ACP output to the channel — agents post their own replies via the `buzz` CLI using spawn-env credentials — and Buzz cancels + re-prompts mid-turn agents by default with a 5-second drain. Hence the small set of core seams this milestone adds (§6.3): a registry `trust` field, a per-conversation queue stop, an optional turn-result callback, a `:raw` stream tier, and a session env overlay consumed at one point.

## 2. Research

### 2.1 Buzz v0.5.2 BYOH mechanics

- A custom harness is a JSON file `<app-data>/custom_harnesses/<id>.json` — `{id, label, command, args, env, installInstructionsUrl?, installHint?}` (`desktop/src-tauri/src/managed_agents/custom_harnesses.rs:47-70`), created from the Settings Harnesses panel or inline from the agent dialogs. Constraints: `args` may not contain literal commas (they travel comma-delimited in `BUZZ_ACP_AGENT_ARGS`); `env` may not set keys on the finite, case-insensitive reserved list (`env_vars.rs:58-90` — the `BUZZ_*` wiring keys plus `NOSTR_PRIVATE_KEY`); ids collide-checked against builtins/presets.
- The desktop never speaks ACP itself. It spawns one `buzz-acp` harness per (agent, relay) pair, env-configured; `buzz-acp` spawns a pool of `parallelism` (default 10, max 32) copies of the custom binary — NDJSON JSON-RPC over stdio, 10 MiB line cap (`crates/buzz-acp/src/acp.rs:21`).
- Custom binaries are PATH-resolved with generous fallbacks (literal absolute path; `/opt/homebrew/bin`; `~/.local/bin`; login-shell `command -v`; `~/.bun/bin`; …) — a Homebrew `fermix` resolves from a GUI launch. **No probing**: no `--version`, no handshake test (version gating is codex-only).
- Spawn context: cwd `~/.buzz` (the shared "nest"; `$HOME` fallback; no per-agent workspace), env inherited from the harness including **`BUZZ_PRIVATE_KEY` (the agent's Nostr nsec), `BUZZ_RELAY_URL`, `BUZZ_AUTH_TAG` (when set), `NOSTR_PRIVATE_KEY` + `GIT_CONFIG_*` (git-over-relay credentials), and the harness's augmented PATH** (`runtime.rs:552-578,828-850`; `acp.rs:493-511`). **Every Buzz agent's own shell children see these too** — claude/codex under Buzz run arbitrary shell with these variables present. Custom harnesses get no MCP sidecar (`mcpServers` always `[]`), no model/provider env wiring, no auth probes.
- Lifecycle: subprocess crash → respawn with backoff + a 3-in-60 s circuit breaker; **if every initial slot fails (daemon down at first spawn), the harness exits — the stderr message lands in the per-agent log but is not guaranteed to surface as the displayed status summary**. Idle turn timeout default 900 s (reset by any valid frame from the agent, and explicitly by `tool_call`), hard cap 7200 s. **v0.5.2 exposes no UI field for the idle timeout** — the agent record's `idle_timeout_seconds` exists (`runtime.rs:716-724`) but no dialog sets it; the harness default governs in practice. A successful cancel drain keeps the subprocess; only drain expiry (5 s for control-signal cancels) triggers kill + respawn.

### 2.2 The wire contract buzz-acp exercises (v0.5.2)

| Wire item | Buzz behavior (cited to `crates/buzz-acp/src/`) |
|---|---|
| framing | NDJSON JSON-RPC 2.0, numeric client ids; unknown agent→client *requests* answered `-32601`, unknown notifications dropped (`acp.rs:1670-1685`) |
| `initialize` | sends `protocolVersion: 2` (deliberate squat ahead of upstream, `acp.rs:599-601`); `clientCapabilities` carry **no spec `fs` and no spec `terminal`** (only a nonstandard `auth: {terminal: true}` / `_meta["terminal-auth"]` flag for its out-of-band auth flows); reads back `protocolVersion` (≥2 ⇒ system prompt via `session/new.systemPrompt`, else legacy in-message `[Base]`/`[System]` sections), `agentInfo.name`, `_meta.steering.supported`; **ignores `agentCapabilities`**; 60 s timeout |
| `authenticate` | never called at runtime (only by `buzz-acp auth-methods/authenticate` CLI flows) |
| `session/new` | one session per Buzz channel (DMs included), lazily on first prompt, reused until rotation; params `cwd` (= harness cwd, `~/.buzz`), `mcpServers` (`[]` for custom), `_meta.sessionTitle` ("Agent · #channel"; bare agent name for DMs); mines `modes`/`configOptions`/`models` from the response for optional mode/model switching (skipped when absent) |
| `session/load` | never called; agent restart ⇒ fresh `session/new` |
| `session/prompt` | **text ContentBlocks only**; `[Context]` (scope, channel, thread ids, `buzz` CLI hints, reply-anchor instruction) → optional `[Thread/Conversation Context]` → one or more `[Buzz event]` blocks (sender label + npub + hex, raw content, tag JSON); multiple pending mentions batch into ONE turn; a triggering message that is a **single-event batch** whose content (after leading mentions) starts `/alnum…` is passed through as a separate first text block (`acp.rs:741-753`) |
| `session/update` | mirrored to the desktop session viewer (owner-encrypted kind-24200 observer frames) and consumed for harness state: `tool_call` resets the idle clock, `session_info_update._meta.goose.activeRunId` feeds steering, goose-style usage notifications feed kind-44200 metrics. **Nothing the agent streams is posted to the channel** |
| replies | the agent posts its own messages via the `buzz` CLI (`buzz messages send --reply-to <anchor>`), authenticated by the spawn env; the injected base prompt mandates this (`base_prompt.md`) |
| `session/request_permission` | auto-answered, no UI: `allow_once` option, else `reject_once`, else protocol error (`acp.rs:1856-1940`) |
| `session/cancel` | notification; sent on idle timeout, steer fallback, interrupt, owner `!cancel`/`!rotate`, model switch, desktop stop; **5 s drain** for control-signal cancels, then subprocess kill+respawn; the agent must answer the in-flight prompt with `stopReason:"cancelled"` |
| `_session/steering` | mid-turn injection; gated solely on `_meta.steering.supported: true` in the initialize response (BYOH may opt in); non-steering agents get cancel + merged re-prompt (desktop pins steer mode) |
| errors | turn errors whose message contains `"Re-authenticate"` or `"API Error: 401"` dead-letter immediately with a visible in-channel notice; anything else requeues with backoff up to 10 times, then dead-letters with a visible notice (`lib.rs:3002-3179`) |
| stopReason | case-insensitive; exactly `end_turn`, `cancelled`, `max_tokens`, `max_turn_requests`, `refusal`; missing/unknown = protocol error |

### 2.3 ACP spec state (verified live 2026-07-30)

Wire `protocolVersion` = integer **1**; artifact `schema-v1.20.0`. Framing: newline-delimited JSON-RPC 2.0 over stdio, UTF-8; **agents MUST NOT write non-ACP bytes to stdout** (stderr free for logs). Negotiation: the client sends the latest version it supports; an agent that doesn't support it **replies with the latest it does** — the client then decides whether to disconnect (so version `0` gets `1` back, not an error). All paths absolute, `session/new.cwd` included. Minimum conforming agent: `initialize`, `session/new` (accept `cwd` + `mcpServers` — **stdio MCP is an ungated MUST**), `session/prompt` (accept `text` + `resource_link`), handle `session/cancel` (→ `stopReason:"cancelled"`), stream `agent_message_chunk`, one `stopReason` per turn; `authMethods: []` when auth is not needed; `-32000` auth required; `$/cancel_request` → complete the referenced request with `-32800`. Everything else is capability-gated, omitted-means-unsupported. **ACP v2 draft** (2026-07-20) restructures prompt turns and removes fs/terminal/`session/load` — a reason to keep the wire codec and the session layer separate, and not to chase Buzz's `protocolVersion: 2` squat.

Elixir ecosystem: no maintained current-spec library (hex `acpex` 0.1.1, `agent_client_protocol` 0.1.0 pre-date the 2026 stabilizations). Hand-roll the small codec; vendor the schema; contract-test against it (the `priv/realtime` pattern).

### 2.4 Verdict: can Fermix be added to Buzz out of the box?

**Yes — via BYOH — provided Fermix speaks ACP v1 over stdio and solves two problems the protocol does not state:**

1. **Reply publication.** Buzz posts nothing on the agent's behalf. Replies happen because the injected base prompt instructs the model to run `buzz messages send` and the spawn env carries relay credentials. A daemon-bridged agent must make that env reachable from the session's shell tool (§8.3) or it can never answer in-channel. Corollary: anything Fermix "replies" outside the model's own posting — command output, system texts — would be invisible in the channel; rev 2 removes those reply classes from this surface instead of building a delivery path for them (§4).
2. **Cancel latency.** Steer-mode is pinned: every mid-turn mention triggers `session/cancel` + merged re-prompt with a 5 s drain before kill-and-respawn. Turn abort must complete in well under a second (§8.5).

Everything else fits: no spec fs/terminal advertised (Fermix has its own tools), no MCP servers passed to custom harnesses, permissions auto-handled, capabilities Fermix won't advertise are ignored, no version/vendor probe on custom binaries.

## 3. Relationship to M23 (and its §13 ACP rejection)

M23's verdict stands: **the chief-of-staff rail remains native relay membership.** M23 rejected ACP *for the CoS role*; this milestone ships ACP for a different role — a worker/dev agent an org member adds from the Buzz UI — and for the ACP client ecosystem beyond Buzz. They compose: a CoS Fermix (M23, Fermix-owned keypair) can delegate to a Buzz-managed Fermix-over-ACP agent (Buzz-owned keypair) like any org agent. Against M23 §13, objection by objection:

| M23 §13 objection | M29 disposition |
|---|---|
| harness owns identity, sessions, queueing, batching, replies | Accepted for this role — it is what "being a Buzz-managed agent" means; claude/codex accept the same terms |
| "Fermix demoted to a prompt-responder inside someone else's loop" | Half-dissolved: the loop is harness-owned, but memory, skills, sandbox policy, compaction, and telemetry stay daemon-owned — the half that made "prompt-responder" an insult |
| kills slash commands | **Conceded, and made deliberate**: rev 2 disables the command pipeline on this surface entirely (§4) — the alternative was exposing daemon-admin commands to anyone who can @mention the agent. `/compact` is redundant (auto-compaction) and session reset exists harness-side (owner `!rotate`) |
| kills streaming, reaction acks | Accepted: streaming surfaces in the Buzz session viewer, not the channel; reactions are harness-posted. Channel-visible streaming remains an M23-rail property |
| kills single-flight | Dissolved: sessions map 1:1 to gateway conversations; per-conversation single-flight applies unchanged |
| harness auto-approves permissions — "the opposite of Fermix's trust model" | Dissolved by not playing: Fermix never emits `session/request_permission`; its sandbox modes + hardline blocklist remain the enforcement layer, and the approval flow is structurally unreachable from this surface (§11) |

M23 §14's deferred `buzz-backend-fermix` deploy binary is unaffected. M23's "revisit only as a thin demo shim" sentence is superseded by this design; the CoS-rail decision is not.

## 4. Decisions locked

| Question | Decision |
|---|---|
| Process topology | **Bridge, not boot.** `fermix acp` is a stdio⇄UDS pump into the running daemon (SQLite single-writer forbids a second tree; a private home would fork memory). Daemon down ⇒ fail fast and loud (§6.2). No standalone fallback (Rule 12) |
| Where logic lives | All ACP protocol logic daemon-side in `fermix_channels` (`Channels.Acp.*`). The bridge parses exactly two control lines (its hello, the daemon's ack) and nothing else |
| Integration shape | A channel. Registry entry: `%{name: "acp", config_key: :acp, adapter: Channels.Acp, remote?: true, trust: :local_operator, commands?: false, transport: :gateway, child: Channels.Acp.Supervisor}`. See the two new registry fields below — rev 1's `remote?: false` entry was broken (Sources would have carried `channel_key: :acp` and been rejected, `source.ex:36` + `authorizer.ex:45`) and would have opted ACP into the one-shot loopback behaviors (per-turn browser reaping, `queue.ex:419`) |
| `trust` registry field (new) | `trust: :local_operator` — consulted first by `Authorizer.resolve/1` (unconditional operator, before the sender-id clauses) and by the registry's `startable?`/`missing_ingress_authorizations` gates (channels with this trust need no ingress list). `cli`/`daemon` entries gain the same field (behavior unchanged); `remote?` keeps its lifecycle meanings only — for acp, `remote?: true` correctly keeps browsers warm across turns of a persistent session and makes harness-continuation delivery refuse loudly. One field, two consumers, no third trust tier |
| `commands?` registry field (new) | `commands?: false` — the gateway's command-dispatch step skips channels that opt out; message content is always model input. **This is the two-principal answer, simplified**: operator *tool* trust under Buzz is peer-parity (claude/codex run full-tool with `bypassPermissions` there — §11), but operator *command* trust would hand `/sandbox grant|revoke|confirm`, `/soul`, `/background` and friends to anyone who can @mention the agent — a cross-surface, durable blast radius no peer has. Removing the pipeline closes that hole with one field. All other channels default `commands?: true` |
| Protocol version | **Honest v1** (`schema-v1.20.0`). Buzz sends `2`; Fermix replies `1`; buzz-acp proceeds on legacy in-message prompt framing (verified). A client sending `0` also gets `1` back — negotiation replies with the latest supported version and the *client* decides to disconnect |
| Capabilities advertised | `loadSession: false`, `promptCapabilities: {}`, `mcpCapabilities` omitted, no modes/configOptions, `authMethods: []`, `agentInfo {name: "fermix", version}`. No `_meta.steering.supported` |
| Conformance scope | **"Buzz-first ACP v1 interoperability profile"** — spec-v1-shaped everywhere except: non-empty `mcpServers` ⇒ named `-32602` error ("session-scoped MCP servers are not supported yet; configure MCP in Fermix's own config"). Stdio MCP is a spec MUST, so rev 2 does not claim general v1 conformance (rev 1 did; the claims could not coexist). Buzz always sends `[]` for custom harnesses; Zed works when the user attaches no MCP servers to Fermix. Full conformance = §14 |
| Session ⇒ conversation | `session/new` mints a UUID `sessionId`; conversation key `{"acp", session_id, :root}`. Continuity across harness restarts = **daemon-global state only** (curated memory, skills, SOUL — the Reviewer/MEMORY.md pipeline), not conversation transcripts: Buzz never calls `session/load`, so a restart is a fresh conversation by construction. Worded honestly everywhere (rev 1's "memory intact" implied more) |
| Reply publication (Buzz) | **The model posts via the `buzz` CLI through Fermix's shell tool — exactly like every other Buzz agent** (the injected base prompt instructs it; the env overlay makes it work, §8.3). No framework-owned posting (§13). Turn *failures* become JSON-RPC errors, and **Buzz itself posts the in-channel failure notice** (its dead-letter/retry machinery) — error visibility without any Fermix delivery code. **Narrowed by §16.5** (effect gate): a turn that already posted answers `end_turn`, so Buzz raises no notice for it — the failure is visible in the Fermix log and the trace instead, which is the price of not repeating the post |
| Env overlay | Bridge hello carries its spawn env; the **daemon** filters to an internal allowlist (`BUZZ_RELAY_URL`, `BUZZ_PRIVATE_KEY`, `BUZZ_AUTH_TAG`, `BUZZ_ACP_DISPLAY_NAME`, `NOSTR_PRIVATE_KEY`, `GIT_TERMINAL_PROMPT`, `GIT_CONFIG_COUNT`+`GIT_CONFIG_KEY_n`/`VALUE_n`, `PATH`) and discards the rest before storing. Applied at **one consumption point**: sandbox shell-command env construction for that session's conversations. Custody posture in §11 — peer-parity, plus scrubbing of the two secret values at the telemetry choke point. **Custody superseded by §17** (owner decision, 2026-08-01): the filtered env becomes a durable client identity keyed by derived pubkey — the allowlist, the discard, and the single consumption point are unchanged; the RAM-only lifetime is not |
| Workspace | **Reuse `request_cwd`** — the seam already exists end-to-end: `Message.request_cwd` (`message.ex:26`) → operator-only threading (`turn_runner.ex:334`) → `Sandbox.Mode.effective_roots/2`, where standard mode admits an inside-home cwd as a root (never `$HOME` itself), strict never admits it, open already covers it, canonicalization + blocked-roots always apply. The session's `session/new.cwd` (validated absolute) becomes `request_cwd` on every synthesized message. `~/.buzz` therefore works grant-free in standard mode; outside-home project dirs surface the existing sandbox refusal with the existing `fermix grant` guidance. Rev 1's new "workspace override" seam is **deleted** |
| Streaming out | A third stream tier, **`:raw`**: the adapter's `stream_capability/0` returns `:raw`; the gateway's existing stream-spec assembly selects it; the Queue then threads the adapter-built callback straight through **without a DraftStream engine**. Only `text_delta`/`text_done` become `agent_message_chunk` suffix-deltas; reasoning events are dropped (v1); the final `{:text, response}` delivery reconciles (emit any unsent suffix). Rev 1's quartet plan is dead: default block mode emits reasoning side-blocks (`draft_stream.ex:191,256`) and post-final compaction notices (`queue.ex:396,544`), so chunk concatenation would not equal the final message |
| Tool events | `activity_callback` threaded Queue→TurnRunner (same nil-safe shape as `stream_callback`), with one payload extension: `{:tool_finish, name, %{status: :ok | :error}}` (both consumers — cron watchdog, acp — updated together). Session emits `tool_call` (`in_progress`, title = tool name, kind mapped from policy class) at start and `tool_call_update` (`completed`/`failed`) at finish. Resets Buzz's idle clock at tool *start*; renders in the session viewer |
| Turn results | New optional **`turn_result_fn`** on the agent message (assembled by the gateway from an optional adapter callback, mirroring `build_text_reply`): invoked **exactly once per turn by the Queue** — `{:completed}` after the normal deliver/commit path, `{:failed, reason}` from the error path (the *raw* reason, before `error_reply/1` stringification) and from abnormal task DOWN, `{:cancelled}` from the stop path. Existing channels omit it; nothing else changes. This is what lets `Acp.Peer` emit exactly one terminal JSON-RPC response and map provider-auth failures to a message starting `"Re-authenticate: …"` (Buzz's dead-letter matcher) — today the Queue collapses every error into channel text (`queue.ex:398-402`), which no adapter can classify. Bounded public error rendering; raw reasons go to Logger, never the wire. **The `{:failed, reason}` ⇒ JSON-RPC error mapping is conditional as of §16.5** (effect gate, 2026-08-02): a JSON-RPC error invites the client to re-run the whole turn, so it is emitted only when the turn performed **no** externally-visible effect; a failed turn that already acted answers `stopReason: "end_turn"` and the reason goes to the log alone |
| Cancel | `session/cancel` ⇒ new `Queue.stop_conversation/2` (per-key extraction of `stop_all` internals: terminate the active turn task, stopped-turn marker, clear pending) ⇒ `turn_result_fn.({:cancelled})` ⇒ respond `stopReason:"cancelled"`. **The wire fence lives in the Peer**: after responding, late deliveries/stream events for that turn id are dropped-and-logged — the Queue's freshness check is check-then-act, not atomic, and rev 2 does not pretend otherwise. No rollback of already-performed side effects is claimed. `$/cancel_request` naming an in-flight `session/prompt` id runs the same stop path and completes that request with `-32800` |
| Approvals | `session/request_permission` never sent. No `approval_fn` is injected for acp turns ⇒ `request_directory_access` self-hides (its advertise gate requires `approval_fn`). Sandbox escalations end as normal denials whose text says how to grant from an owner surface |
| Detached work | Harness run tools hidden on this surface (their `advertise?/1` gains a channel check — continuations cannot deliver back to a client-owned ephemeral session; with `remote?: true` and no owner configured, `ContinuationDispatcher` would refuse loudly anyway, `continuation_dispatcher.ex:101`). Origin-mode `schedule_job` refused at schedule time with a named message; explicit-target scheduling to other channels works. `/background` is gone with the command pipeline. **Superseded by §17.6** (owner decision, 2026-08-01): with credentials durable the continuation delivers, so harness tools are hidden only on *identity-less* sessions; the `schedule_job` refusal stays on a corrected reason (§17.6(e)). Cite correction: the refusal is `continuation_dispatcher.ex:111`, not `:101` |
| Telemetry | No new event names, no new run kind. **The transport emits the shared channel events itself** — `ChannelTelemetry.emit_parse/emit_message`, exactly as `cli.ex:30,123,189` does; `Gateway.ingest` does not do it for you (rev-1 error). Tools/providers via shared emitters. Overlay secret **values** scrubbed from telemetry content previews (§8.3). Socket lifecycle = structured Logger |
| Config | `[fermix_channels.acp] enabled` — the only knob. **Default `true`** (owner decision 2026-08-01; rev 2 shipped `false` — see §16.4). Socket path fixed; caps internal constants |
| Dependencies | None. Hand-rolled NDJSON JSON-RPC codec (Anubis is MCP-method-bound; hex ACP libs are stale). Upstream `schema.json`+`meta.json` vendored at `apps/fermix_channels/priv/acp/`, pinned by a contract test |

## 5. Goals / non-goals

**Goals**

- G1: An operator adds Fermix to Buzz as a custom harness (label "Fermix", command `fermix`, args `acp`) and org members @mention it like any agent: it answers in-channel via the `buzz` CLI it is instructed and equipped to run, shows live activity in the desktop session viewer, honors cancel/steer-fallback semantics, and carries Fermix's daemon-global memory/skills/persona across harness restarts (conversation transcripts do not survive restarts — Buzz never resumes sessions).
- G2: The same surface works for any spec-v1 ACP client **that passes `mcpServers: []`** (the Buzz-first interoperability profile): honest capability advertisement and negotiation (including version 0 → reply 1), baseline prompt handling (`text` + `resource_link`), `$/cancel_request`, clean stdout.
- G3: Sessions run as first-class gateway conversations: operator tool trust under the real sandbox (session cwd via `request_cwd`), durable memory, full telemetry through existing emitters — with the command pipeline, approvals, and detached work structurally absent.
- G4: The whole surface is one gate: `enabled = false` ⇒ no listener, no socket, nothing advertised anywhere — pinned by a test that enumerates the surface, not per-tool asserts. (The default is `true`, so the gate is what an operator uses to turn the surface *off*; readiness still gates the listener, so an unconfigured install opens nothing.)
- G5: `self_knowledge` updated in the same change; site docs get the BYOH runbook.

**Non-goals (v1)**

- The M23 CoS rail or any Nostr code (**"any Nostr code" superseded by §17.2**: bech32 decode/encode plus one `:crypto` pubkey derivation, used only to name an identity record and print an npub — still no relay client, no signing, no event model). Slash commands on this surface. Steering. `session/load` replay. Session-scoped MCP servers (and with them, general v1 conformance). Modes/configOptions. Plan/thought/usage updates. fs/terminal consumption. Image/audio prompts or outbound media. ACP registry listing. Windows. ACP v2.

### 6.1 Modules

| Module | Job |

### 6.2 The bridge verb

1. Resolve `<FERMIX_HOME>/acp.sock`, connect. Failure: one stderr line ("Fermix daemon not running (or `[fermix_channels.acp]` disabled) — start it with `fermix run`; socket: <path>"), exit 1. No retry loop — the harness owns respawn policy. Note the honest Buzz UX: if the daemon is down at first spawn, all slots fail and the harness exits; the message is in the per-agent log, not necessarily the status summary.
2. Send one hello line: `{"fermix_bridge": 1, "app_version": "<vsn>", "env": {…full process env…}}`. **Wait for one ack line** (bounded: 5 s, 4 KiB): `{"fermix_bridge_ack": {"status": "ok"}}` → become a pure byte pump; `{"status": "error", "message": …}` → print message to stderr, exit 1. `fermix_bridge` is the compatibility integer — app patch skew never refuses. The ack is what keeps daemon refusals off stdout (rev 1 had the bridge "printing the daemon's refusal" with no channel to receive it on — self-contradiction, fixed). Hello caps: 256 KiB, 5 s, enforced daemon-side too.
3. Env filtering happens **daemon-side only** (single policy point; the transport is a same-user 0600 socket — a second filter in the bridge would add code, not security).
4. **stdout purity**: Logger to stderr before any output; no banner; golden test asserts a full session's stdout is byte-exact protocol frames.
5. Lifecycle: stdin EOF → close socket, exit 0. Socket close → stderr line, exit 1. Two pump directions, one coordinator, deterministic EOF handling. SIGKILL from the harness process group needs no cooperation.

Peer treats bridge disconnect as teardown: in-flight turns are cancelled via the same path as `session/cancel` (a respawned buzz-acp slot never reuses sessionIds — verified: fresh `session/new` after any exit).

### 6.3 Core seams (the complete list)

1. `ChannelRegistry` fields `trust:` + `commands?:` with their three consumers (Authorizer first clause; `startable?`/`missing_ingress_authorizations` ingress exemption; gateway command-dispatch skip). Every `local?` call site audited: authorizer (superseded by `trust`), browser reaping `queue.ex:419` (acp is `remote?: true` ⇒ keep-warm, correct), approval `resume_intent` `gateway.ex:516` (inert — no approvals here), continuation `local_channel` (refuses acp loudly — wanted).
2. `Queue.stop_conversation/2` — extraction of the existing `stop_all` per-key internals.
3. `turn_result_fn` — optional agent-message field, three exactly-once invocation sites in the Queue (normal return, error/DOWN, stop).
4. `:raw` stream tier — one clause in the existing stream-spec selection; no DraftStream for this tier.
5. `activity_callback` threading (Queue→TurnRunner→loop opts; `AgentLoop` already accepts it) + the `{:tool_finish, name, %{status: …}}` payload extension (cron watchdog match updated in the same change).
6. Session env overlay — context-carried, consumed at sandbox shell-command env construction only; plus secret-value scrubbing in `Tools.Telemetry.maybe_put_content` (one choke point, driven by a context-carried redaction list).
7. `request_cwd` set from the session's cwd — **zero new mechanism** (existing field, existing policy).

Nothing else in core changes.

Timeout fit (documented, no code): Buzz's 900 s idle clock resets on every chunk and at every tool *start* (`tool_call`). A single silent tool exceeding 900 s still trips it; v0.5.2 has **no UI field** to raise the limit (the record field exists but nothing sets it), so the honest v1 posture is: long delegated work belongs on owner channels, not Buzz mentions — consistent with detached-work tools being hidden here anyway. No keepalive hacks (masks real hangs). **Superseded by §17.6(f)** (owner decision, 2026-08-01): *delegation* never fought this clock — the launching turn returns a run id immediately and the completion arrives as a new turn with its own clock — so the constraint applies to long **foreground** tools only.

## 8. Session & turn design

### 8.1 Keying, queueing, persistence

Conversation key `{"acp", session_id, :root}`. One FIFO turn per key via the existing Queue; distinct sessions parallel. History persists in ConversationStore under the key; compaction and memory review run normally. Harness restart ⇒ new sessionId ⇒ new conversation, by construction (Buzz never calls `session/load`); what carries over is daemon-global: curated memory, skills, persona. Stated as-is in docs and `self_knowledge`.

### 8.2 Prompt folding

`text` blocks verbatim; `resource_link` ⇒ `[resource: <uri> (<name>)]`; `image`/`audio`/`resource` ⇒ `-32602` (capabilities are honestly false). Blocks join `\n\n`. With `commands?: false`, Buzz's slash pass-through block (single-event batches only, §2.2) lands as ordinary model text — the model can act on "/compact please" conversationally, but no Fermix command executes. `metadata.user_id` unset; sender attribution stays inside the prompt text where Buzz put it (§11).

### 8.3 The env overlay (the Buzz-reply enabler)

> **Custody superseded by §17** (owner decision, 2026-08-01). The allowlist, the single consumption point, the telemetry scrub and the test discipline below all stand; what changes is lifetime — the filtered env becomes a durable client identity, and both live and continuation turns build the overlay from that record (§17.1). Read "RAM-only … dropped at session end" below as describing rev 2.

- Peer stores the daemon-filtered hello env per connection; each session snapshots it with its cwd. Tool executions for that conversation build their **sandbox shell-command** env as policy env ⊕ overlay (overlay wins on its keys; PATH included — the harness's PATH is what makes `buzz` resolvable). One consumption point; git/file/MCP/other tools untouched.
- **Custody, stated honestly (peer-parity, not invisibility):** any shell command the model runs in this session can read `BUZZ_PRIVATE_KEY` — exactly as it can for claude/codex under Buzz today, whose children inherit the same variables from the same harness with `bypassPermissions` on top. Fermix is strictly tighter (sandbox modes, profiles, hardline blocklist still bind). The key is Buzz-owned and relay-revocable (remove the agent, rotate). The overlay is RAM-only session state, never persisted, dropped at session end.
- **The boundary that is Fermix's own to defend is telemetry export**: tool output previews are captured under `capture_content` (`tools/telemetry.ex` `maybe_put_content`), so the two secret *values* (`BUZZ_PRIVATE_KEY`, `NOSTR_PRIVATE_KEY`) ride the context as a redaction list and are scrubbed at that single choke point before any preview is attached. Conversation history may still contain what the model chose to print — local SQLite, same trust domain as the harness's own logs; accepted and documented, not hidden.
- Non-Buzz clients: the allowlist matches nothing but PATH — tools see the client's PATH and run in the project root the client chose. Right for editors.
- Tests (the 2026-07-26 env-sanitizer lesson, both halves): **fidelity** — seeded fake `BUZZ_*` env + a fake `buzz` on the overlay PATH is reachable from a shell exec inside the session; **isolation** — absent from sibling conversations, absent after session end, and secret values absent from telemetry previews *even with* `capture_content: true` and a command that prints them.

### 8.4 Streaming and tool events

`:raw` tier: the Queue threads the adapter-built callbacks directly (no DraftStream). Peer keeps `sent_len` per turn; `text_delta`(cumulative) ⇒ suffix chunk; final `{:text, response}` ⇒ emit unsent suffix (or the whole text for unstreamed turns). Reasoning events dropped (v1); any *additional* `{:text, …}` delivery after the final reconcile (compaction notice — it is delivered post-commit, `queue.ex:396`) is dropped-and-logged: an internal housekeeping notice, not part of the reply. Tool events per §4: `tool_call` at start (kind from policy class: shell/harness/computer-use ⇒ `execute`, web/http ⇒ `fetch`, read/search classes ⇒ `read`/`search`, else `other`; toolCallId minted sequentially per turn), `tool_call_update` with the real `:ok | :error` outcome at finish.

### 8.5 Cancel

On `session/cancel` (or bridge disconnect): `Queue.stop_conversation(key)` (kill active turn task synchronously, stopped-turn marker — precisely right for Buzz's merged re-prompt — clear pending) → `turn_result_fn.({:cancelled})` → respond `stopReason:"cancelled"` → **Peer fences the turn**: any late delivery/stream event for that turn id is dropped-and-logged. The freshness check in the Queue is check-then-act; the fence is what makes the *wire* clean — rev 2 claims exactly that and no more (no atomic finalization machinery, no rollback of side effects; in-flight sandboxed subprocesses die with the task's tree via the existing CommandHost group-kill). Cancel-to-response target well under 1 s, pinned by test, against Buzz's 5 s drain.

## 11. Security model

- **Transport trust.** The bridge is spawned by a process running as the operator on the operator's machine over a 0600 UDS under `FERMIX_HOME` — the same class as `fermix ask` and the realtime socket. `trust: :local_operator` encodes it in the registry instead of overloading `remote?`.
- **Content posture, stated plainly.** Under Buzz, channel members' words arrive inside operator-trust prompts: whoever can @mention the agent drives its tools. This is the same envelope the operator already accepted for claude/codex under Buzz (full tools, `bypassPermissions`, same credential-bearing env) — and Fermix binds it tighter: sandbox floor/modes/profiles and the hardline blocklist gate every command, `:network`-class tool output renders inside untrusted framing. What Fermix **removes** from that envelope on this surface: the entire slash-command pipeline (`commands?: false` — no `/sandbox grant|revoke|confirm`, no `/soul`, no `/background`, nothing), the approval flow (no `approval_fn` ⇒ `request_directory_access` self-hides; a client that auto-answers `allow_once` can never mint a grant), and detached work (harness tools hidden; origin-mode scheduling refused). There is no claim that "owner-only boundaries hold" beyond this list — rev 1 made that claim and it was false. Operators who want a guest-trust Buzz presence use the M23 rail; a third trust tier for "delegated" content is rejected for v1 as machinery without a second customer (§13).
- **Session credentials.** Peer-parity custody, one Fermix-specific hardening: secret values scrubbed from telemetry export previews (§8.3). RAM-only, never persisted, closed struct with a custom `Inspect`, dropped at session end. Relay-side revocation is the recovery path (remove agent, rotate key). **Superseded by §17** (owner decision, 2026-08-01): custody is now connected-provider — a 0600 durable record kept until the operator disconnects it. The scrub, the closed struct and the custom `Inspect` move onto that record unchanged; relay-side revocation remains the recovery path, and §17.7 states the threat delta.
- **Workspace.** `request_cwd` reuse means the *existing* policy decides: standard mode admits an inside-home session cwd as a root (never `$HOME` itself, canonicalized, blocked-roots enforced — `sandbox/mode.ex`), strict admits nothing, open already covers home. A hostile cwd cannot widen scope beyond what that policy always allowed.
- **Socket surface.** 0600, stale-probe before unlink, 64-connection cap, 10 MiB line cap, 256 KiB/5 s hello caps, one in-flight prompt per session, malformed frames answered with parse errors. `enabled = false` removes everything (G4).
- **Injection.** Prompt text is ordinary channel input — Content-Is-Data applies; nothing in it can reach commands (none), approvals (none), other sessions' overlays, or another Peer's sessions (Peer-local tables).

## 13. Rejected alternatives

- **Standalone boot / boot-if-daemon-down hybrid**: SQLite single-writer + forked memory; Rule 12.
- **A third trust tier ("delegated") or per-channel capability profiles**: real machinery through TurnRunner/CapabilityRegistry/commands for exactly one surface, when disabling the command pipeline + hiding detached tools achieves the material risk reduction with two registry fields. Revisit only when a second delegated surface exists.
- **Framework-owned Buzz posting** (`Acp.BuzzDelivery` running the `buzz` CLI): double-posts against a model the injected base prompt *instructs* to post; requires parsing Buzz's `[Context]` prompt text for reply anchors (coupling to a prompt format Buzz can change silently); makes core delivery Buzz-specific. Its motivating hole — command replies invisible in-channel — is closed by removing commands; error visibility is provided by Buzz's own dead-letter/retry notices once failures are JSON-RPC errors (§4). If a future client needs framework posting, it is a new design, not a fallback here.
- **Per-binary credential injection** (env visible only to `buzz` invocations): matching "the command is really `buzz`" on shell-mediated strings is unsound (compound commands), and a sound matcher is a new security-relevant parser — complexity with a false-safety smell. Peer-parity + export scrubbing is honest instead.
- **Claiming `protocolVersion: 2`**: buys `systemPrompt`-via-param today, breaks the day Buzz adopts real v2 semantics. Legacy framing is verified-working.
- **The streaming quartet / DraftStream for acp**: block mode emits reasoning side-blocks and post-final notices — concatenation would lie; draft mode's throttle/edit semantics solve a chat-UX problem this wire doesn't have. A raw tier is less code end-to-end.
- **Reusing `realtime.sock`/`daemon.sock`**: different wires, different version cadences.
- **Anubis / hex ACP libs as the codec**: MCP-method-bound strict validation / stale pre-2026 surfaces.
- **`remote?: false` (rev 1)**: broken authorization via `Source.channel_key` derivation, plus per-turn browser reaping on a persistent-session surface.
- **Mapping sandbox approvals onto `session/request_permission`**: the first target client auto-answers `allow_once`; an approval UI that cannot decline is not one.
- **A keepalive to defeat Buzz's idle timer**: masks real hangs; the honest posture is "long detached work doesn't belong on this surface" (and its tools are hidden here).
- **A `trust` config knob**: a security boundary as a toggle invites the guest-but-actually-operator misconfiguration; postures are rails (this one, M23), not knob values.

### 16.1 Deviations that change a design decision

1. **The harness prompt/wire mismatch was fixed by removing the category, not by gating the prose.** §4 hid harness *tools* on acp turns, but `Prompt.RuntimeSections` renders the "Coding Harness" section from `HarnessConfig` alone, so an acp turn was told to route work to `codex_run` while no harness tool was on the wire (the M28 pitfall shape). Fix: the client-owned trust profile is built with `excluded_categories: [:harness]` — an existing knob already used by realtime/voice — cached as a `harness_free_profiles` variant on `RuntimeContext` (required field, `Map.fetch!`, fail-loud). Prompt text and advertised schemas now derive from **one** list, which is the actual cure for the drift class. **Consequence beyond the design's wording:** the harness family leaves `profile.capabilities`/`dispatchable` entirely on acp turns, so a by-name `codex_run` dispatch misses the tool instead of reaching the execute-time `Harness.Authorization` refusal. Judged more correct (§4 says such a run cannot deliver its continuation, so the alternative spawns a real vendor CLI, does real work, then fails to report), and reversible in one line if the owner disagrees. **Partially superseded by §17.6(b)** (owner decision, 2026-08-01): the two-variant cache and the one-list cure stay exactly as built; what changes is that the harness-free variant is selected per *turn* on identity presence rather than unconditionally on the channel — which makes the predicate's two call sites (`turn_runner.ex:1087-1090` and every `advertise?/1`) have to be fed one identical input, or this same drift class returns.
2. **The env overlay reaches the shell tool via `Sandbox.shell_plan/3`, not only `Sandbox.CommandTool`.** §8.3 named "sandbox shell-command env construction" as one consumption point; in reality `Tools.Shell` builds its env through `Env.build/3` while `CommandTool` uses `Env.build_command/3`. As first built, a shell exec on an acp turn saw neither the harness `PATH` nor `BUZZ_PRIVATE_KEY` — i.e. reply publication (§2.4 problem 1) did not work. Both callers now share one caller-side merge helper on `Sandbox.Env`; `build/build_command` semantics are unchanged, so every non-acp caller is byte-identical. Corollary worth knowing: `git_read`/`git_write` run through `CommandRunner` with an additive env and never see the overlay, so the allowlist's `GIT_*` keys only take effect when the model runs git *through the shell tool*.
3. **The telemetry scrub is broader than §8.3 described.** §8.3 specified scrubbing the `:input`/`:output` previews. Implementation found those are capture-gated while caller-supplied `:metadata` is merged **unconditionally** — and `Tools.Shell` passes `metadata.command` (verbatim command text) plus an `error_summary` that embeds child stdout on a non-zero exit. A command containing the key, or a failing command printing it, therefore exported the secret on the always-on path. The scrub now also covers metadata values (recursive, depth-capped at 8, same `«redacted»` marker and 8-byte floor, structs passed through, zero traversal when `redact_values` is empty). The guarantee is now strictly broader than the prose.
4. **The `schedule_job` origin refusal lives in `Jobs.DeliveryDefaults.resolve/3`**, not `schedule_job.ex` (§9). That function has exactly one caller and is the only place the *resolved* mode is known — a `default_delivery_mode = "origin"` config default never appears in the tool's args and would have slipped past a check on raw args.
5. **Doctor's acp section is a `Fermix.CLI.Doctor.Checks` row**, not a `Setup.Doctor` probe (§9 item 5). Every doctor row lives in `Checks`; `Setup.Doctor` is the probe library that runs in the tree-less CLI VM where the Endpoint cannot exist. Liveness goes over the daemon control socket's existing `health` method (no new socket method, no new payload field). `Setup.Doctor.enabled_probe_channel?/1` gained one clause so a `trust: :local_operator` channel is not reported as "enabled but unprobed". `Channels.Acp` deliberately exports no `health_check/1` for the same reason.
6. **`FermixCore.Readiness` is unchanged.** §9 item 6 called for a check; acp has no credential and no external dependency, so the correct implementation is the *absence* of one (a check that always returns nil is dead code). Behavior is pinned by tests only.

### 16.2 Smaller deviations, grouped

**Wire/codec (Stage 0).** The contract test pins *structure* (every `known_methods/0` entry present in the vendored `meta.json`, schema `$defs` presence, checksums in `PROVENANCE.md`) rather than running full JSON-Schema validation — §4 forbids a new dependency. `decode_line/1` additionally rejects non-object `params` (`-32602`), a non-string/number `id` and an empty/non-string `method` (`-32600`), and treats explicit `"id": null` as a notification — validating at the codec rather than silently coercing (Rule 12). `Wire.Error` is a struct defined in `wire.ex`.

**Gateway/queue (Stages 1–2).** The gateway's closures tuple became a keyed map (7 members); `run_commands/5`, `configured_stream_spec/3`, `build_agent_message/3` extracted to hold the size rule. `stream_capability/0` is typed `:draft_edit | :raw | :none` (`:none` is load-bearing in the existing docs). `AgentLoop`'s internal tool-result map gained `status: :ok | :error` (`text_result/1` → `/2`, 6 call sites) because that map is the only non-heuristic carrier of the outcome. `turn_result_fn` is stashed only in the queue's active-turn entry and claimed via `{:claim_turn_result, key, pid}` — the claim is what makes exactly-once hold under a stop-vs-completion race. Two outcome sites beyond the three specified: a failed turn-state checkout and a failed `Task.Supervisor.start_child` each fire `{:failed, reason}` (both already reply to the channel and neither produces an abnormal DOWN, so without them a turn would end with no terminal signal).

**ACP surface (Stage 3).** Session ids are `"acp-" <> 32 hex`, not a UUID. `$/cancel_request` naming a pending *non-prompt* id is dropped-and-logged: every non-prompt request is answered synchronously inside its own frame, so that state cannot occur. `:iteration_started` is *consumed* (resets the cumulative-delta baseline) rather than ignored — the loop's `text_delta` snapshots are cumulative per iteration, so without it a multi-iteration turn puts sliced garbage on the wire. `Endpoint` traps exits so `terminate/2` releases the listen socket and the socket file on every path. Tool-kind map extends §8.4's: `:read_write`/`:exec`/`:gui_control` → `execute`, `:external_api` → `fetch`. Test-injectable opts (`:socket_path`, `:max_connections`, `:hello_timeout_ms`, …) mirror `Realtime.LocalVoiceSocket`'s seam shape and add no operator-facing knob.

**Bridge verb (Stage 4).** Module is `Fermix.CLI.AcpCommand` (house naming, every sibling verb is `*Command`). **`:io.setopts(encoding: :latin1)` before pumping is required and the design missed it** — Elixir stdio defaults to unicode, so `IO.binwrite` double-encodes every non-ASCII byte and corrupts the protocol stream; a byte-exactness test on ASCII fixtures passes while production breaks. Connect errors outside the daemon-down family (`enoent`/`econnrefused`/`timeout`/…) get their own named line rather than being collapsed into "daemon not running" (M28 lesson on distinct failure kinds). The bridge does not enforce the 256 KiB hello cap client-side — the daemon is the single policy point (§6.2.3) and a second cap would be duplicate policy. `application.ex` needed no change: `acp` already falls through to the tree-less `System.halt(run_cli(argv))` clause. `Timeouts.acp_bridge_hello/0` (5 s) is now read by both ends.

**Setup (Stage 5).** No interactive wizard *question* — acp gets a flag plus a web toggle, following the `computer_use_enabled`/`harness_approved` precedent for off-by-default advanced features. `config/config.exs` declares `acp: [enabled: false, mode: :gateway]`; `mode` is a registry-shape constant, never asked for, never rendered to TOML, and `normalize_acp/1` accepts only `enabled` — so `enabled` remains the one operator knob. The health payload carries `process_alive` but no peer/session counts (§9 item 7): `fermix_core` has no compile dependency on `fermix_channels`, so counts would need reflection — the accessors (`Endpoint.connection_count/1`) exist when wanted.

### 16.2b Stdout purity needed a second, earlier redirect (found by manual dev-daemon testing)

§6.2 item 3 said "configures Logger to stderr before any output", and `AcpCommand` does — but that is **too late**. `config/runtime.exs` calls `ConfigStore.bootstrap_runtime_config/1` before any application starts, and a boot warning there (an unresolvable `@keyring` sentinel, a plaintext-secret notice) goes to the default handler = **stdout**, ahead of the verb's own redirect. Reproduced from source (485–582 stdout bytes) and confirmed for the release path from the built `start.script` boot order: the config provider runs after only `kernel`+`stdlib`, so Erlang's `:logger` owns the default handler (`logger_std_h`, `type: standard_io`) and Elixir's Logger has not started yet.

Fix: `config/runtime.exs` sniffs argv (`System.argv/0`, plus `Burrito.Util.Args.argv/0` when running standalone) and, **only for the `acp` verb**, points the default handler at `:standard_error` before hydration. **Both redirects are load-bearing** — a release starts the `logger` app *after* the config provider, and `Logger.App.start/2` re-adds a `:default` handler that falls back to `standard_io`, so the verb's own move is what re-establishes the guarantee. Regression test is necessarily a **subprocess** test (an in-process assertion cannot observe output emitted before app start), asserting stdout is byte-empty while stderr carries the refusal.

Two consequences worth carrying forward: any future stdio-protocol surface inherits this hazard and needs the same argv sniff; and an invocation that does not put the verb in argv (e.g. calling `AcpCommand.run/2` directly from `mix run -e`) misses the sniff and leaks — the dev wrapper must dispatch through `Fermix.CLI.main/1`. Related: under a locale-less GUI spawn (`env -i`), stdio opens as latin1 and the refusal's em dash renders as `\x{2014}` on **stderr** — cosmetic only; the pump was proven byte-identical for UTF-8 payloads under both `env -i` and a UTF-8 locale, because `raw_mode/1` pins both devices to latin1 and writes via `IO.binwrite/2`.

### 16.4 The surface ships ON by default (owner decision, 2026-08-01)

Rev 2 specified `enabled = false`, argued from minimal-knobs and the house pattern (inbound MCP, computer use, harness approval all default off). The owner overrode it on a discoverability argument that beats it: a user who never learns the surface exists adds Fermix to Buzz or Zed, hits the refusal, and concludes Fermix has no ACP support — the feature fails silently for exactly the people it is for.

The security review that supports the flip: the socket is 0600 same-user, and **`~/.fermix/daemon.sock` is already always-on, unauthenticated** (its own comment: "the trust boundary is the 0600 socket file") and strictly *more* capable — its `agent_message` path runs through the `cli` channel with the slash-command pipeline enabled, reaching `/sandbox grant`, `/soul`, `shutdown`, `plugins_apply`. The acp entry carries `commands?: false`. Default-on therefore adds no new privilege class, and gating the §8.3 env overlay behind a second knob (floated in review) would have been theater against that baseline. Readiness still gates the listener, so an unconfigured install opens nothing.

Two implementation findings, both of which invalidate reasoning stated earlier in this doc:

1. **One line in `config/config.exs` was NOT sufficient — the release would have ignored an operator's `enabled = false`.** `ConfigStore.apply_channel_config/2` merges persisted TOML over the compile-time default, so an absent `[fermix_channels.acp]` section correctly inherits the new default (this is what makes `brew upgrade` seamless: no existing config.toml carries the section, since the feature never shipped). But `Config.Provider.boot/1` ends with `Application.put_all_env(merge(sys.config, runtime.exs declarations), persistent: true)`, so any key declared in `config/config.exs` and **not re-declared in `config/runtime.exs`** is reset to its compile-time value *after* `bootstrap_runtime_config` hydrated it. All five sibling channels re-declare themselves (`config :fermix_channels, telegram: Application.get_env(...)`); `:acp` did not, so a persisted `false` would have been silently overwritten back to `true` in a release. Fixed by adding the same re-declaration. Invisible under `mix`, where `loadconfig` applies only what runtime.exs declares — which is why it took decompiling the provider to find. **The same gap still exists for `:fermix_core` `:jobs` and `:transcription`** (found, not fixed — a separate change).
2. **A failed socket bind took down the whole daemon.** `Endpoint.init/1` returned `{:stop, reason}`, which propagates through `FermixChannels.Application` and kills boot — reproduced with a 121-character `FERMIX_HOME`, where `acp.sock` exceeds the platform `sun_path` limit (~104 bytes on macOS) and `:gen_tcp.listen` returns `:einval`. Unreachable while the surface was off; with it on, every ready install binds at boot, so one unbindable path bricks the daemon entirely — no agent, no channels, not even the CLI control socket. Fixed so an unbindable listener refuses loudly and returns `:ignore`, leaving the daemon up (a bad Telegram token does not kill boot either), with a pre-flight path-length check because `:einval` is unreadable as a diagnosis. Verified against a real `:fermix_core` + `:fermix_channels` boot: with a 121-byte `FERMIX_HOME` the tree, its sibling children and the daemon all survive, no socket is created, and the operator gets one line — *"ACP is disabled for this boot: the ACP socket path is 130 bytes, over the 103-byte limit this OS allows for a unix socket address — set a shorter FERMIX_HOME and restart. Path: …"*; with a short home the endpoint binds at 0600 and serves a real client. Failure kinds stay distinct (path-too-long / permission-denied-bind / permission-denied-mkdir / another-daemon-listening), the live-socket case is now proven non-destructive (the other daemon's socket survives *and still accepts clients*), and a fresh-machine first run is pinned alongside the fail-closed branches per the pre-flight pitfall. `Health` already reported a non-started endpoint as `:degraded` with `process_alive: false`, and doctor turns that into an actionable row — verified, unchanged.

Setup copy was also cut to one sentence — "Lets clients like Zed or a Buzz harness drive this daemon over a local socket." — matching the other channel toggles; the omitted detail (no token, no slash commands, restart required) belongs in docs, and the restart is already carried by the restart-key affordance.

### 16.5 Live Buzz acceptance, and the fix set it produced (2026-08-02)

Stage 6 ran against a real Buzz org and produced one compound failure: the model posted its reply in-channel with the `buzz` CLI, the turn then ended in a provider error, the Peer answered the prompt with a JSON-RPC error, buzz-acp requeued the batch, and **the same reply was posted five times**. Five changes landed, plus §17 in full.

1. **The effect gate** (§17.10's first pending decision, now built). `Channels.Acp.Session` carries a per-turn effect ledger; `Peer` records one effect per tool that **succeeded** and was not a `read` — fail closed on the coarse kind map, so a capability nobody registered renders as "other" and counts, while a tool that failed performed nothing and leaves the ledger alone. `Peer.apply_turn_result/3` then branches: zero effects ⇒ today's JSON-RPC error (the user got nothing, so re-running the turn is exactly the right response), one or more ⇒ `stopReason: "end_turn"` with the raw reason on `Logger.error`. Verified in buzz-acp's own source rather than inferred: a `stopReason` response is handled with `batch: None`, so **no requeue happens** — the terminal answer is what stops the repetition, not a retry cap. The honest cost is in the §4 table: Buzz raises no in-channel failure notice for an effect-bearing failure.
2. **The Codex empty-continuation gate** (§17.10's second). A `completed` response carrying output items but rendering neither text nor a tool call is a **legitimate empty turn** — under Buzz it is the *normal* ending, because the reply was published by a shell tool and the model has nothing left to say — and the loop already models it (`AgentLoop`'s empty completion, the queue's `handle_empty_completion/1`). Calling it a provider failure is what produced the `-32603` above. **Item count is the discriminator, not usage**: `output_tokens` counts reasoning tokens, so it is non-zero for turns that produced nothing at all, and zero items under a terminal event stays an error (the cron regression `811d0ad3`/`c258142c`). The genuinely undelivered case is no longer minted as `:transport_closed` — nothing was cut — but as `ProviderError.api/5` with `code: "empty_response"`, which is retryable by no classifier and failover-eligible for none, so a turn that already acted is never re-issued. `undelivered/2` also logs status, usage and item types: that path was silent through the whole incident.
3. **Identity custody (§17), implemented.** `FermixCore.Nostr.Key`, `FermixCore.Acp.Identity` and `FermixCore.Acp.IdentityStore` in core; Peer binding with `SessionEnv` deleted; the `client_origin_json` `ALTER TABLE` migration plus continuation delivery; the advertise gate widened to "identity-capable session"; and the operator surfaces — `fermix doctor`'s identity list (npub only, read straight off disk, rendered **ahead** of the `enabled` short-circuit) and `fermix acp forget <npub> | --all`. One rendering of an `IdentityStore` failure serves both (`AcpCommand.identity_error_message/1`), so a broken record cannot be described two different ways.
4. **Failed-turn observability.** `[:fermix, :agent, :message_error]` now carries the same identity and the same content-gated **input** a successful turn does (no output — the turn produced none; `reason` carries the failure), and `Codex`'s error path reports the usage it actually measured instead of an empty map. Both existed because the incident's traces read as "nothing came back on the wire" while the model had in fact spent 12.5k prompt tokens, reasoned, and run a tool.
5. **A failed turn no longer orphans its user message (channel-wide, not acp-only).** The runner persists the user message before the loop and a failed turn commits no assistant message, so the row was left dangling; `Queue.deliver_turn_error/2` now closes it with the same stopped marker a cancel uses. Without it, any legitimate retry — durable, or a client re-running the prompt — reaches the model with no record of what the failed turn already did, which is the same repetition class as the effect gate one layer down.

## 17. ACP client identities: provider-connection custody (rev 3 direction)

**Status:** rev 3 — owner decision 2026-08-01, **implemented 2026-08-02** across Stages 1–5 (log: §16.5 item 3). Supersedes the session-scoped credential custody in §4 ("Env overlay", "Detached work"), §7's timeout note, §8.3, §9 ("Deliberately skipped"), §11 ("Session credentials") and the *unconditional* half of §16.1 item 1. Everything else in §§1–16 stands, including §13's rejection of framework-owned Buzz posting.

Rev 2 held the client's presented env as `Acp.SessionEnv` — a closed struct, RAM-only, per-connection, dropped with the socket (`session_env.ex:14-18`, `peer.ex:254-264`). A live Buzz test surfaced the two consequences that follow from that choice and from nothing else: **coding-harness tools are hidden here** (§4 "Detached work") because a run terminalizes minutes later through a continuation re-ingest, by which time the credentials are gone; and **any daemon or harness restart forgets credentials nothing revoked**. The operator asked Fermix, over Buzz, to do a coding task expecting harness delegation, and no harness tool was on the wire.

**The owner's directive (design constraint, not up for debate):** credentials an ACP client presents are a **connected provider**, not session state. Fermix already persists every comparable credential until it is explicitly disconnected — provider OAuth/API keys (`Auth.Store` → `auth.json`, `auth/store.ex`), plugin tokens (`Plugins.Auth` login/logout over the same store), channel secrets (`SecretWriter`/`SecretPaths` keyring) — and M23 §9 item 4 already plans keychain custody for `BUZZ_PRIVATE_KEY` on the CoS rail. The peers prove the model too: under Buzz, claude and codex read durable credential stores of their own (`~/.claude/.credentials.json`, `~/.codex/auth.json`) that outlive every harness session — the daemon holding a durable credential for a Buzz agent is the custody class the operator already runs. **Persist on first presentation, refresh on re-presentation, keep until the operator disconnects.**

The second-order win is the point: with custody durable, **the continuation blocker dissolves** — a continuation turn re-ingested into the acp conversation builds its tool env from the persisted identity and posts the outcome with the `buzz` CLI exactly as a live turn does — so harness tools return to Buzz-capable ACP sessions (§17.6).

### 17.1 The rule: one source for turn env

After this change there is **exactly one producer of a turn's `session_env`**: `Acp.Identity.to_env/1`, applied to the record the turn's session is bound to.

- A session bound to a **durable** identity resolves it **from the store at message-build time**, never from connection state. A rotation persisted by another connection therefore takes effect on the next turn (last-writer-wins), and a live turn and a continuation turn read the same bytes.
- A session with **no** identity (§17.5) holds an *unpersisted* `%Identity{id: nil}` built once at hello, and calls the same `to_env/1`.
- A durable read that **misses or is refused** (the operator forgot the record; it was quarantined; its perms were changed) is not a fallback and not a third state: the connection **transitions** to the identity-less state for the rest of its life, with one named warning per kind (§17.3). It does not re-read on the next turn, so the state cannot flap; a reconnect re-presents and re-persists.
- One record type, one env constructor, one authority for durable records.

Placement, which the seam depends on: `Identity` and `IdentityStore` live in **`fermix_core`** (§17.2 "Placement") because their central call sites are core modules. `fermix_channels` is a caller on both ends — exactly as the plain `session_env` map crosses that boundary today.

**Forbidden, explicitly (Rule 12): "live env with persisted fallback."** There is no path where a turn reads connection state *and* falls back to the store, or reads the store *and* falls back to connection state. A durable identity is never read from connection state; an identity-less connection never consults the store. Two configurations, one path. `SessionEnv` is **deleted**, not kept beside the store — its allowlist becomes `Identity.new/1`'s filter and its redaction discipline (values never rendered; `Inspect` prints key names only, `session_env.ex:76-90`) moves onto `%Identity{}` verbatim.

### 17.2 Decisions locked (rev 3)

| Question | Decision |
|---|---|
| Custody rail | **A durable daemon-owned record store — `auth.json`'s discipline, its own directory: one file per identity.** `$FERMIX_HOME/acp_identities/<pubkey hex>.json`, directory 0700, records 0600, `{"version": 1, …}` per record, atomic tmp→chmod→publish, a corrupt record preserved as `<hex>.json.broken.<ts>` and refused loudly, permissions validated on read — every discipline copied from `Auth.Store` (`auth/store.ex:53`, `:83`, `:97`, `:154-163`). **Not `auth.json` itself**: its `normalize/2` hard-requires a non-empty `tokens.access_token` (`store.ex:154-163`), `list_profiles/1` silently drops entries without one, and every consumer (`TokenManager`, `TokenSupervisor`, `Setup.Doctor.stale_token_profiles/0`, `fermix auth status`) assumes a refreshable, expiring token. A relay signing key is none of those; shoehorning it into `access_token` would teach four readers a second record kind to keep an unearned "we reused it" claim |
| Placement (which app owns what) | **`FermixCore.Nostr.Key`, `FermixCore.Acp.Identity` (allowlist filter, `new/1`, `to_env/1`, `id_from_env/1`, `posting_capable?/1`) and `FermixCore.Acp.IdentityStore` all live in `fermix_core`.** `FermixChannels.Channels.Acp.*` and the channels-side `ContinuationDispatcher` are **callers only**. Forced, not preferred: core's `deps/0` declares only `fermix_nif` (`apps/fermix_core/mix.exs:35`) and, dev/prod-only, `fermix_opik` (`:66`) — so core cannot see `fermix_channels` — and two of the three central call sites are core modules (`Tools.HarnessSupport`, §17.6(a); `Harness.Delivery.resolve_snapshot/2`, §17.4). Naming the record in the channels namespace would leave them uncompilable and force the seam to be redesigned under pressure at Stage 3/4. This is the same direction the plain `session_env` map already crosses (channels builds it, core consumes it), and the same shape as `FermixCore.Realtime` — a client-protocol data model core owns while the client lives elsewhere. The one-way rule is also *why* the dispatcher is module-injected (§17.6(c)) |
| Concurrency | **The filename is the serializer; there is no lock and no singleton writer.** `Auth.Store` can get away with none because "callers are serialized in-process: TokenManager is a singleton GenServer" (`auth/store.ex:9-12`) — untrue here: writers are N `Acp.Peer` processes, and buzz-acp spawns a pool of `parallelism` bridges per agent (default 10, max 32, §2.1) with N agents supported (§17.5). Atomic rename prevents a torn file, **not a lost update**: two hellos interleaving read-modify-write on one shared JSON drop a record silently. One file per identity removes the read-modify-write entirely — a whole-file write **is** the record, and two agents write different paths. It also holds **across VMs**, which a GenServer cannot: `fermix acp forget` runs in the tree-less CLI VM (§17.3) and would otherwise race the daemon's writer. Mechanics: write the record to a 0600 tmp in the same directory, then `:file.make_link/2` onto the target — `:ok` means *this* process created it (the one consent `Logger.info`), `{:error, :eexist}` means a record exists, so compare and `:file.rename/2` over it only when the material changed, else drop the tmp silently. Readers never observe a partial or empty file on either branch, and perms are 0600 from creation. A hard link is safe to require: `FERMIX_HOME` already holds a SQLite database and unix sockets, so it is already a local filesystem |
| Not the keyring | `SecretPaths` is a compile-time `@secrets` list keyed by a fixed atom (`secret_paths.ex:16`, `:228`), and `SecretWriter` derives the keychain coordinate from that entry's `env` name — **N runtime identities cannot be named in it**, and "keyring where a writer exists, file otherwise" is precisely the Rule-12 fallback. The line the repo already draws holds: **operator-configured secrets are settings → keyring; runtime-acquired credentials are data → a 0600 Fermix-owned file**, which is exactly what `auth.json` has always been. This is not a Fermix keystore in M5's sense: it holds what a client handed the daemon, and never offers to hold the operator's arbitrary secrets |
| Relation to M23 | **Sibling stores, deliberately separate, and the separation is the point.** M23's `BUZZ_PRIVATE_KEY` is *Fermix's own* org identity — one per daemon, chosen by the operator, a **setting** → `[fermix_channels.buzz] private_key` + `SecretPaths` + keychain (M23 §9 item 4, §11). An ACP-presented key is *Buzz's* identity for a Buzz-managed agent — N per daemon, arriving at runtime → this store. Merging them would force one static atom per client (impossible) and let a client's credential collide with the operator's own `BUZZ_PRIVATE_KEY` keychain item. **Hard invariant: a record in this store is never readable as the CoS identity, and the `buzz` channel/`buzz_workspace` tool never consult it** — the failure mode (a CoS turn signing as a client-managed agent, or the reverse) is silent |
| Identity key | The agent's **x-only public key, lowercase hex**, derived once from the presented `BUZZ_PRIVATE_KEY`; the **npub** is its display form and the only form ever printed (M23 §11 hygiene, carried verbatim). New `FermixCore.Nostr.Key`: `decode_secret/1` (bech32 `nsec` or 64-hex → 32 bytes), `public_hex/1` (`:crypto.generate_key(:ecdh, :secp256k1, sk)`, x-only = bytes 2..33), `npub/1`. Pure Elixir, `:crypto` only, **no relay client, no signing, no event model** — and it *is* the npub↔hex normalizer M23 §9 item 3 plans, so M23 consumes this module instead of writing a second one (the two stores must never disagree about what an npub means) |
| Derivation failure — and why "identity-capable" is **one** fact | An unparseable or underivable `BUZZ_PRIVATE_KEY` **is not an identity**: nothing is persisted, one `Logger.warning` names the reason, and the connection proceeds identity-less (§17.5). One state machine, two states, no fallback — "identity-capable" is "an identity id was derivable", full stop. **The hazard is that the §4 allowlist filters by key *name*** (`session_env.ex:29-38`), so a malformed nsec passes the filter untouched, and "the env carries a `BUZZ_PRIVATE_KEY`" (what the advertise gate cheaply sees, §17.6(a)) would then disagree with "an id was derivable" (what persistence, the ledger snapshot and the continuation use). Made equivalent **by construction**: `Identity.new/1` **drops `BUZZ_PRIVATE_KEY` and `NOSTR_PRIVATE_KEY` when no id is derivable from them** — an unusable signing secret is not worth carrying into a turn, and keeping it would only buy a `buzz` call that fails at the relay. A record carries a key **iff** it has an id, so the two questions have one answer. The same rule covers a failed `upsert`: the Peer binds an id only after the store returned `:ok`; on a write failure it logs a named warning and **rebuilds the record identity-less before the connection's first turn**, so no turn ever holds a key whose record is not on disk. Without this the surface reproduces the exact outcome §16.1 item 1 rejected — a real vendor CLI does minutes of work and then cannot report |
| Record shape | `%Identity{id, kind: :buzz, display_name, relay_url, auth_tag, path, git_config, secrets, first_seen, last_seen}`. `secrets` = `BUZZ_PRIVATE_KEY` + `NOSTR_PRIVATE_KEY`; `git_config` = `GIT_TERMINAL_PROMPT`/`GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`. `to_env/1` reconstructs exactly the §4 allowlist map from these fields — the allowlist is enforced on the way *in* (`Identity.new/1`) and the shape is regenerated on the way *out*, so nothing outside it can ever reach a turn |
| Binding | A **connection** binds to at most one identity (the one its hello presented); every session on that connection inherits it. Peer-local, so one client can never reach another's identity — the §11 isolation claim is unchanged |
| Consent | **Consent is configuration**: the operator added this agent, with this binary and this env, in their own client. Same argument §16.4 used for default-on, against the same baseline (`daemon.sock` is already always-on, unauthenticated and strictly more capable). First persist emits **one loud `Logger.info`** naming kind + npub + store path — *one*, not one per bridge, which is why the create path is the atomic link of the Concurrency row rather than an `exists?` check a 10-slot pool would all pass at once. The identity appears in `fermix doctor` from that moment, and stays visible even with the surface disabled (§17.3). No prompt: there is no operator at a terminal when a GUI-spawned harness connects, and a ceremony nobody can answer is a feature that never works (the M28 eval-home lesson) |
| Telemetry | **None new.** First persist, refresh-with-changes, and disconnect are structured `Logger` lines, matching §10's treatment of every other acp lifecycle event. A new event name would oblige a `fermix_opik` mapping (`docs/TELEMETRY_CONTRACT.md`) for three lines a year |

### 17.3 Lifecycle

| Event | Behavior |
|---|---|
| **First presentation** | `Peer.complete_handshake/3` (`peer.ex:254-264`) builds `Identity.new(env)`; if it has an id, `IdentityStore.upsert/1` writes it, `first_seen = last_seen = now`, one `Logger.info`. The Peer stores **the id**, not the record. A failed `upsert` is not survivable as an identity: named warning, record rebuilt identity-less, **before the connection's first turn** (§17.2) |
| **Re-presentation** | Same call. Upsert **replaces the record wholesale** (newest presentation wins field-by-field; no merging — merging would make a stale field a second source of truth), preserving `first_seen` and stamping `last_seen`. Rotation-safe in the only sense that matters: a re-issued auth tag, a moved `buzz` binary, a new relay URL all take effect on the next turn |
| **Key rotation** | A new keypair is a **new relay identity**, so it is a new record. The old one is not deleted (nothing revoked it *here*) and remains visible with its stale `last_seen` until the operator forgets it. Stated plainly rather than papered over with a heuristic |
| **Disconnect** | **Explicit operator action, one verb: `fermix acp forget <npub>` (`--all` to clear every record).** Deleting the record file **is** the sever — no second mechanism. Because every turn resolves from the store at message-build time (§17.1), the next turn on a bound connection misses, takes the named transition below, and advertises no harness tool. This is why the verb needs no control-socket method and no Peer scan: it runs in the tree-less CLI VM (the same constraint that pushed doctor liveness onto the control socket, §16.2 item 5) and could not reach a Peer if it wanted to. Ordering is `Plugins.Auth.logout`'s — store first, process follows on its own. Hazard to pin: bare `acp` **is** the bridge; `acp <word>` is management, and an *unknown* subcommand must exit non-zero with a named message and never silently become a bridge (a client misconfigured with `args: acp,--foo` must fail loud, not pump protocol) |
| **A bound record is unreadable at turn build** | Rev 2's read was infallible because it was RAM; this one can miss, so the branch is named rather than left silent. The connection drops to identity-less for its remaining life (§17.1) and the turn proceeds — the reply itself goes over the ACP wire and needs no credential, so refusing the prompt would break ordinary chat because a file vanished. What is lost is the model's own `buzz` posting and (from the next turn) the harness tools, both of which are the honest consequence of the record being gone. **Three kinds, three messages, never collapsed** (M28): *record missing* (`fermix acp forget`, or a home that was reset), *record quarantined* (`.broken.<ts>` — the JSON did not parse), *record refused for permissions* (the `chmod 600 <path>` line, `store.ex:97`, `:125-127`). Each names the npub and the store path |
| **Visibility** | The existing `Checks.acp/1` doctor row (`cli/doctor/checks.ex:483-534`) gains the identity list — count, kind, **npub only**, `last_seen` — read **straight off disk** (doctor is a tree-less VM; liveness still goes over the control socket, unchanged). Store-permission failures surface on the same row, the `auth_file_permissions` pattern. **The list renders regardless of `[fermix_channels.acp] enabled`** — one clause *ahead* of the `enabled` short-circuit that returns `ok("acp surface", "disabled")` before any probe (`checks.ex:484-490`). Identities are data, not a live surface, and turning the surface off is the most natural "disconnect" gesture an operator will reach for: if the row went dark there, N durable nsecs would sit on disk with nothing showing them, which is the one place the consent-by-configuration story would leak. Stated plainly on the row and in docs: **disabling ACP deletes nothing; `fermix acp forget [--all]` is the only deletion** |
| **Expiry** | **None.** No TTL, no idle sweep. A credential nobody revoked stays connected — the whole directive |
| **Relay rejects a persisted credential** | **v1: the model's `buzz` CLI errors loudly in-turn**, and Buzz's own machinery makes it visible (its turn-error path retries with backoff and dead-letters with an in-channel notice, §2.2 "errors"). Fermix does **not** probe the relay: a validity probe needs the relay client §17.7 deliberately does not build, and a probe that runs at hello would be stale by the time a turn ran anyway. Marking a record `stale` on a delivery failure is v2 — it requires observing a failure Fermix does not currently see (the model runs `buzz` through the shell tool; the exit status is the model's to read). Acceptable because the failure is loud at the only place it matters, and recovery is the same relay-side revocation + rotation M23 §11 already names |

### 17.4 What the store means for the ledger

One new `harness_runs` column, `client_origin_json`, **appended by its own `ALTER TABLE harness_runs ADD COLUMN client_origin_json TEXT;` migration following `continuation_depth`** — never inserted into the `CREATE TABLE` body beside `platform`/`destination`/`send_opts_json`. `repo.ex:465-469` states the rule for this exact table where `continuation_depth` was added: "Appended by ALTER so a migrated and a freshly created database share one column order (`SELECT *` is positional)". A mid-body column gives a fresh database a different column order than a migrated one — a silent positional-read corruption on the very rows the continuation depends on. Frozen at launch by `Harness.Delivery.resolve_snapshot/2` (`delivery.ex:68-82`) for a client-owned origin only:

```
{"identity": "<pubkey hex>", "cwd": "<session cwd>", "reply_context": "<bounded excerpt, ≤4 KiB>"}
```

- `identity` — derived at launch by the **same** `Identity.id_from_env/1` the Peer used at hello (one definition, so the two can never disagree). This is what lets a continuation find credentials for a run whose `destination` is a session id that no longer exists.
- `cwd` — the session cwd the launching turn ran under, so the continuation turn reproduces it (`request_cwd`, §4 "Workspace") instead of falling to `Mode.default_working_dir`.
- `reply_context` — a bounded, **opaque** excerpt of the launching user turn (the text carrying Buzz's `[Context]` block: channel id and reply anchor), read from `ConversationStore` under `ctx.conversation_key`. **Fermix never parses it** — it stores bytes and re-presents them inside `Continuation`'s existing untrusted frame (`continuation.ex:220`). This keeps §13's rejection intact on its own terms (no Fermix-side parser of a Buzz prompt format) while removing history-driven's one real failure mode: pre-flight auto-compaction (`turn_runner.ex:226-227`) can summarize a high-entropy uuid away in the minutes between launch and completion, and that is exactly the window this feature exists for.

### 17.5 Multiplicity, and Zed-class sessions

- **N Buzz agents → N identities**, keyed by pubkey; one daemon serving several agents is the already-supported topology (§15 open question 4), now with durable per-agent custody instead of per-connection.
- **A session binds to the identity its connection presented** — never to "the newest identity", never to a lookup by channel or by name.
- **A client that presents no identity persists nothing and behaves exactly as today.** Precisely, of the §4 allowlist:
  - **Identity keys** (persisted when an identity exists): `BUZZ_PRIVATE_KEY`, `NOSTR_PRIVATE_KEY`, `BUZZ_RELAY_URL`, `BUZZ_AUTH_TAG`, `BUZZ_ACP_DISPLAY_NAME`, `GIT_TERMINAL_PROMPT`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, and `PATH` — `PATH` is an identity field because it is what makes `buzz` resolvable, and a continuation with no live session has no other source for it (a launchd-started daemon's own `PATH` is bare, so this is not an optimization: without it the continuation cannot post at all).
  - **Ambient** (never persisted): the same allowlist filtered from a hello with **no derivable identity**, **minus `BUZZ_PRIVATE_KEY` and `NOSTR_PRIVATE_KEY`**, which `Identity.new/1` drops in that case by rule (§17.2, "Identity-capable is one fact") — not "in practice", by construction, which is what keeps the advertise gate and the store from disagreeing. So: `PATH`, the non-secret `BUZZ_*` descriptors and any `GIT_*` the client set. Held on the `%Identity{id: nil}` the Peer built at hello, dropped with the connection, exactly rev 2's behavior. A Zed session is bit-for-bit unchanged: same env, same cwd, no store record touched, no harness tools (§17.6). A Buzz agent whose nsec is malformed lands here too, and its `buzz` CLI fails loudly at the relay with no key — the loud outcome, not a run that works for minutes and cannot report.

- **One identity presented from two places with different metadata is out of contract, and the store does not referee it.** Upsert replaces the whole record when material fields change, so the *same* pubkey presented concurrently with two different `relay_url`s (or two different harness `PATH`s) would leave last-writer-wins on the record and route continuations by whichever connection spoke last. This cannot arise from Buzz's own topology — it generates a fresh keypair per agent and runs one harness per (pubkey, relay) pair, and a pool of bridges for one agent presents byte-identical env (an unchanged re-presentation writes nothing, so there is no flap) — it takes an operator hand-reusing one nsec across two agents or two relays. Stated as a uniqueness assumption: **one key, one home**; if it is ever violated the observable is the record's `relay_url` changing on reconnects, visible in doctor. Refereeing it (keying records by pubkey + relay digest) is a data change the file-per-identity layout absorbs without migration, deliberately not built for a topology no supported client produces.
- **A future client kind is data, not a second store.** Records self-describe (`kind`, `version`), so a non-Buzz credential kind added later costs exactly its own allowlist keys, id-derivation rule, and posting predicate (the M27 `runtime.kind` shape: a new kind as data plus per-kind gates, never a parallel code path) — and its records prefix their filenames with the kind (`<kind>-<id>.json`) so the bare `<pubkey hex>.json` namespace stays Buzz's. No change to layout, custody, lifecycle, or the one-source rule.

### 17.6 Harness re-enablement

**(a) The gate becomes "identity-capable session", not "not acp".** `HarnessSupport.advertisable_channel?/1` (`harness_support.ex:92-95`, `@client_owned_channels` at `:82`) is renamed to what it now decides — `harness_deliverable?/1`, "can a run launched here report back?" — and for a client-owned channel answers `FermixCore.Acp.Identity.posting_capable?(context[:session_env])`: true iff the env carries a non-empty `BUZZ_PRIVATE_KEY` and a `PATH`. Both modules are `fermix_core` (§17.2 "Placement"), so this is an ordinary in-app call.

The cheap sniff is **only** legitimate because §17.2's drop rule makes it equivalent to asking the store: a record carries a key iff it has an id, `Identity.to_env/1` is the *only* producer of such a map (§17.1), and a failed `upsert` downgrades the connection before its first turn. Without that rule this would be a second definition of "identity-capable" — one answering from the env's contents, one from a derived id — and they would disagree on exactly the input that costs the most: a present-but-malformed nsec, where the gate says yes, a vendor CLI runs for minutes, and the continuation then finds no identity.

**(b) The one-list property from §16.1 item 1 is preserved, and it is the whole difficulty.** The two cached profile variants stay exactly as built (`runtime_context.ex:101-104`, `:120-128`) and selection stays a per-turn boolean (`profile_for/4`, `:180-186`, `Map.fetch!`, fail-loud) — no third variant. What must change is that **both consumers of the predicate are fed one identical input**. Today `TurnRunner.profile_for_trust/4` passes a synthetic one-key map (`turn_runner.ex:1087-1090`) while each tool's `advertise?/1` receives the full turn context; the moment the predicate reads anything beyond `:channel`, those diverge and the prompt offers a harness section whose tools are not on the wire (the M28 drift class §16.1 was written to cure). Pin:

1. `session_env` is computed **once**, before `profile_for_trust/4` (it is at `turn_runner.ex:235`, the selection at `:215`; both derive from `msg`, so this is a move, not a new source).
2. The predicate input is `%{channel: msg.channel, session_env: session_env}` at both call sites, and the turn context already carries `:session_env` (`turn_runner.ex:270`) so `advertise?/1` needs no change at all.
3. The invariant test is feature-shaped, enumerated from the seeder (§17.9, Stage 4).

**(c) Continuation: the refusal, the env, the destination, the wire.**

| Break | Fix |
|---|---|
| `ContinuationDispatcher.owner_id/1` refuses acp at `continuation_dispatcher.ex:111` — `channel_key("acp")` is `:acp` (non-nil), so control reaches `configured_owner/2` and `[fermix_channels.acp]` has no `owner_user_id` (nor can it: `ConfigStore.normalize_acp/1` accepts only `:enabled`, §16.2) | The precondition's purpose is "re-ingest as the owner, never escalate trust" — but `Authorizer.resolve/1` consults `ChannelRegistry.trust/1` **first** and acp is `:local_operator` (`channel_registry.ex:92-101`, `:158-165`), so the stamped `metadata[:user_id]` is never read here. `owner_id/1` gains a `trust(platform) == :local_operator` arm alongside the existing `local?/1` one: "needs no sender id" is a property of transport **trust**, not of `remote?: false`. (§4 "Detached work" cites `continuation_dispatcher.ex:101` — that is the `local?` branch acp never reaches; the refusal is line **111**.) |
| The synthesized `Message` carries no `session_env` and no `request_cwd` (`continuation_dispatcher.ex:124-135`) — the continuation turn's shell would get the daemon's bare `PATH`, no `BUZZ_*`, and `redact_values` off (`turn_runner.ex:372-381` derives the telemetry scrub *from* `session_env`, so identity restored by any other path silently unscrubs the turn nobody is watching) | `build_message/4` sets both from the run row's `client_origin_json`: `session_env` from `Identity.to_env(IdentityStore.fetch(id))`, `request_cwd: cwd`. **This is the single injection point**, and it lives in `fermix_channels` (which may depend on `fermix_core`; the reverse is forbidden — the reason the dispatcher is injected by module at all). Core's turn path is untouched: `TurnRunner.session_env_for/2` keeps reading `msg.session_env` and nothing else (`turn_runner.ex:369-370`). A store lookup in `TurnRunner` would be the second source Rule 12 forbids |
| Identity gone (operator forgot it, or the run predates the store) | The dispatcher refuses with a **named** reason before ingest — the run must not proceed into a turn that cannot post. Distinct from "unknown channel" and "no owner"; the M28 lesson on collapsing failure kinds applies. **The name has to survive into the ledger, not only the log**: `Manager.log_continuation_failed/2` writes a `Logger.warning` and nothing else (`manager.ex:1053-1060`), while `last_delivery_error` (`memory/repo.ex:446`) is filled by the *later* worker attempt — so without (d)'s change `list_coding_runs` would report a forgotten credential as `{:unsupported_delivery_platform, "acp"}`, and the operator would conclude ACP delivery was never implemented when the real cause is a record they removed, which a reconnect re-presents and restores |
| Destination (Buzz channel + reply anchor) | `Continuation.notice_text/2` re-presents `reply_context` inside the existing untrusted frame, and the closing line for a client-owned origin **names the posting obligation** — `@closing`/`@failed_closing` (`continuation.ex:42`, `:59`) say "report the outcome", which on this surface means the ACP wire, which nobody reads. History still carries the same context for the usual case; the excerpt is what makes it survive compaction (§17.4) |
| Every reply/stream/activity closure hits `Acp.notify/2`'s no-fence clause (`acp.ex:152-158`) — a `Logger.error` **per stream delta** | `build_message/4` stamps `metadata[Acp.turn_opt()] = :detached`; `notify/2` gains one clause for that sentinel returning `{:error, :detached_turn}` at `Logger.debug`, the same quiet shape as the existing `:peer_gone` clause (`acp.ex:141-147`). **`nil` keeps meaning bug.** `Acp.build_raw_stream_callback/1` and `build_activity_callback/1` return `nil` for a detached message; `build_stream_spec/3` (`gateway.ex:96-102`) omits the spec when the raw callback is nil (one clause — today it wraps unconditionally), and `maybe_put_callback` already omits a nil activity callback. **`build_turn_result/1` still fires**, exactly once, so the terminal-signal invariant is uniform across turn kinds |

**(d) The delivery guarantee, stated honestly — and every branch that is not a continuation.** There is **no text fallback on this surface**: `jobs.delivery_channels` has no `"acp"` entry (`config/config.exs:117-124`) and `Acp.send_message/3` cannot send without a turn fence, so adding one would be a second path that cannot work (Rule 12) — do not. When dispatch succeeds, `Manager.hand_off_outcome/3` marks the run `delivered` the moment the turn was **queued**, not the moment anything was posted. The guarantee this surface offers is exactly: *the agent got a turn carrying the outcome and the credentials to post it.* No at-least-once posting is claimed; what an operator can check is `list_coding_runs` (status) and the trace (whether a shell `buzz` call happened).

Dispatch failure is not the only way an outcome misses the continuation. `Continuation.continuable?/1` is `chat_origin? and depth < 3 and result_terminal?` (`continuation.ex:71-73`, `:298-300`), and everything it rejects goes to `Manager.hand_off_outcome/3`'s other arm — `deliver_and_mark` → `Delivery.deliver` in `origin` mode → `ChannelSend` → `{:unsupported_delivery_platform, "acp"}` (`delivery/channel_send.ex:186`) → dead-letter. Stage 4 re-advertises **every** harness tool, including `cancel_coding_run` and `stop_tracking_coding_run`, so this design creates each of these cases rather than inheriting them. Four branches, four positions:

1. **Dispatch failed** (identity gone per (c), agent unavailable, ingest error) — terminal here, not `pending`. `pending` would be a lie: the worker has no acp path and can only re-fail with the platform term, so leaving the row for it is retry theater that also *overwrites* the real reason.
2. **Cancelled** (`cancel_coding_run`, or an owner halt from another conversation) — **defensible, and stated so rather than left implicit.** The model cancelled it from inside a live turn, where it can still speak; the tool result is the notification. A cancel issued from another conversation reaches the operator who issued it, and the acp side is silent by design — `result_terminal?/1` exists precisely so "continue the request this run was for" cannot relaunch work someone just killed.
3. **`tracking_stopped`** — same shape as 2, same position.
4. **A depth-capped chain** — **not defensible by that argument** (nobody is in a live turn), and it is the outcome an operator most wants: the last run of a 3-deep chain. It still does **not** get a push. A "one last delivery turn" would make the cap bound nothing on this surface — that turn can launch another run, whose outcome would again need a terminal turn, an unbounded ladder of one-more-turn (§17.8). What the operator gets instead is honesty: the row carries `:depth_capped` by name, `list_coding_runs` shows it, and the next live turn can read it. `Continuation.note/1`'s wording ("its outcome was delivered as a message instead of continuing the work") is **false on this surface** and must not be reused verbatim here. Mitigating fact, not an excuse: the chain already delivered in-channel turns at depths 1–3, so what is lost is the fourth outcome after four auto-chained runs with no operator input.

**In all four, the reason is written onto the row where the operator reads it.** `Manager.log_continuation_failed/2` writes only a `Logger.warning` today (`manager.ex:1053-1060`) and `last_delivery_error` is otherwise filled by the later worker attempt (`memory/repo.ex:446`) — so for a client-owned origin the Manager marks the row `dead_letter` with the **named** reason (`:identity_forgotten` / `:owner_halt` / `:tracking_stopped` / `:depth_capped` / the dispatch error) instead of handing it to a text path that cannot exist. `{:unsupported_delivery_platform, "acp"}` never becomes an operator-facing diagnosis on this surface: it is true and useless, it collapses four causes into one word, and one of them the operator fixes by reconnecting the client (M28's twice-written lesson; the vendor-words pitfall).

**(e) The §9 origin-mode `schedule_job` refusal stays** — with a corrected reason. It is currently refused because "the session is owned by the client and ends with it" (`jobs/delivery_defaults.ex:16`, `:53-62`), which durable custody falsifies. The refusal survives on a different and sharper ground: a job's delivery is a **framework send** into `delivery_channels`, and there is no acp wire to send into (see (d)); the model-posted path exists only *inside a turn*, which is what a harness continuation is and a job delivery is not. Reword the message to say that; keep the refusal. §16.3's ungated `update_job` is unaffected and still open.

**(f) §7's timeout note is corrected, not deleted.** Delegation does not fight Buzz's 900 s idle clock: `HarnessRun` returns the run id immediately with no wait window, `Manager.start_run/2` is a bounded `GenServer.call` that replies before the vendor CLI is spawned, the tool result explicitly ends the turn, and the launch itself emits a `tool_call` that resets the clock. The completion arrives later as a *new* turn with its own clock. The constraint §7 states applies to long **foreground** tools, not to delegation.

### 17.7 Honest costs

**What is on disk now that was not.** One 0700 directory, `$FERMIX_HOME/acp_identities/`, holding one 0600 record per connected Buzz agent: the agent's nsec, `NOSTR_PRIVATE_KEY`, its git-over-relay credentials, its relay URL, its harness `PATH`, and two timestamps. Plus one bounded excerpt of channel text per harness run in `client_origin_json`.

**Threat delta vs RAM-only.** Rev 2's exposure was "a memory dump of a live daemon, while connected". Rev 3's is "a readable copy of those records, whether or not anything is connected". Both are same-user exposures on a host that already stores the operator's provider refresh tokens in `auth.json` at the same 0600 and (on macOS) their keychain items with `-A`, i.e. readable by any process running as them (M23 §11 documents that trade for this very key). The blast radius of a stolen store is **every Buzz agent identity the operator has connected**, and — as M23 §11 says of the same key class — an nsec is a *transferable org identity*, not a revocable token: **recovery is relay-side revocation (remove the member / ban) plus keypair rotation**, not a Fermix action. The compensating fact is that all of this material is **Buzz-owned and Buzz-revocable**, unlike the operator's own provider keys, which the §4 allowlist still keeps out of session state entirely.

**Why this is peer-parity, not a new posture.** Under Buzz, claude and codex hold durable credential stores that outlive sessions and survive restarts; that is why they can answer at all after a respawn. Rev 2 gave Fermix strictly *less* durable custody than its peers and paid for it with a missing capability. Rev 3 matches them and keeps the two things Fermix does better: the arriving env is allowlist-filtered before anything is stored, and the secret values are scrubbed at the telemetry export choke point (§8.3, §16.1 item 3) — which now reads from the identity record instead of the connection.

**Deliberately not built.** No Nostr relay client, no event model, no signing (only bech32 decode/encode + one `:crypto` point multiplication, used to *name* a record and print an npub). No validity probe and no auto-invalidation. No merge with M23's `[fermix_channels.buzz]` identity, and no path by which one store can be read as the other. No keyring for these records. No per-identity trust or policy knob — trust on this surface remains `:local_operator` by transport (§11), and a third tier is still rejected (§13).

### 17.8 Rejected alternatives (rev 3)

- **Keep RAM-only custody.** The status quo, and it is what the live test broke on. It costs harness delegation from Buzz outright (a run cannot report back), forgets credentials nothing revoked on every restart, and is out of step with every comparable credential in the daemon *and* with the peer agents on the same harness. Its only advantage — nothing on disk — is measured against a daemon that already persists provider refresh tokens beside it.
- **Persist a `buzz`-binary directory only, not `PATH`.** Narrower blast radius, but it discards the rest of the harness `PATH` that a `buzz`-adjacent helper or a git credential helper needs, and it requires Fermix to *resolve* `buzz` at persistence time — a new probe with its own failure mode, whose staleness nothing detects. Persisting `PATH` verbatim makes the continuation turn **identical** to the live turn rather than a second, differently-constructed environment; it is validated by failing loud at use.
- **Require re-presentation each connect (session-scoped, but rebuilt).** This is RAM-only with extra steps: a continuation fires minutes later with no connection at all, so there is nothing to re-present *to*. It also cannot survive a daemon restart, which is the second half of the reported problem.
- **Parse Buzz's `[Context]` in Fermix code** to extract channel id and reply anchor. This is §13's rejected coupling one layer down — a Fermix-side parser of a prompt format Buzz can change silently, now in the harness tool instead of a delivery module. §17.4 stores an opaque excerpt and re-presents it; the **model** reads it, exactly as it did on the launching turn.
- **Key the record by a digest of the presented secret.** Same upsert semantics, no crypto — but it hands the operator an opaque blob they cannot match to an agent in Buzz's UI, and makes M23 §11's "print the npub only" rule inexpressible.
- **Put the records in `auth.json`.** Free reuse of perms/atomicity/backup/listing, at the price of four existing readers learning a record kind with no token and no expiry (§17.2). A sibling store with the same disciplines is the smaller change.
- **One shared `acp_identities.json` behind a singleton writer** — the literal `Auth.Store`/TokenManager shape (`auth/store.ex:9-12`). It is the house pattern, and it is wrong here twice: the writers are N `Acp.Peer` processes rather than one GenServer, and the reader/deleter (`fermix acp forget`, doctor) runs in a **different VM**, which no in-process serializer can reach. Serializing writers would then need a lock file or a control-socket method — new machinery whose only job is to protect a shared-file layout nothing required. One file per identity makes a whole-file write the record, so the lost-update class does not exist to be protected against (§17.2, "Concurrency").
- **Deliver a depth-capped chain's last outcome as one final continuation turn** (carrying `Continuation.note/1`). Tempting because it is the only mechanism this surface has, and it destroys the cap: the terminal turn can launch another run, whose outcome again has no non-turn path, so "one last turn" recurs without bound. The cap's whole purpose is to stop automatic follow-up; a surface-specific exemption is not a smaller cap, it is none. Named `:depth_capped` on the row instead (§17.6(d) branch 4).
- **A `[fermix_channels.acp]` `owner_user_id` setting** to satisfy the continuation precondition. It would be config for a value that is never read on this channel (trust is settled by transport before any sender lookup) — a knob whose only function is to unblock a gate that should not be asking.

### 17.10 Two pending decisions this design does not subsume

**Both were decided and built alongside it — §16.5 items 1 and 2 (2026-08-02).** They stayed separate decisions for the reason stated below, and the sections are kept as written because they are why each one exists.

**The effect gate for retry / duplicate posting remains required.** A `buzz messages send` is an irreversible external effect, and nothing in this design dedupes one. The continuation depth cap (`continuation.ex:71-73`, depth < 3) bounds *recursion*, not repetition: a model that posts, is continued again, and posts again produces two messages in the channel, and a re-dispatched continuation after a restart produces another. §17.6(d) does not touch this: it removes the *text* worker's retry on this surface (there was never an acp path for it), and the duplicate risk lives entirely on the succeeding path — a continuation turn that runs twice. This design makes that strictly more likely by creating the surface at all — harness continuations into Buzz did not previously exist — so the gate is more necessary after it, not less. It is a separate decision because it belongs to the effect layer (what has already been done), while everything here belongs to the identity layer (who is allowed to do it); wiring one into the other would put an effect ledger inside a credential store.

**The Codex empty-continuation gate remains required.** A run that terminalizes with no harvested text produces a notice whose body is empty, and the model is then asked to "continue the request this run was for" with nothing to act on — it will confabulate an outcome or re-run the work. Durable credentials change *where the continuation can post*, never *whether the vendor produced anything to post*; the gate is a property of the run's result, upstream of delivery, and it fires identically on telegram today. Folding it in here would couple a vendor-output check to an ACP credential design and hide it from the channels where it already misfires.
