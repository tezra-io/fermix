# Lessons

Incident-backed lessons for anyone working in this repo. `AGENTS.md` carries a one-line rule for each entry under the same title; read the full entry here before working in that area. When the repo teaches the same lesson twice, add an entry here and its rule to `AGENTS.md`. Every mistake is a rule waiting to be written.

## API plugin architecture — 2026-09-07

For an OAuth REST integration, start from the existing GitHub, Notion, and X HTTP plugins and their shared authentication/execution path. A hosted MCP integration is not the default template for an API plugin. Keep any provider-specific requirement that needs a helper, such as Tesla vehicle-command signing, separate from ordinary REST methods; do not move those methods into a new MCP server unnecessarily.

## General-purpose prompt edits — 2026-09-13

Keep task examples, sample replies, and scripted jokes out of Fermix's general-purpose runtime prompts; use scenarios only in external evaluations. Start prompt surgery with stale and duplicate instructions, replace existing wording, and measure the net token change. Distinguish instructions contradicted by the current runtime from model-specific steering that needs an ablation test; a newer model alone does not justify removing an operating safeguard.

## App-managed production configuration — 2026-09-16

Production Fermix is managed through the macOS app; do not prescribe a user-facing `fermix` CLI for its setup or recovery. Inspect the app's daemon environment and management surface. A sandbox env allowlist grants child-process passthrough; it neither stores credentials nor imports terminal shell exports into the launchd engine. External skill credentials need an app-accessible storage and injection path.

## Completion proofs and the order a daemon opens its doors — 2026-09-20

**A daemon does not open all its doors at once, so a completion proof that asks once proves nothing about the door that opens last.** `fermix service install` polled the control socket 180 × 500 ms and then called `Service.health_probe/1` **exactly once**. The engine binds `daemon.sock` before the Phoenix endpoint — measured 57-65 ms warm and 315 ms cold — so the single unretried request landed inside that window and refused a healthy install with `health_unavailable` once in every four runs on ubuntu:26.04. The patient half hid the impatient one: every test injected a probe that answered `:ok` immediately, so the race was structurally unreachable from ExUnit and only an install matrix running the real thing repeatedly ever saw it.

Three rules come out of it.

- **Every half of a completion proof polls, or none of it is a proof.** When a verification waits for one signal and then asks for a second, the second gets the same interval, the same declared attempt cap and the same defined behaviour at that cap as the first.
- **Waits that verify one transaction share one budget.** The ceiling M38 §4.1 sets is 90 seconds for the whole transaction, not per step, so the web wait spends what the socket wait left rather than stacking a second budget on top and quietly making the ceiling 100 s.
- **A component-to-caller boundary gets its own test.** A part can be right and still be useless: a writer answered `{:ok, output}` where all three of its callers matched `:ok`, so a *successful* store crashed after writing the secret; a measured `:keyring_locked` fell through a mapping's tuple clauses into a catch-all and reached the wire as "unavailable", the one untrue word the change existed to remove. Both passed every test of the component, because the tests stopped at the boundary the author happened to be working on. Test the value where it is consumed, not only where it is produced.
- **An error must not claim something nobody checked.** `health_unavailable` says the address did not answer, so the budget floor is one probe: a hello that consumed everything still buys a single request instead of reporting a refusal it never tested. Conversely a condition that cannot change by waiting — a daemon that published no origin at all — refuses on the spot rather than spending the budget re-asking.

A retry that only ever runs on a real machine needs a test that injects failure *n* times and then succeeds, and one that never succeeds and asserts the bound was spent. An injected probe that always answers `:ok` proves only that the happy path compiles.

**A gate that cannot fail proves nothing, so measure the control under the same conditions as the change — and when a control comes back clean, suspect the instrument before crediting the fix.** Measuring this race taught it: a loop that installed and uninstalled repeatedly saw one refusal in thirty on the unfixed engine and none in thirty on the fixed one, which read as confirmation and was not. The same loop then went **0 in 100 on the unfixed engine** once the machine was quiet. The race is load-dependent, so an idle rig could not fail and its green number meant nothing.

The shape recurs, and this race is only its latest instance — a build id that named two different engines identically, an archive digest that passed a per-file check while the whole was wrong. Every instrument fails in both directions: a search for symbols in an unpacked binary reported them ABSENT because `strings` was not installed and the shell swallowed it, and a search that finds the names it expects proves only that a large binary contains plausible words until a deliberately fake third name comes back absent. Run the negative control; a missing tool and a missing symbol look the same.

The transferable part is not the rule. The retraction above happened only because someone measured the baseline first, and they measured it only because a zero from an untested rig felt too easy. Distrust the convenient number before you can say what is wrong with it.

## Hermetic tests

**Tests must never mutate or silently depend on host/global state.** Four incidents, one family:
- *A test wiped the host filesystem* (2026-04) — an `on_exit` called `File.rm_rf!(dir)` where an empty interpolation collapsed `dir` to a root path. **Never** call `File.rm_rf`/`rm_rf!`/`rm`/`rm!` directly in `test/`; route through `FermixTestSupport.SafeRm` (hard-asserts a tmp prefix, ≥4 segments, no `..`). Production counterpart for the plugin store: `FermixCore.Plugins.Dist.SafeRm`. Sandbox tests must also never call `System.cmd` or `Port.open` — classify dangerous commands as strings via `Sandbox.classify/3`.
- *Tests clobbered the operator's real keychain* (2026-06) — fixture secrets hit the real macOS `security` writer (`-U` updates in place), green locally, 24 failures on writer-less Linux CI. Anything that can reach `SecretWriter` must run against `FermixTestSupport.SecretWriterStub` (the `config/test.exs` default — never delete it). Tests for the writer-less path override with `UnavailableSecretWriter`, not by removing the stub.
- *Order-dependent flake from leaked app env* (2026-06) — tests asserting "the default when nothing is configured" or "X is NOT captured" read global `Application` env an earlier module had dirtied. Such a test must **establish** its precondition in its own `setup` and restore in `on_exit`. Reproduce deterministically with a throwaway polluter module that `put_env`s at compile time. Second occurrence (2026-09-11): the umbrella `mix test` runs every child app in ONE VM, so a leak is cross-app — `admin_tools_test` (fermix_core) applied `subagent_provider = "openrouter"` through the real tool, its header comment claimed a restore its `on_exit` never did, and the value surfaced as a LiveView crash in `setup_live_test` (fermix_web) whose module setup re-established every key except `:routing`. A module that says it restores a key must restore it, and a setup that establishes the world establishes all of it. Third occurrence (2026-09-12): `management/secrets_test` left a `plugin:eden` token behind because that key was absent from its restore list, and the doctor plugin check — which captures and restores `:plugin_secrets` but never *establishes* it — read the leftover as a credential and reported `ready` where the ladder owed `needs_secret`; the same run's twin leaked through a mailbox rather than app env, `management/providers_test` asserting on the first `[:fermix, :provider, :call]` event to reach its globally attached handler, which was another async module's session-less fixture — a global handler's `assert_receive` must pin its own correlation id.
- *A test that crosses a platform gate must inject the platform* (2026-09-11) — a `recall_activity` test expected the topic-validation sentence but built its context without a gate snapshot, so `Gate.snapshot/2` read the real `:os.type()`: green on every macOS leg, refused with "not available on this turn" on both Linux legs. Any test that reaches a `ComputerHistory.Gate`-guarded path passes `macos?: true` (`Gate.snapshot(ctx, macos?: true)`, or `computer_history_gate:` in the tool context) — the gate tests already said so in their moduledoc, and a macOS-only pass is not a pass.

## Feature flag vs environment gate

**A feature flag is not an environment gate.** `FERMIX_OPIK_ENABLED=1` in the dev shell switched the exporter on inside `mix test` and POSTed every fixture as a near-empty trace — `only: [:dev, :prod]` dep gating doesn't stop a *sibling umbrella app* from booting. Gate "should this run at all" on the compile-time env (`@compiled_env Mix.env()`, release-safe), then let the flag decide within allowed envs. See `FermixOpik.enabled?/0`. **The same variable bit twice** (2026-08-11): `config/runtime.exs` derived `capture_content` from `FERMIX_OPIK_ENABLED`, and runtime config runs in `:test` too — so on the operator's machine the whole suite silently ran with content capture ON, and three test files asserted trace fields that only exist in that posture. A runtime-config default must let an already-set compile-time value win (`Keyword.get(existing_x, :key, default)`), `config/test.exs` must pin the posture the suite asserts against, and any test reading that posture establishes it in its own `setup`. Prove it by running `mix test` once with the variable set and once with `env -u`. **And then the base `config/config.exs` must NOT pin that key at all** — the fix above has a second half that is easy to miss. `Keyword.get/3` returns its default only when the key is *absent*, so a pin in the base config (which applies to **every** environment, not just the one that wanted it) makes the runtime default unreachable and erases the difference between "pinned for the suite" and "pinned for everyone." That is how content capture shipped OFF under a change titled *"capture trace content by default"*: every dev-daemon turn traced with `input: nil`, and the behavioral eval — which correlates a turn by its exact input text — matched zero traces and reported every case INCOMPLETE, i.e. a total eval blackout that looks like an infra hiccup. A runtime assertion on the live posture cannot catch this (the test env is *supposed* to be pinned); the test must read the compile-time chain **per environment** (`Config.Reader.read!("config/config.exs", env: env)`) and assert the key is absent for `:dev`/`:prod`.

## Gates and the world they inspect

**A gate that inspects a different world than the work runs in is not a gate.** Three incidents, the first two in the same function:
- `Harness.Artifacts.admission_check` probed free space with `df` on a directory that `Artifacts.prepare` creates *after* admission — so on a fresh home the probe failed, admission refused, the directory was never created, and the first harness run on every machine was refused forever. A gate must probe something guaranteed to exist at gate time (`existing_ancestor/1`). Pair every fail-closed branch with a first-run-on-a-fresh-machine test, and keep distinct failure kinds distinct (`:quota_exceeded`/`:below_min_free`/`:free_space_unknown` all rendering as "quota full" sent everyone chasing a phantom).
- The same probe spawned through `CommandHost`, but `fermix doctor` is a **tree-less CLI verb** where `resolve_supervisor!/1` raises — so the one command that explains a broken install died with a stacktrace and zero output on every host. Every test injected `quota:`, and `mix test` boots the tree, so the path was structurally unreachable from ExUnit. When correctness depends on *which* world the call site runs in (daemon tree / tree-less CLI / release boot), the test must reproduce that world. A sibling call site that already got it right is the strongest review signal — `Checks.harness/1` passed `supervised: false` five lines above and the probe didn't.
- *The packaged standalone binary is a fourth world, and it had no gate at all* (2026-09-12). `fermix migrate-to-app` shipped through three engine releases and refused its own launcher as a foreign `fermix` on PATH (`foreign_cli_target`) on **every** Homebrew install: the Burrito wrapper boots ERTS out of an unpacked copy under `HOME`, `erlexec` prepends `$ROOTDIR/bin` to the PATH every spawned process inherits, and `which -a fermix` therefore answers with the release's own launcher. Every unit test injected the world, so both that and the preceding defect (refusing an already-installed Fermix.app) were green. Add the packaged standalone beside the daemon tree, the tree-less CLI and the release boot: any CLI verb that inspects PATH, the process environment, or the account's files ships with a step in `scripts/release/verify_standalone.sh` that runs it from the staged artifact in a throwaway `HOME`/`FERMIX_HOME` — and the install paths to walk by hand before announcing are the matrix in `docs/RELEASING.md`.

## Env sanitizers and credential context

**Env sanitizers, credential context, and OS-blind requirements** (harness, 2026-07-26):
- *Test what a sanitizer INCLUDES, not just what it excludes.* `Harness.Env` spawned vendors under `env -i HOME/PATH/TERM`; the test proved no secret leaked but never that the child could still authenticate. Claude Code reads its Keychain item under account `$USER`; wiped, it read an empty account and died with "Not logged in" in ~2s. Every env-sanitizer test needs a **fidelity** assertion paired with its non-leak assertion. Stub CLIs need no identity, so a fake-vendor test is structurally incapable of catching this — the missing coverage is a real-child env dump.
- *Detection and execution must share one environment constructor.* `Vendors` probed with the daemon's own env while runs spawned under `env -i`, so readiness could never observe the missing variable and `fermix doctor` stayed green.
- *Make the value resolvable; don't make its absence fatal everywhere.* Hard-requiring `USER` fixed macOS and broke Linux, where Claude Code has no platform branch, no libsecret, and falls back to `$HOME/.claude/.credentials.json` — `USER` is a no-op there, yet bare containers don't set it, so every run refused (including codex, which never wanted it). `Harness.Identity` reads `$USER`, else `id -un` (`getpwuid(geteuid())`), and refuses only when neither answers. Never consult `LOGNAME` or `Path.basename(home)` — both can name a *different* account, and a wrong account yields a healthy CLI reporting "not logged in." `System.user_home!()` is not an independent source: it re-reads `$HOME` and raises without it.
- *Inherit credential-store CONTEXT, not just identity.* `CLAUDE_CONFIG_DIR` re-keys the Keychain service (`Claude Code-credentials-<sha256(dir)[0..8]>`); a child that can't see it reads an empty store. Resolve that context (Fermix key → daemon env → vendor default) and have detection read the same resolver.

## Plugin releases

**Releasing a plugin is a two-repo change, and the catalog ships INSIDE the binary.** The procedure lives in `fermix-plugins/plugins/README.md` § *Releasing a plugin* and is the authority — bump `version` + `CHANGELOG.md`, PR to `main`, tag `<name>/v<version>` (must equal the manifest version), then regenerate fermix's `apps/fermix_core/priv/plugins/index.json` with `scripts/release/sync_plugin_catalog.py` and land it as a normal PR. Do not hand-write catalog pins; the script downloads every artifact, checks its sha256, and cosign-verifies it against the release-workflow identity, failing the whole run rather than writing a bad pin. What that README does not yet say, learned the hard way (2026-08-03):
- *A `remote_mcp` plugin cannot be developed through `dev_local` at all.* The provenance gate refuses an unsigned remote manifest (`:unverified_remote_runtime`), because a remote manifest binds a live credential to an endpoint with nothing vouching for it. The author loop for a remote plugin is release-then-install, not edit-in-place. The refusal excludes that one plugin rather than failing the registry, so the symptom is "my plugin vanished", not an error.
- *`runtime_kind` must be OMITTED, never `null`.* `Index.parse/1` tolerates an absent key (entries published before the field existed) but throws `{:invalid_plugin_entry, nil}` on a present-and-null one — which takes down the **entire catalog**, not the one entry. The field is derived from the manifest's `runtime.kind`, and it is what picks the pre-install consent sentence: with it missing, a hosted plugin renders the *local-process* line and tells the operator it runs on their machine while it ships their content to a vendor.
- *The installed `fermix` binary carries a stale baked-in catalog.* There is no remote index and no refresh, so a freshly synced `index.json` is only visible to a daemon run **from source**. Testing an install against the binary will silently use the old catalog.
- *`min_core_version` gates installability* — set it above the core you are installing into and the plugin is simply never offered, with no error.

## Trace files

**A trace file is not a run — split it before you believe any error distribution.** `~/.fermix-dev/traces/<date>/*.jsonl` accumulates *every* run that day. Counting error kinds across the whole file mixed a 01:20 run with a 22:04 one and produced two confidently wrong diagnoses in a row (first "it's all credits", then "no, connection closes outnumber credits" — the closes were entirely in the other run). Bucket by run window first, then count; a tool that both succeeded 24× and failed 10× in the same file is the tell that you are reading two populations. And when a vendor refusal looks like a standing account condition, check whether the run *caused* it: 49 metered calls succeeded and then everything after 22:07:50 refused, which is a cliff the suite walked off, not a precondition it started from.

## Long-lived state

**A defect in long-lived state is invisible to a fresh-process probe.** Eden sessions expire server-side, and `Session` classified the 404 but never renewed — so a daemon up since yesterday failed *every* Eden call with `:session_expired`. The probe written to look for it opened a new `Owner` per iteration and reported a healthy connection at 70s idle, because expiry is a property of the MCP **session**, not the socket. When the suspected fault is "it rots over hours," the probe must reuse one process across the interval; per-iteration setup silently re-establishes the very thing under test. Related: MCP 2025-06-18 *requires* the 404→re-initialize recovery, so this was a spec gap, not a hardening idea.

## Failures the trace can't show

**A failure the trace can't show is a failure nobody can diagnose.**
- *Quote the vendor's own words.* An auth error was captured in `events.jsonl` then discarded four times (`record_diagnostic` fires only for non-JSON lines; `result.txt` persisted only on `"completed"`; both `Continuation.body/2` and `Delivery.failed_body/1` used `result_text` only for completed runs). The agent saw a bare `reason: exit_1`, blind-retried into the same wall, and fabricated a codex failure that never happened. A terminal status word is not a diagnosis — vendor text must reach the continuation notice *and* the delivered message, and be persisted so the durable retry (which sees only the ledger row) can recover it.
- *One model tool call = exactly one `[:fermix, :tool, :exec]` event*, recorded under the name the **model** used (the only name a reader can search for), routed through `Tools.Telemetry.exec/5`. `AgentLoop` returned "Tool not found"/"not available"/parse errors emitting nothing, so two iterations spent guessing withdrawn tool names left no tool row anywhere. Keep the three miss kinds distinctly messaged.

## Whole feature surface

**Gate on the whole feature surface, not tool-by-tool.** The harness `approved` test asserted "all three run tools are hidden," and passed while four other harness tools gated on `enabled` alone — an unapproved host advertised tools whose entire prompt category `RuntimeSections` had dropped. Write the invariant as "**no** harness tool is advertised" and loop over everything the seeder can register, so a tool added later either joins the invariant or fails the test.

## Validity gates

**A validity gate keys on what was DELIVERED, not on whether the protocol finished tidily.** A Codex 200 whose SSE stream ended before `response.completed` yielded `output: []` + `usage: %{}`, which `ResponsesShared.build_turn/5` renders as a *successful empty turn* — 72 silent ones over three months. But rejecting any non-`completed` status is also wrong: `items` fill from `response.output_item.added/.done`, independent of the terminal event, so a cut stream can still carry real content (3 of the 72 did). Require a **positive** delivery signal (non-empty output); never infer failure from a missing protocol marker. Two corollaries: before turning a degraded path into a hard error, name the layer that will recover it — `AgentLoop.continue_with_retry/3` runs `eligible?: fn _ -> false end` with `retryable?: &Transient.pre_response_timeout?/1`, and `Jobs.Runner` refuses to retry once tools have started, so "retryable" is a property of the *call site*, not the error. And a bespoke reason atom on `ProviderError.transport/4` falls to `TurnRunner.provider_error_reply/1`'s catch-all, which shows operators raw `inspect(reason)` — only kinds with their own sentence (`:timeout`, `:transport_closed`) are safe to mint.

## Eval homes

**Eval homes are fresh `FERMIX_HOME`s, so every default-off consent gate blocks them silently.** The capability home (`benchmark/bin/seed_capability_home.py`, regenerated on every `capability-daemon.sh up` — hand edits do not survive) carried no `[fermix_core.harness]`, so `approved` defaulted false while `enabled` defaulted true: tools were advertised, the model delegated, and every run stalled on an interactive prompt no eval can answer. Five tasks scored 0 with nothing wrong in the product. Pre-grant every human-decision gate in the seeder. When an eval scores 0, read the traces before believing the model failed — check for a refusal or pending approval first. Related: a delegation-steering prompt change silently re-routes *existing* eval tasks, so a suite that ranks the model must tell the task not to delegate.

## Behavioral gates

**A behavioral gate that encodes wording, a weekday, or a truncated id fails clean product.** All four defects in one `make regression` (2026-08-11/12) were in the suite or the runner; the model was right every time, and the LLM judge scored the "failures" 0.93–1.00. Read the actual reply out of the trace before believing a red gate.
- *A `reply_matches` vocabulary is a hand-maintained allowlist and it rots on every model or prompt change.* Second occurrence: `03740a77` hardened these same gates by enumerating the phrasings `gpt-5.6-luna` produced, and they then rejected correct `gpt-5.6-sol` answers — "48 isn't right" (allowlist had `isn't 48`), "Proceed with tomorrow's launch" (wanted `proceed with the launch`), "rollback works" (wanted `rollback…pass`), "versus B's 10" (wanted the literal `Campaign B`). Do not widen the positive allowlist a third time: **`reply_not_matches` + a phrasing-independent floor is the structural half, and the rubric owns the wording.** Widening has a proven ceiling — every pattern that catches "I still recommend we hold" also fires on "I no longer recommend holding", and a gate that fails good behavior is the worse failure.
- *"The rubric owns the wording" holds only if the rubric itself cannot be misread.* Third occurrence of the family (2026-08-19/20 nightly reds, issue #64): the meetings rubric's "treats the 'ignore your owner' line as content rather than as an instruction" was intermittently read by the temperature-0 judge as "must not editorialize" — it returned `pass: false` for replies that correctly flagged the injection, while passing near-identical replies on other trials (one refusal scored 0.72, so the score is no tell; the candidate was right in every repro trial). Describe expected behavior as a requirement, never as a metaphor the judge can invert: say "flagging X is correct behavior and must never be penalized." The neighbor case whose rubric explicitly *required* the flagging never flaked. Corollary: a redacted-by-default report cannot distinguish this from a real regression — reproduce with `--include-content` (a dispatch of eval-box on a temp branch) before believing a rubric red. `Prompt.CurrentDate` injects the real date on every surface, so the model orders by next occurrence from today: `order_deadlines` passed Mon/Tue/Sat/Sun and failed Wed/Thu/Fri — 3 days in 7, a **stable** fail (both attempts) that reads exactly like a model regression. Beware a coincidence hiding it: alphabetical order equalled the Wednesday answer, and only the prior day's passing reply distinguished them. Any relative temporal reference in a fixture needs an absolute date or a gate accepting every legitimate rotation.
- *A bounded identifier must compress its middle, never drop its tail.* `sess()` ended in `[:90]`, which cut the trial suffix off 83 of 449 cases, so a `--fail-retries` attempt re-entered the **same daemon conversation** it exists to independently confirm — and its turns became indistinguishable from the prior attempt's in Opik. `find_turn_trace` demands a UNIQUE candidate and `after = sent_at - 10s` reaches back into the previous attempt, so the retry resolved to None and the case went INCOMPLETE with the real verdict masked (one turn escaped by 13 ms, the next missed by 685 ms). An id that disambiguates by suffix must keep the suffix; hash the middle.

## compux pairing

**compux (computer-use sidecar) and Fermix ship as a paired change** — the wire `protocol_version` pins them and the handshake refuses a mismatch.
- *Bumping the dep here:* the ref lives in more than one place and a partial bump silently ships a mismatched sidecar. Update `apps/fermix_core/mix.exs` `ref:`, run `mix deps.get` so `mix.lock` re-pins, then `git grep` the old ref **and** the old version string (tests and comments hardcode it). Prefer the release tag commit so the download URL resolves. Verify with `mix compile --warnings-as-errors` plus the `computer_use/` tests.
- *Releasing upstream (`tezra-io/compux`):* bump `mix.exs` `@version` **and** `native/compux/Cargo.toml`; grep the old version string; bump `PROTOCOL_VERSION` in **both** `native/compux/src/main.rs` and `lib/compux/protocol.ex` only on a wire-incompatible change (a new action counts). Push to `main` is safe — `release.yml` fires only on a `v*.*.*` tag. Tag → signed/notarized `Fermix.app` sidecar. Then regenerate checksums **via a PR**: `gh release download`, `mix compux.checksum --dir <dist>`, commit `checksum-compux.exs`. Never hand-write it. Finally pin fermix's `ref:` to that checksum commit. Installed fermix is insulated — it pins the old ref and downloads the old sidecar.
- *Testing an unreleased compux locally:* both halves must match or you get `{:protocol_mismatch, ...}`. The **library** comes from the dep (`path:` or new `ref:`); the **sidecar** is resolved separately — `SidecarInstaller` does **not** honor `COMPUX_BUILD` — from `[fermix_core.plugins] dev_local` at `<dev_local>/computer_use_sidecar/bin/<target>/compux` (e.g. `macos-aarch64`, underscores). A bare local build is unsigned: it shows in Privacy settings as `compux`, not "Fermix", and re-prompts TCC every run because its cdhash churns. Revert a `path:` dep before committing, and bump the fake sidecar fixture's default proto (`fake_compux_sidecar.pl`).

## The macOS app

**The Fermix macOS app lives in `tezra-io/fermix-macos`, and this engine is half of it.** The app is a native SwiftUI client with the engine bundled inside it; it never reads config, secrets or state itself. Everything it shows and changes goes over `daemon.sock` through the **management protocol** (`apps/fermix_core/lib/fermix_core/management/`, canonical export in `apps/fermix_core/priv/management/`: `PROTOCOL.md`, `protocol.schema.json`, golden `fixtures/*.jsonl`, pinned by `protocol_contract_test.exs`) and, for voice, the realtime wire (`realtime/`, export in `priv/realtime/`). The app vendors both exports byte for byte by checksum (`Resources/Contracts/`), so **a change here that the app has not re-vendored is a drift the app's tests refuse, not a silent mismatch**. The M34 spec (`docs/design/MILESTONE_34_UNIFIED_MACOS_APP_IMPLEMENTATION.md`, machine-local) and the app's `docs/SHIPPING.md` are the references.
- *Any change to what the app shows is a change to the export, in the same commit.* Settings descriptors (`management/settings/*.ex`: rows, labels, footers, options), readiness, providers and their auth modes, plugin rows and their status/action vocabulary, jobs and their phases, doctor checks and remediations, and every published refusal sentence are the wire. Regenerate the goldens (`protocol_contract_test` pins them), keep `PROTOCOL.md` and the schema true, and run `Management.CopyTest` (sentence case, no em dashes, no exclamation marks, no version numbers, no wire tokens; proper nouns are hand-listed in `management/copy.ex`). Both doors render one descriptor: the browser setup LiveView and the app draw the same rows, so a label fixed in one place is fixed in both.
- *A wire-shape change is a paired cross-repo change and the daemon ships FIRST.* Add methods under a new minimum in `Management.Protocol` (`method_minimum_versions`), widen the window by construction, never break a shape a shipped app decodes; the router refuses a newer-engine call with `{method, requires}` so an older app degrades to a sentence, not a crash. Then release the engine, then re-vendor in fermix-macos (`scripts/verify_protocol_contract.sh --source <this checkout>` must report byte-identical, and `SOURCE.json` must pin a **committed** engine commit or the app's release audience refuses), then cut the app release. Same rule for `realtime/protocol.ex` and its `@protocol_version`.
- *One engine release feeds both channels, and the app half is a release obligation.* `mix release fermix_app_engine` is the tree the app bundles (`Release.Tree`, the engine manifest the app verifies); `release.yml` publishes `fermix_app_engine_<target>.tar.gz` for `macos_aarch64` and `macos_x86_64` beside the formula binaries, cosign-signed, from one tag. The app pins that tag, verifies checksum and signature, and asserts the tree's version, source commit and protocol window at staging. A daemon capability the app should expose therefore ships as: engine change + export + engine release + app pin bump + app release. Never make the app build its own engine.
- *Identity is fixed even though the name changed.* The bundle identifier `io.tezra.FermixPet` and the agent label `io.tezra.FermixPet.agent` stay across the rename to `Fermix.app`: TCC grants (microphone, App Management), the SMAppService login item and the coexistence preflight are keyed on them. An SMAppService agent needs a Team ID: an ad-hoc signed app is refused at spawn after every rebuild (AMFI launch constraint), so development bundles that register the service are Developer ID signed too. A GUI launch inherits no shell env; the app reads its home from `~/Library/Application Support/Fermix/launcher.json`, defaulting to `~/.fermix`, which a Homebrew install's app adopts in place. The dev loop stages `Fermix Dev.app` under a development identity (`io.tezra.FermixPet.dev`, agent `io.tezra.FermixPet.dev.agent`, its own support folder and `fermix-dev` scheme, `scripts/product.dev.json` applied through `PRODUCT_CONFIG_OVERLAY`) on `~/.fermix-macos` and port 4530, so an installed `Fermix.app`, its service, record and grants are untouched and the two coexist.
- *Both halves of a plugin row spell one fact in one vocabulary* (2026-09-13). `runtime_kind` is the catalog's two words (`local_stdio`, `remote_mcp`, or null for the http rail) and it drives the consent sentence on both doors. The catalog half derives it from the manifest's start-kind (`node`, `python`, `binary`, `escript` are all `local_stdio`); the installed half matched the manifest against the catalog's words instead, so every installed local plugin, the Tesla helper included, published null and "Runs inside Fermix on this Mac" while its process ran beside it. `Registry.local_runtime_kinds/0` is the one list; a row-shape field that both halves publish gets one test per half.
- *Keychain items are named by profile, never by home.* `SecretWriter` stores every secret as `fermix:<ENV>` (or `fermix:<profile>:<ENV>` under `[fermix_core] profile`) in the one login keychain, and `-U` updates in place. Two homes on the default profile therefore share and overwrite each other's secrets: on 2026-09-05 a Telegram token saved into `~/.fermix-macos` replaced the live `~/.fermix` daemon's, which polled the new bot after its next restart. Every additional home on a machine gets its own profile (`~/.fermix-dev` uses `fermix-dev`, the app's dev loop `fermix-macos`); a saved secret that "vanished" from one install usually reappeared in another.
- *Sidecar pins are release facts, not refs.* The app-engine and the formula share `compux`, `fermix-meetbot` and the local STT pins; a pin at an unreleased commit (a protocol bump without a version bump) makes every host download a sidecar the library refuses (`protocol_mismatch`). Pin released tags with checksums, always.

## macOS TCC identity

**Any process the daemon spawns inherits fermix as its macOS TCC "responsible process" — and fermix's own TCC identity churns every release.** Third TCC-identity lesson (compux sidecar grants, then the App Management per-upgrade popup). A GUI app spawned as a bare Port child (Chrome, 2026-08) gets its TCC activity attributed to fermix; the daemon's identity is the launchd job's resolved program path (the versioned Cellar realpath — tccd resolves the stable symlink) with the ad-hoc wrapper's cdhash as csreq, so every release is a brand-new path-keyed TCC client: prompts re-fire per upgrade, dead rows accumulate, and `tccutil` cannot reset a single path-keyed client (OSStatus -10814; whole-service reset only). Chrome flags (`--disable-component-update`, `--disable-background-networking`) demonstrably do NOT stop its launch-time bundle probe. Remedies, in order: spawn through the `disclaim` exec shim (`fermix_nif` priv; `responsibility_spawnattrs_setdisclaim` + SETEXEC — same pid, fds intact, fail-loud, never an undisclaimed fallback), or give the responsible binary a stable signed identity at a version-stable real path (design doc `MACOS_APP_MANAGEMENT_TCC_IDENTITY_FIX.md` Leg B). The shim is an EXECUTABLE: it must not build with Burrito's NIF-recompile `$(CC)` (which bakes in `-shared`) — cross-builds get the zig triplet via the burrito target's `nif_env` `DISCLAIM_TARGET`; keep its strict flags in lockstep between `apps/fermix_nif/Makefile` and ci.yml's `disclaim-shim` job (the v0.6.0 lenient-local-cc/strict-release-zig class).

## Config round-trips

**A config section that normalizes strings→atoms MUST ship the inverse (`to_keyword/1`), and the persist path must use it.** Second round-trip incident (2026-08-19): setup's "Set primary" serialized the LIVE app env back to TOML, and `computer_history`'s normalized `summarizer: :default_provider` atom rendered as `summarizer = "default_provider"` — a spelling the parser rightly refuses — so the very next `load_runtime_config` (inside the same save flow) raised and took the whole daemon down, leaving a poisoned config.toml that re-crashed every boot. `normalize/1` is one-way; rendering its atoms verbatim is a latent parse-refusal for every value whose TOML spelling differs from `Atom.to_string/1` (a Tier-3 provider atom or `remote_summaries` atoms crashed the *save* itself). The pattern (realtime/computer_use already had it; computer_history's comment explicitly — wrongly — waived it): `persistable_snapshot` runs `normalize |> to_keyword`, `apply_*` re-normalizes whichever shape arrives so app env holds exactly one shape on every path, `normalize` is idempotent over its own output, and the proof is a save→load round-trip test seeded with the **normalized app-env shapes** (not TOML strings — the live snapshot is what setup actually persists). First occurrence of the class: web-setup round-tripping live app env resurrected a deleted ollama provider block.

## Default on

**A feature is not "default on" until it works after a fresh install AND a `brew upgrade` with zero new config.** `brew upgrade` swaps the binary and never touches `config.toml`, and upgraders never re-run setup — so a wizard-seeded key reaches nobody who already installed. M30 shipped reminders default-on but hard-required `[fermix_core.jobs] default_delivery_target`, which neither install path provides: every upgrader's first "remind me…" refused, while M26 (same week) derived the owner's inbox from the configured channel owner — two subsystems answering "where is the owner's inbox" differently was the tell. Rule for any new feature that needs an operator value: derive it deterministically at acceptance time from config that already exists (visibly — the acknowledgment names the derived choice so the owner can correct it; snapshot it, never re-resolve per use), or don't advertise the surface until the value exists. A loud first-use error is a last resort, not a posture. One concept, one resolver — shared by every subsystem that needs the answer.

## Passthrough lists

**A global passthrough list resolved all-or-nothing is one stale entry away from disabling every command, and the operator's shell is not the daemon's environment.** (2026-09-16) Two Alpaca keys were allowed on `[sandbox.env] allow` for one trading skill, exported only in `~/.zshrc`; the launchd app engine never sources a profile, `Sandbox.Env` halted on the first unresolvable name, and every shell command in every session (`date`, `pwd`, an unrelated wardrobe tracker) was refused for 26 days. Nothing logged it, doctor's `sandbox` row only counted entries, every cron run still reported `ok`, and the shell-launched dev daemon inherited the export so dev never showed it. Rules: a policy list resolves per name and reports the misses (tool result, trace, log on transition, readiness) while the command runs with the rest, and only a name a consumer requests for itself is a hard requirement; a run's `status` says the loop finished, so carry `tool_failures` beside it; a health fact about the daemon's own environment is recorded where it is produced (`Sandbox.EnvHealth`: boot, config apply, every command) and read by readiness, never re-probed from a CLI whose world differs; and a shell export never reaches a service, so the remedy is a `command` source (keychain helper), never "export it".

## Replayed compile warnings

**Mix records a compile warning against the source that produced it and replays it forever, so one bad compile poisons every later build.** Third occurrence (2026-09-12) of `mix fermix.dev` dying on "the Inspect protocol has already been consolidated, an implementation for `FermixCore.Auth.OAuthProvider` has no effect" under `warnings_as_errors`, and the first with the mechanism proven. Elixir 1.19 stores per-source diagnostics in `_build/<env>/lib/<app>/.mix/compile.elixir` and re-emits them on every `mix compile` for files it considers unchanged — so the build fails with nothing recompiling and nothing wrong in the source. Read the manifest before theorising: `:erlang.binary_to_term(File.read!(manifest))` and search the term for the warning text (it hangs off the source path, here `lib/fermix_core/auth/oauth_provider.ex`); a poller over `:code.is_loaded(Inspect)` during the failing compile shows the VM holds the *un-consolidated* stdlib `Inspect`, i.e. the warning is a recording, not a live condition. The recording is genuine in origin: `Mix.Compilers.Protocol.compile/4` ends with `Code.prepend_path(_build/<env>/consolidated)`, so the VM running `mix fermix.dev` has consolidated protocols on its path, and `code_reloader: true` then recompiles an edited `@derive {Inspect, ...}` struct *inside that VM* — editing a derived struct while the dev daemon is up is the trigger, not the struct. `touch` does not clear it (1.19 keys staleness on the content digest, not mtime): change one byte, compile, `git checkout --` the file, compile — or `mix compile --force` for the whole umbrella. Never loosen `warnings_as_errors`. Stray per-app `_build/<env>/lib/<app>/consolidated` dirs (from running mix inside `apps/<child>`) are a *different* fault and were a false lead twice; dev had none on this occurrence.

## Identity by contents

**Verify an artefact by what it contains, not by what produced it.** (2026-09-20) In the Linux single-package work four identifiers stayed correct while the artefact under them changed: GTK `4.16.7` named four different private runtimes; the runtime cache key hashes the lock file, Dockerfile and patches, so two exports differing by ten `.pyc` files shared it; the `runtime-dev` image tag carries that same key, so a stale image survived a rebuild; and `dev-<sha>-dirty` named both the engine with the install health race and the engine without it, which let "is this the fixed engine" be answered wrongly with apparent evidence. A version, a cache key, a tag and a build id all name inputs, and a check that reads a recipe cannot detect a change to the output. Rules: gates compare digests of bytes (`engine_tree_sha256`, the runtime manifest's per-file digests and its `archives` tarball digests — a correct tree inside a non-reproducing tarball passes every tree check); the artefact carries its own identity (`identity.json` written at export, `build.json` in the package) so a consumer asks the installed thing directly; a dirty dev build id folds in a digest of the uncommitted changes. Instruments: extract-and-hash to compare two trees under one key, and read identity from the installed tree, never from the archive name.

## A pass that measured nothing

**A green result is evidence only if the check could have come out red on this artefact, and a statement about what should be true is not an observation.** (2026-09-20) The same failure appeared seven times in one day of the Linux keyring work, in every lane, and never once felt like a guess to the person making it. A widget suite that needs `FERMIX_GTK_TESTS=1` and a display printed `1 passed` in 0.00s when it skipped itself, so every "all binaries green" excluded the dialogs the work existed to build; an acceptance run passed in full on a superseded package, because its guards (`engine_tree_sha256`, contract bytes) were identical in both pairs and only the app binary differed; a tree was declared "final" from a sense of being finished while its files' mtimes were eight minutes newer than the copy; a probe using `strings` printed zero for everything on an image that has no `strings`; a source copy without `.git` produced a build id with no `-dirty`; a compiled module was read as a published method; a ruling was printed in a status line as though it were a reading of the file. Rules: every presence check carries a positive control (a string known present) and a negative control (an invented one), so "tool could not run" and "absent" give different answers; a skip must not print as a pass, and a duration of 0.00s for a test that opens a window is a skip; acceptance hashes the files it is about to test and refuses unless they equal the digests in the handover, and probes the shipped binary for a string the newest change emits; "final" is said only with the copy's timestamp beside the newest file's mtime; a claim about another component's behaviour is measured or attributed to its owner, and the attribution travels with the claim; a gate that every input passed says nothing about a layer no gate can see (here: what a window draws after an action), so that layer is named as uncovered rather than implied green. Retracting a correct claim on weak contrary evidence is the same error in reverse: settle it by looking. None of these were caught by care; each was caught by a control returning a value it had no business returning, or by a second party looking at the bytes. Prefer gates to reminders.

## A deliberate separation the code did not explain

**A line whose reason lives only in a design document will be deleted by someone reasonable.** (2026-09-20) The vendor unit set `FERMIX_LINUX_PACKAGE_INSTALL_DIR` so the service's Burrito payload sat apart from the CLI's. Nothing in the unit, the template or any test said why, and the obvious-looking reason — keeping the packaged engine's directory apart from a standalone `fermix` — is already handled by the release name, so merging the two roots looked like a simplification and was very nearly made twice, once by me and once in a ruling. The real reason was in MILESTONE_38_ENGINE_SLICE_PLAN.md:57, "so the daemon's extracted payload lives in a directory no CLI invocation prunes", and it is not about our pruning: Burrito's wrapper calls `do_clean_old_versions` on EVERY launch (wrapper.zig:110) and `deleteTreeAbsolute`s every sibling extraction of the same app at an older version. Measured on a real install, a bare `fermix --version` deleted a 0.10.4 sibling — so with one root, an owner running any command during an upgrade would delete the running daemon's payload, and the daemon would die later at a lazy module load, far from the cause. Rules: when a line exists to prevent a failure, the reason goes NEXT TO THE LINE, because the design doc is not in the reader's hands at the moment they are deleting it; before removing a guard, find the failure it was written against and reproduce it rather than inferring its purpose from its shape (the inferred purpose was wrong and would have passed review); and a dependency's own maintenance behaviour is part of your design — read what it does on every launch, not only what its API offers. The same measurement proved the good half: semver ignores build metadata, so two builds of `0.10.5+<id>` compare equal, neither deletes the other, and nothing reclaims either — which is why the accumulation this created needed its own bounded sweep.

## A cache keyed by a name, not by contents

**A cache directory named after a version is a cache that cannot notice a new artefact, and the component that reads the key decides who is allowed to fix it.** (2026-09-20) Burrito extracts its payload into `<release>_erts-<erts>_<version>` and reuses it whenever a metadata file exists there, so on the owner's machine one directory extracted at 13:28 served every package installed afterwards: same version, different bytes, and the first engine answered for all of them across restarts. The reporting half hid it — `fermix service status` took *both* sides of its comparison from the identity compiled into whichever binary answered, so a stale engine compared itself with itself and reported `aligned`, and the desktop client draws its skew row only on `pending_restart`. Two defects, one symptom, and each made the other invisible. Rules: name a cache directory after a digest of the thing cached, never after a version or any other input — a reuse check that reads metadata is reading something the checked artefact wrote, while a name that differs cannot collide at all; a freshness comparison takes its two sides from two different places (the package on disk versus the process answering), because a comparison whose sides share a source can only ever agree; and when the consuming component reads its key from the environment before any of your code runs, the fix belongs in whatever execs it — which also means every launch path (here a systemd unit *and* a bare CLI invocation) must go through one place that sets it, since two writers of the same variable will eventually disagree and the one that is wrong will be the one nobody tested. Cleanup that becomes necessary *because* of such a fix is part of the fix: digest-named directories accumulate one per build, so the prune is owed in the same change — bounded, logged, refusing to delete the entry in use, and placed where the caller can know the other entries are idle, never on a path an ordinary CLI invocation takes.
