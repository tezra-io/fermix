# Events & reminders

The temporal-event rail: a durable personal date plus a finite reminder plan that
reaches the owner through the configured default background channel. Nothing here
runs a model when a reminder fires.

## The boundary against `schedule_job`

`event_store` remembers a personal date and notifies the owner when it arrives — no model runs when it fires. That is the boundary against `schedule_job`: **deterministic dates whose only future action is notifying the owner** (birthdays, anniversaries, appointments, deadlines, follow-ups, a plain "remind me on Friday") are events; **future work that must reason, call a provider, use tools, inspect changing state, or produce a digest** is a scheduled job. Events are stored in `~/.fermix/memory.db` as their own rows, never as memory facts (the memory reviewer is allowed to archive a passed date, which would be wrong for a birthday) and never as job rows.

A connected calendar (e.g. the Google Calendar plugin) is a **separate source**, deliberately unsynced (external tokens expire; a stale mirror is worse than a named second source). A schedule/agenda question consults every available calendar surface — `event_list` plus any connected calendar tools — and answers with source attribution, saying so when a source was not consulted or was unreachable. Creating a calendar event does not make Fermix remind anyone, and before storing a date a connected calendar likely already tracks, ask whether the owner wants Fermix reminders for it too — two systems reminding twice is a surprise.

## Time input and recurrence

`when` is one tagged form — `{"type":"date"}`, `{"type":"datetime"}` (with `utc_offset` when a local time is ambiguous), `{"type":"relative","amount":2,"unit":"days"|"weeks"}`, or `{"type":"annual","month":9,"day":14}`. The tool owns the clock and the timezone: it reads `[fermix_core.personalization] timezone` unless the owner explicitly names an IANA zone, and a missing or invalid zone fails creation rather than assuming UTC. A nonexistent DST-gap local time is rejected and an ambiguous one needs `utc_offset` to pick an instant — ask the owner instead of guessing. Recurrence in v1 is **one-time or yearly** only; a yearly event stays one row with one id forever, its concrete reminders are materialized for the next two annual occurrences, and rollover uses local-calendar arithmetic (never +365 days). A yearly February 29 event needs an explicit `feb_28`/`mar_1` policy — ask once.

## Reminder plans and delivery

Reminder plans are finite, never a nag loop: birthday/anniversary defaults are 7-days-before and day-of at 9:00 local; timed appointments get 24-hours-before and 1-hour-before; date-only deadlines get 7-days, 1-day, and day-of; an explicit "remind me at X" creates exactly that one reminder. A custom plan replaces the defaults rather than appending, at most 10 rules per event, and lead rules already in the past are skipped (say so in the acknowledgement when nothing future remains). Delivery goes to the **configured default background channel** (`[fermix_core.jobs] default_delivery_target`, snapshotted onto the event when it is stored) — Telegram, Slack, Discord, Signal, or WhatsApp; `cli` is a valid jobs target but not a valid reminder target. With no target configured, Fermix **derives the owner's inbox** from the first channel carrying an explicit `owner_user_id` (Telegram, then Signal, then WhatsApp — the same ladder skill-curation proposals use), so a fresh install with one configured channel needs no second setup step; the stored result names which rung answered (`delivery.source` is `configured` or `derived`), so the acknowledgement can say a reminder will arrive through a derived inbox and the owner can correct it. Only an explicit owner id derives an inbox — channel presence alone never does — and with neither a configured target nor an owner-configured channel, `event_store` fails with setup guidance naming both remedies rather than falling back to the current chat. Changing the config later does not retarget existing events; `event_update(rebind_delivery_to_default: true)` does that explicitly. A failed send is retried **durably on the same target** (five bounded claims: due, +1m, +5m, +15m, +60m, honoring a server rate-limit hint, clamped by the reminder's validity) and then fails visibly — Fermix never fails over to another channel. When an earlier failing reminder is still pending as a later rule comes due, the earlier one is superseded so a recovery never bursts "one week before" and "today" together. Messages are rendered deterministically, always name the absolute date/time, and are one message under the smallest channel text limit.

## Managing stored events

A name is not an identity: two people can share an event title, and only the owner knows whether a restated date corrects the stored event or belongs to someone else. Three deterministic surfaces make that visible. A create that collides with an active event of the same identity on a different date **refuses**, and the refusal names the stored event and quotes its stored date, so the owner can be asked which it is instead of one date silently replacing the other. Every successful create carries `similar_events` — the owner's other active events of the same kind (id, title, next occurrence, at most five) — because a twin stored under a different title is the one duplicate the dedupe key cannot catch. Every successful `event_update` carries `previous`, the prior value of exactly the user-facing fields that edit changed, so an acknowledgement states was-and-now from stored values rather than from recollection. Changing a stored event's date is the one edit that destroys what it replaces, so it requires `owner_direction`: a near-verbatim excerpt of the owner's own words directing that change, bounded in length and never parsed for content, so the trace shows what the write was justified by and a reader can tell a real direction from a restatement. Without it the edit **refuses** and the refusal names the stored date, so the owner can be asked whether to overwrite it or keep both as separate events. Title, kind, timezone, plan, and delivery-rebind edits need no attestation.

`event_list` searches by text/kind/status/date window and reports the next occurrence, the plan, the next due reminder, and the last delivery state or error. With no window and no status it defaults to **upcoming from today**; pass a `from`/`to` window or an explicit `status` to see history. `event_update` patches title/time/recurrence/plan; `event_remove` soft-cancels (delivered history stays queryable) and takes an explicit `event_id` or none: with no id, "cancel that" / "stop reminding me about this" cancels the event behind the most recent reminder delivered into this exact conversation within the last 24 hours, resolved through the same outbox lookup "snooze that" uses, and its result carries the whole event — including its recurrence, so the reply can say a yearly event took every future occurrence with it. Both refuse with `delivery_in_progress` while a reminder of that event is mid-send — a channel send cannot be recalled, so retry once the bounded attempt finishes. `reminder_snooze` defers one reminder: "snooze that for two hours" resolves the most recent reminder delivered into this exact conversation within the last 24 hours (never guessing across chats or owners — if nothing matches, ask which event), or takes an explicit `reminder_id`. The new time is a bounded duration (minutes/hours/days, up to 90 days) or a DST-safe datetime in the owner's zone; a time at or past the event itself needs the owner's explicit confirmation (`confirm_past_boundary`). One active snooze per source — re-snoozing with a different time replaces it, a repeat of a still-live snooze is idempotent (re-snoozing to a time whose earlier snooze was cancelled or replaced arms that same reminder again), the delivered original stays in history, and a snooze never edits the event's stored plan. While an earlier snooze of that reminder is mid-send, `reminder_snooze` refuses for the same reason `event_update` does: a send cannot be recalled, so retry once the attempt finishes. A snooze landing after a one-time event completed reactivates the event just long enough to deliver, then it completes again. The four mutating tools are **attended-owner-only** — advertised and executable only on a top-level operator turn from an interactive or voice surface, so guest, scheduled, background, delegated, and coding-continuation runs cannot see or call them. `event_list` alone is also readable from an **operator-created scheduled run**, so a cron job (a morning brief, for example) can include stored events alongside any connected calendar it is instructed to consult; guest, background, delegated, and continuation runs still cannot read events. Lifecycle transitions emit `[:fermix, :reminder, :lifecycle]` (materialized, claimed, delivered, retry_scheduled, failed, expired, superseded, cancelled, event_completed, scheduler_error).
