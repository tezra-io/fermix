# Outbound presentation & live streaming

How a reply physically lands on a chat surface: per-channel rendering, the
boundary-ladder splitter, message hygiene, streaming modes, and the ephemeral
thought stream.

## Outbound presentation

Telegram: a long reply lands as a few section-shaped cards, not 4096-character walls. The model's Markdown is rendered to Telegram HTML and cut on a boundary ladder — a section heading first, then paragraph, line, sentence end, whitespace, and a hard cut only as a last resort — measured in the UTF-16 code units Telegram actually counts, with a per-message formatting-entity budget as a second, independent fill condition (dense links can blow the entity cap while sitting far under the length cap). A cut never lands inside a fenced code block and never strands a heading or a `:` lead-in at a message's tail. Chunks go out strictly in order: the first rings and every later one is silent, so one reply is one notification, and a failed send aborts the remainder instead of half-delivering. Link previews are disabled on every outbound text message, draft edit, and seal. A fenced code block too large to render inside a message is uploaded as a text document after the chunks, with a one-line caption, instead of being split into corrupt halves. If Telegram refuses the formatted message ("can't parse entities"), that one chunk is resent once as the raw Markdown with no parse mode — the reply is never lost, and the renderer defect is logged at error level and marked in channel-render telemetry. Discord, Slack, WhatsApp, and Signal ride the same boundary ladder: a reply over that platform's own message cap is delivered as sequential boundary-aware messages (each measured the way that platform counts, and a failed send aborts the rest) instead of erroring out over the cap. Each of those channels also has its own **dialect**, so the model writes one house style and never sees raw syntax leak: Discord reads Markdown natively and is passed through untouched; Slack gets mrkdwn (`*bold*`, `_italic_`, `~strike~`, `<url|label>` links, headings as one bold line, `•` bullets, code fences and blockquotes native, tables as a monospace fence); WhatsApp gets its own styles (`*bold*`, `_italic_`, `~strike~`, triple-backtick monospace, headings as one bold line, `•` bullets, links as "label: url" since WhatsApp auto-links bare URLs and has no link markup, quotes as plain `>`-prefixed lines, tables as a monospace fence); Signal gets clean plain text (every emphasis and code marker removed, links as "label: url", headings as a bare line with a blank line under it, `•` bullets, fenced code kept verbatim but indented, tables as indented aligned rows) because signal-cli transmits an unstyled body — real Signal style ranges are a later addition. Every dialect follows the same flanking discipline as the Telegram renderer, so `snake_case` identifiers, `2 * 3 * 4` arithmetic and bare URLs full of underscores are never mangled, and a link's URL always reaches the reader byte-for-byte. The boundary ladder walks the model's Markdown, where headings and section boundaries are still legible, while every candidate chunk is measured through that channel's renderer, so the fill condition counts what the reader actually receives. Replies are additionally *shaped* per channel by a presentation note injected into every chat turn — the five chat surfaces are told they are writing for a phone-width bubble stream (lead with the answer, short self-contained sections, no tables or horizontal rules, shallow headings, links inline on the claim, deep optional detail in a quote block, plus one line of channel-specific posture), while machine and terminal surfaces (`cli`, `acp`, scheduled runs) get no such note; a group chat adds one line about addressing the asker.

## Live streaming

On by default, per-channel capability: a configured channel that can edit drafts (Telegram today) defaults to `"draft"`, every other configured channel defaults to `"block"`, and an unconfigured channel stays `"off"` (`[fermix_channels.<name>] streaming = "off" | "draft" | "block"`). `"draft"` streams the reply into a live message edited in place (~1/s, ≥30 chars before the first bubble opens) that **rotates**: when the live text grows past one section card (~1,400 rendered units on Telegram) it is sealed at the best ladder boundary — section, then paragraph, then line, never mid-sentence and never inside a code fence — and the remainder keeps streaming into a fresh bubble, so a long answer lands as a few section-shaped cards instead of one frozen wall. Sealed cards are finished messages: a tool round seals the live bubble as commentary before the next round starts its own, `/stop` deletes only the unsealed live bubble, and at turn end the authoritative remainder is merged into the live bubble when it fits (a short tail never rings a second message) or handed to normal chunked delivery when it does not. If the final response is not an extension of what was sealed, the reply is delivered in full instead. Needs a draft-capable channel (`fermix doctor` warns when "draft" is set on one that cannot edit). `"block"` sends each completed model "thought" as its own ordinary message (semantic boundary = completed output item; 800–1200-char paragraph chunking only as the long-text fallback, 1 s idle flush) — works on every channel, and pre-tool commentary lands as its own message and persists as conversation. A completed item that overflows one message is cut on the same paragraph/line boundaries as any other block, never mid-word, and an unterminated code fence is sent whole rather than held back. The model's 💭 reasoning-summary headings are a separate, ephemeral progress stream that never survives the turn. On a draft-capable channel they roll into ONE 💭 status bubble edited in place (newest headings win; the oldest are trimmed with a leading "…" so it stays one short bubble), deleted when the answer is sealed or the turn is stopped. On a delete-capable channel without in-place edits, pending headings drain as a single silent 💭 message (one prefix, one heading per line) and every such message is deleted once the answer lands. Either way answer text takes the tick first (answer > rotation > status), so a thought never lands between a paragraph and its continuation, and the sweep is best-effort — logged, never retried, never able to fail the reply. A channel that cannot delete messages gets no thought stream at all rather than permanent 💭 residue. Both modes need a streaming provider (Codex today — others simply deliver normally). Only real channel turns stream — background/CLI/cron runs never do. Stream telemetry: `[:fermix, :channel, :stream]` with `phase` open/edit/block/rotate/seal/discard and the turn's `session_id`.
