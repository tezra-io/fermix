# Sandbox

The sandbox bounds what the file, image, search, git, attachment and shell tools reach. It does not limit plugins, web search, memory or provider calls, and it sets computer use's `access` (`strict` is look-only). On a Mac and on Linux the operating system holds every command to the mode as well (below): Seatbelt on a Mac, Landlock on Linux. A Linux kernel that cannot (no Landlock, or one older than Linux 5.19) runs no command at all, and says so.

## Modes and roots

| Mode | Roots |
|---|---|
| `strict` | the workspace (`~/.fermix/workspace`) + grants. Not the skills folder: a skill that uses its own files needs `/grant path ~/.fermix/skills`. |
| `standard` (default) | the workspace, `~/.fermix/skills`, grants, and, when strictly inside the OS home, the folder the daemon started in and the folder the request came from (where `fermix ask` ran, or an ACP session's working directory) |
| `open` | all of `$HOME`, minus protected paths |

- The request folder counts only on a trusted local operator turn; remote channels and guests get the workspace, the skills folder, the start folder and grants. A background service (the Mac app, launchd, systemd) starts in `/` or the home folder, so there only a `fermix ask` or ACP folder adds anything. The home folder itself is never a `standard` root.
- Roots live in `[sandbox]`: `workspace_root`, `allowed_roots` (grants), `blocked_roots` (wins inside a grant or mode root).

## Always refused

- **Protected paths**, in every mode and even inside a grant (file, search and git tools cannot open them; no shell command runs from inside one): `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.docker`, `~/.kube`, `~/.codex` (or its configured home), `~/.anthropic`, `~/.config/fermix` (a Linux service's env file), `~/.npmrc`, `~/.netrc`, `~/.git-credentials`, `~/.config/git/credentials`, gcloud's `credentials.db`, `access_tokens.db`, `legacy_credentials/` and `application_default_credentials.json` in `~/.config/gcloud` (the rest of `~/.config/gcloud` stays reachable), Claude Code's `~/.claude.json` and the `.credentials.json`/`.claude.json` in its config folder (the rest of `~/.claude` stays reachable); Fermix's `config.toml`, `auth.json`, `chatgpt_host.json` (the Sign in with ChatGPT install id), `secrets/`, `secret_key_base`, `setup-token`, `setup-launch-token.json`, `acp_identities/`, `mobile/` (the phone gateway's keys: `gateway_key`, `tls.key`, `iroh_key`), `device/` (a desktop's key and its link to the primary), `plugins/run/`, `browser/profiles/`, `bootstrap/`, `memory.db`, `grants/`, `logs/`, `traces/` and its sockets; an Always-On host's `/run/fermix` (its enrollment code); OS roots (`/etc`, `/usr`, `/bin`, `/sbin`, `/System`, `/Library`). Names match with a `.` or `-` suffix (`memory.db-wal`) and case-insensitively (`~/.SSH`). A grant for a protected path, the home folder, the Fermix home or `/` is refused as `unsafe_root`.
- **Catastrophic commands**, before any shell command runs: recursive delete of a protected root, `mkfs`, `dd of=/dev/…`, a fork bomb, mass kill, shutdown or reboot, `sudo -S`. A pattern check for common mistakes, not a complete boundary.

## What commands can reach (Mac and Linux)

Every `shell` command, operator command (`[sandbox.commands]`, the `dev_tools` presets) and `git_read`/`git_write` run, and every program it starts, runs inside a sandbox the kernel enforces, built from the mode: Seatbelt on a Mac, Landlock on Linux (through Fermix's `fermix_landlock` helper, which also stops setuid programs such as `sudo` from gaining privileges).

- **Writes** go only to the mode's roots and grants, plus the temp folders. In `open`, a command may write anywhere the account can except what is listed below, so `brew install` works there and not in `standard` or `strict`. Tool caches (`npm`, `pip`, `uv`, `go`, `yarn`, Playwright, `XDG_CACHE_HOME`) point into the workspace's `.cache`, never your own caches; `cargo`, SwiftPM and `xcodebuild` keep theirs in your home, so they need a grant or `open`.
- **Never, in any mode:** writing Fermix's home except its workspace and skills folders, or renaming it; writing the protected paths, Fermix's installed engine, `~/Library/LaunchAgents` or `~/Library/Application Support/Fermix` (on Linux `~/.config/systemd/user`, `~/.config/autostart` and the browser extension's host manifests); reading Fermix's secrets (a key being saved to the keyring included: it waits in `secrets/` while it is written), `auth.json`, the phone and desktop keys (`mobile/`, `device/`), browser profiles, `memory.db`, `logs/`, `traces/` or `/run/fermix` (`config.toml` stays readable); running a program under its `plugins/` folder directly; on a Mac, connecting to Fermix's sockets and mounting a disk image anywhere but `/Volumes`. Every path a command cannot read it cannot move or rename either.
- **Reads in `strict` and `standard`:** a command also cannot read your credential paths (the home-folder entries of the protected list: `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.docker`, `~/.kube`, `~/.npmrc`, gcloud's credentials and the rest), so `ssh`, `git push`/`pull` over SSH, signed commits, `aws` and `kubectl` work from a command only in `open`. `npm` still runs, but without your `~/.npmrc`: its registry, proxy and tokens are skipped without a warning. `gcloud` can read its login only in `open`, and even there it cannot save a refreshed token, so expect it to fail from a command. No command, in any mode, can write these files: `npm login`, `npm config set` for your user config, `gcloud auth login` and git's `store` helper saving a password are for you to run in your own terminal. Every other hidden file and folder (`~/.gitconfig`, `~/.config/git/config`, `~/.zshrc`, gh's `~/.config/gh`) stays readable.
- **On Linux, what Landlock cannot do.** It grants by folder, so: a command can list the names in a folder it cannot read, never their contents; it cannot create anything directly in a folder that holds a protected path (in `open`, the home folder and `/` themselves; a Fermix home kept inside a temp folder closes that temp folder the same way); the kernel does not refuse a connection to Fermix's sockets; and before Linux 6.2 a command can still truncate a protected file (doctor warns). A process outside the sandbox, the running daemon included (`/proc/<pid>/environ`), is out of a command's reach.
- A refused write or read is the program's own `Operation not permitted` (`Permission denied` on Linux). The fix is a grant (`/grant path PATH`) or `open`, never a different command. Because commands cannot write Fermix's files, and on a Mac cannot reach its sockets, `fermix sandbox`, `fermix grant`, `fermix setup`, `fermix settings`, `fermix status` or `fermix ask` run as a command fail or are treated as unattended: tell the owner what to run in their own terminal or the app. If the sandbox itself cannot start a command, the result says "could not start inside Fermix's sandbox"; on a Linux kernel without Landlock every command answers "This computer can't sandbox commands (Landlock is unavailable), so Fermix won't run them", and the fix is a newer kernel or Landlock switched on (in the kernel's `lsm=` list), never running the command another way.
- Not held yet: the `codex` and `claude_code` presets, coding runs (`codex_run`, `claude_code_run`) and plugin or MCP server processes. `codex` and `claude` run through `shell` fail, because their own state folders are protected.

## Commands after outside content

When Fermix cannot sandbox a command, it waits for the owner before running it in a turn that has already read content someone else could have written, exactly as an access-sensitive plugin command does (plugins reference): one confirmation in the owner's chat or app, or a spoken yes on a call, expiring in 60 s; the asking turn runs nothing else meanwhile, and Fermix then runs exactly that command, in the folder and sandbox the turn had. The owner's prompt shows the exact command, verbatim, with line breaks and invisible characters shown as escapes (a command too long to show is refused, not run). Outside content is the plugins reference's list, which includes a forwarded message, the message's own attachments (a voice note the owner recorded aside) and the Recent Activity note.
- **Which commands.** On every platform the `codex`/`claude_code` presets and the coding runs `codex_run`/`claude_code_run` (coding harness reference), which run outside the sandbox. `shell`, `git_write` and confined operator commands are held by the kernel on a Mac and on Linux with Landlock, so they do not wait; they wait only where the kernel cannot hold them (a Linux without Landlock, where they then refuse anyway).
- A turn that has read nothing from outside runs commands at once, as before; `git_read` never asks. A shared Buzz channel is not outside content for commands: a Buzz turn's `shell` (its `buzz` CLI replies included) waits only once that turn has read outside content.
- Delegated workers (`subagents`, `skill_run`, which also carry what their parent read), tasks a cue woke, `/background` and other unattended runs never run one after outside content. A scheduled job runs one then only when its `allowed_tools` names it, and a job with no `allowed_tools` (which would run every tool), or one that can start a skill (`skill_run` or a skill by name) or manage jobs (`schedule_job`, `update_job`, `run_job_now`, `resume_job`), cannot be set up, changed, resumed or run now from a turn that read outside content (on a Mac too while the coding runs are set up, since such a job could start one); name the tools the job needs instead, without skill or job tools. What a tainted turn writes for later (memory, a skill, a job's task) runs clean later within those rules.
- On a voice call such a command is refused rather than asked aloud, because the owner must see the exact command: they ask for it from their own chat or the Fermix app.

## Changing it

| Setting | Mac Settings > Sandbox | Browser setup, Sandbox tab | Chat | Terminal (Linux, dev) |
|---|---|---|---|---|
| Mode | **Sandbox** | **Mode** | `/sandbox mode MODE` | `fermix sandbox mode MODE` |
| Command profile | **Command profile** | **Command profile** | `/sandbox commands profile PROFILE` | `fermix sandbox commands profile PROFILE` |
| Presets | none | none | `/sandbox commands enable\|disable PRESET` | `fermix sandbox commands enable\|disable PRESET` |
| Folder grants | none | none | `/grant path PATH`, `/revoke path PATH` | `fermix grant\|revoke path PATH` |
| Allowed variables | **Allowed environment variables** | **Allowed env names** | `/sandbox env allow\|deny NAME` | `fermix sandbox env allow\|deny NAME` |

- Mac app and browser setup changes to mode and profile need a restart; variable changes apply to the next command. Chat changes apply at once (after `/confirm` where one is asked). A terminal edit reaches a running daemon only after a restart; on an app-managed home it also makes the app refuse saves until **Reload settings from disk**, so on a Mac use the app or chat.
- The Mac pane's one-line mode hints are approximate; the table above is what each mode reaches.
- Inspect: `/sandbox status|explain` in chat (the mode, each root marked `(granted)` or `(mode)`, the variable names); `fermix sandbox status|explain` in a terminal, whose `explain` adds the protected paths, whether this system holds commands (Seatbelt, or the Landlock ABI on Linux), and what a command cannot read in the current mode (an entry ending in `*` covers every file whose name begins with it).

## What needs `/confirm`

A change that adds a root, an allowed variable, a preset or a command asks for `/confirm TOKEN` first; one that only removes applies at once. Leaving `open` for `strict` or `standard` asks, because the new roots are named differently from `open`'s single `$HOME` root. `standard` to `strict` applies at once. `/sandbox commands profile` never asks, even when it switches on presets already listed.

## The directory-approval loop

- When a filesystem call is refused as outside the roots and the task genuinely needs that folder, the agent calls `request_directory_access`, only in an attended operator turn. Guests, scheduled jobs, sub-agents and unattended runs never get it, and it never asks for a path it would refuse (`$HOME` wholesale, the Fermix home, `~/.ssh`, OS roots).
- The owner sees the canonical path, the reason and the config diff, and answers `/confirm TOKEN` or `/deny TOKEN` (a visible refusal that discards the grant). Tokens are single-use, bound to that conversation, owner-only and expire in 60 s; a `/confirm` from a process Fermix started is refused. On Telegram and Discord the prompt also has **Approve**/**Deny** buttons that deliver the token privately, and a group chat's text leaves the token out (button mechanics: `channel_presentation` reference).
- On confirm the grant persists to `[sandbox] allowed_roots`. On a chat channel the original request resumes by itself; on the one-shot CLI the owner re-runs it.
- The same prompt also acknowledges a coding agent's config change and holds an access-sensitive plugin command or, where the kernel cannot hold commands, a command after outside content.

## Command profiles and presets

- Profiles: `bare` (default: no presets), `assistant` (presets you turn on are available), `extended` (same as `assistant`).
- Presets: `ai_tools` (`codex` with `OPENAI_API_KEY`, `claude_code` with `ANTHROPIC_API_KEY`) and `dev_tools` (`git`, `gh`, `make`). A preset command appears only when its executable is on the daemon's `PATH`, and every name it passes (`pass_env`) must be on the allowed list or the call fails.
- A single command: a `[sandbox.commands.<name>]` block (`command` required; `args`, `pass_env`, `timeout_ms` default 30000, `description`, `enabled` default true) or `fermix sandbox grant command NAME -- CMD [ARGS...]`; available under every profile, `bare` included. `fermix sandbox command list` lists them.

## Diagnosing

Every refusal is written to the day's `sandbox_event.jsonl` trace. Doctor's sandbox trace check (in the Mac app's **Doctor**, or the `sandbox traces` row of `fermix doctor`) reads the last 7 days and names each refused folder with the grant that would allow it. `outside_root` means approve or grant the folder; `protected_path` cannot be granted. `Operation not permitted` inside a command's own output on a Mac (`Permission denied` on Linux) is the operating system's sandbox, and is not in that trace. Doctor's `os sandbox` row says whether the kernel holds commands on this machine: Seatbelt able to apply a profile on a Mac; on Linux the Landlock ABI (a warning at ABI 2, which cannot stop a truncate) or, failing, the sentence every command gets and what the kernel needs (Linux 5.19 or later with Landlock enabled).
