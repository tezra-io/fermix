# Computer use (experimental, off by default)

Computer use is **experimental and off by default**, enabled from the setup Plugins page (the `computer_use_sidecar` card) on **Apple Silicon (M-series) macOS and Linux x86_64** — Intel Macs are not supported (install fails loud). Enabling downloads the native helper via the `compux` library (fetched from its GitHub release and verified against a baked sha256 — no cosign, no plugin-catalog tarball) and turns the feature on; the capability registers for the model **only once enabled AND `ready?`** holds (below). It is the most dangerous capability — the rest of this section is its operating model, not a casual toggle.

`computer_use` drives the host desktop GUI by screenshot + mouse/keyboard, one action per call (`screenshot` to see, then click/type/key/scroll/drag in screenshot pixel coordinates). It is host-desktop control only — there is no "browser mode" (web automation is the separate browser tool). **computer_use is the only capability that sees and drives the user's actual screen; the browser and shell tools operate in their own isolated contexts — so a task about the user's live screen or a session they have open must use computer_use (a browser/shell action lands in a different context and silently desyncs), but for an addressable target (a file path, a URL, a system fact) still prefer the purpose-built tool even if it is also on screen.** For a small or dense target the model zooms: a `screenshot` with a `region` {x,y,w,h} returns a magnified crop, and passing the SAME region on the follow-up click/drag maps the coordinates read in the crop back to the real pixel — clicks land far more accurately than raw full-screen pixels. Coordinate integrity is enforced, not just prompted: when a pointer action's x,y are plausible on BOTH live grids (inside the on-screen region box while the view is a magnified crop) the session refuses with a typed ambiguous-coordinates error that spells out the exact conversion, and the model re-sends with `confirm_grid: true` only after re-reading the crop; on a magnified view every cursor echo also carries its full-screen equivalent, so a wrong-grid click stops looking self-consistent. The images themselves carry grounding aids: every tool screenshot is drawn with edge rulers in its own pixel space (the answer grid is visible in the picture), a post-action check image marks the EXECUTED click point with a ring + its coordinate (so a miss is seen, not inferred), and a `screenshot` with `marks: true` badges the accessibility click targets with numbers — the model then acts with `mark: <id>` and the daemon resolves the exact point, no pixel estimation at all (marks expire when the view changes, and a stale or unknown mark is refused, never guessed). Element reads target the app that OWNS the window in view — resolved from the window list by stacking order and overlap with the requested region, never from the focused-application query (which is unreliable from the sidecar and, during a voice call, can name the floating voice companion instead of the app on screen). When that app's tree walks to zero elements, the sidecar makes one typed activation attempt (`AXManualAccessibility`, then `AXEnhancedUserInterface` on a typed rejection; cleared again on session end) and re-queries on a short bounded cadence — Chromium builds its tree lazily once an accessibility client starts asking — and every outcome is reported in the result (which app was read, what activation did, how long the tree took) instead of a silently empty list. Full-screen captures are sized by the looser of a long-edge and a pixel-area budget, so an ultrawide display arrives readable rather than as a thin strip. An intent the OS can name — launching an app (`open -a`), a menu item or settings toggle (AppleScript) — is a shell one-liner before it is ever a pixel click. Every mutating action returns a fresh check screenshot — of the same magnified crop when a region rode the action (verification happens in the space the model acted in), of the full screen otherwise — and the model reads it before repeating anything: the image shows what the screen looks like now, never whether the input arrived, so an action is repeated only when the image shows its effect is missing, and a pointer that ended up elsewhere is reported as aim not confirmed rather than as a click that did nothing (a person moving the mouse leaves the same trace). The receipts say exactly what is known: when the check itself cannot be captured the result reports the action performed and unverified rather than failed — reporting failure buys a second real click — and when the helper stops responding or exits during an action the result says the outcome is unknown and the session was reset, so the next step is a fresh screenshot rather than a blind re-send. `inspect` (read-only, macOS only) reports the accessibility element under a point — its role and label (e.g. a button titled "Delete") — so the model can confirm the right control before a consequential click; it informs the model's own judgment and is NOT a blocking gate. `elements` and `inspect` expose best-effort accessibility metadata (macOS only): an empty result does not prove visible content rejects pixel interaction. Only usable returned points replace the current coordinate source — bare points use full-screen coordinates, while regional points require the same region on follow-up coordinate actions; `wait_for_change` blocks until the screen changes and returns the new frame (instead of polling with repeated screenshots); `paste` enters long text via the clipboard (fast and unicode-safe); and key chords include `f1`–`f12`. It is the most dangerous capability — ambient authority over the live session, no rollback, screenshots are untrusted (treated as external content). It is **registered for the model when `ready?` holds: enabled AND the native sidecar binary installed** — a disabled or uninstalled daemon never advertises it. OS-permission state is a separate diagnostic, not part of `ready?`: `fermix doctor`'s `computer use` check probes the sidecar (non-prompting) and reports macOS Screen Recording and Accessibility distinctly (on Linux, X11 vs the unsupported Wayland). The classic failure is **Accessibility not granted, so synthetic clicks and keystrokes are silently dropped while screenshots still work** — a session probes that grant once at start and REFUSES mutating actions with a typed error naming the fix (read-only actions keep working), so the state is one loud refusal instead of a run of invisible no-ops; the fix the error and the check both name is System Settings → Privacy & Security → Accessibility. On macOS the setup Plugins page also offers a **Grant macOS permissions** button that raises the Screen Recording + Accessibility prompts up front and registers the helper with the OS, so it appears in System Settings as **Fermix** (with the app icon) and can be approved at enable time rather than only on the first screenshot. That single **Fermix** identity is deliberate: the sidecar runs as its own signed, notarized `.app` bundle (a stable identity the grant persists against across upgrades) so every macOS permission Fermix needs shows under one "Fermix" app — the same name the voice companion uses for its Microphone entry. If an upgrade leaves the check reporting a missing grant while the "Fermix" Screen Recording box still looks enabled, a stale grant from an older/pre-release build is shadowing the signed one — tell the user to remove the "Fermix" row under System Settings → Privacy & Security → Screen Recording (or run `tccutil reset ScreenCapture io.tezra.fermix.computer-use`) and grant again; first-time installs are unaffected. Read-only screenshots work without the Accessibility grant, which is why a missing permission informs rather than hides the tool. Within a turn the tool acquires a per-conversation session lazily (the OS-driver process opens on first use and is reused across actions). Safety is the **`access` posture, which is DERIVED 1:1 from `[sandbox] mode`** — there is no separate computer-use knob; an `open` sandbox is an `open` desktop. `strict` = look only (mutating actions refused — the one deterministic floor); `standard` = acts freely but the agent confirms conversationally before anything irreversible (its own judgment — it sees the screen — not a rule table or a blocking gate); `open` = acts autonomously but still pauses to confirm only a TRULY dangerous/catastrophic action (a higher bar than standard). Read-only actions always run. Host sessions additionally start only from an **attended origin** — an interactive chat or `fermix ask`, or the voice pet — and scheduled/cron runs fail closed (a host desktop must have a watching human); `access` governs *what* it does, origin governs *whether an unwatched run may start it at all*. Enabling is two coupled parts: installing the `computer_use_sidecar` helper (a native binary that ships no tools of its own) plus flipping `[fermix_core.computer_use] enabled`; both are needed, and the change applies on the next daemon restart. The OS driver runs as a separate process (not in the BEAM), spawned only while enabled; on session start the daemon performs a version handshake with the sidecar and **refuses to run one whose wire protocol is incompatible** with the running build (e.g. after a partial upgrade left an old binary), failing loud rather than misbehaving — reinstalling the `computer_use_sidecar` helper to match the daemon resolves it. Its `:gui_control` policy class is operator-only and **never delegated to subagents**, and carries no sandbox/path enforcement — all safety is the `access` posture (derived from the sandbox mode) + the attended-origin gate. **Coexistence (so the agent does not fight a present human for the one cursor):** because every action moves the real cursor and types into the focused window, a `courtesy` arbiter yields the seat when the human is actively using the machine — before a *disturbing* action (any click/drag/scroll/`mouse_move`/type/key/paste; note `mouse_move` counts even though it mutates nothing, because it warps the cursor) the daemon checks how long the human has been idle and, if they are active, briefly waits in-turn for them to pause, then either proceeds or holds the action back and tells the user it stepped aside. This never blocks read-only actions (screenshot/inspect/elements/wait) and is a courtesy, not a safety floor: the idle signal is macOS-only, and where it is unavailable the arbiter proceeds (falls back to the pre-coexistence behavior) rather than blocking. The human can also reclaim the machine explicitly with `/pause` (the session refuses actions — at classification and again at execution, so one classified a moment earlier cannot slip through — but stays alive and resumable) and hand it back with `/resume`; an action already handed to the helper cannot be recalled, so `/pause` says whether one is still finishing instead of promising the cursor back immediately, and `/pause`, `/resume` and teardown are answered while an action is under way rather than queueing behind it. **`/pause` reports what the helper confirmed, never what was sent:** it installs a barrier in the helper — which stops a sequence such as a drag part way through and releases what it was holding — and reports back that it is paused, that it is paused with one action still finishing, or, when the helper does not confirm the barrier, that the helper was shut down instead, since a machine that may still be driven must never be described as handed back. `/resume` lifts the barrier the same way. Ending a session gracefully — `/stop`, the end of a conversation, a reset after the helper answered — releases any held key or button before the helper is ended; a helper killed outright releases nothing, which is why the pause barrier rather than the kill is what stops a drag part way through. **The machine's cursor and keyboard are held by one conversation at a time:** a disturbing action from a second conversation is refused as busy with nothing sent (looking is never blocked — two conversations may read the same screen), and the hold lapses once its conversation has dispatched nothing for a minute, so a conversation that went quiet cannot keep the seat. Within one conversation there is one action at a time too: a second action sent while the first is still inside the helper is refused as busy rather than queued, so the answer is to wait, never to re-send. The helper reports on every mutating action whether the input was sent, half sent, or never sent, and that report — not a guess from what the check screenshot happened to show — is what the result's outcome says; a helper that does not report it at all is treated as a broken helper, the outcome is unknown, and the session takes a fresh one. That report rides on a refusal too, so a refused action says whether it refused before sending anything or part way through, rather than the refusal's name being read as proof nothing happened. Config: `[fermix_core.computer_use]` (`enabled`, display sizing, `max_actions` — the per-session action budget that halts a runaway; `courtesy` = `yield` (default) or `off`, and `courtesy_idle_ms` = how much human-quiet counts as idle) — note `access` is NOT a key here (it mirrors `[sandbox] mode`), and there is no `mode` key: computer use is host-only.
