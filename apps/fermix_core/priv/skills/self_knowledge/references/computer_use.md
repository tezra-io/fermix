# Computer use (experimental, off by default)

Computer use is **experimental and off by default**, enabled from the setup Plugins page (the `computer_use_sidecar` card) on **Apple Silicon (M-series) macOS and Linux x86_64** — Intel Macs are not supported (install fails loud). Enabling downloads the native helper via the `compux` library (fetched from its GitHub release and verified against a baked sha256 — no cosign, no plugin-catalog tarball) and turns the feature on; the capability registers for the model **only once enabled AND `ready?`** holds (below). It is the most dangerous capability — the rest of this section is its operating model, not a casual toggle.

`computer_use` drives the host desktop GUI by screenshot + mouse/keyboard, one action per call (`screenshot` to see, then click/type/key/scroll/drag in that image's pixel coordinates). It is host-desktop control only — there is no "browser mode" (web automation is the separate browser tool). **computer_use is the only capability that sees and drives the user's actual screen; the browser and shell tools operate in their own isolated contexts — so a task about the user's live screen or a session they have open must use computer_use (a browser/shell action lands in a different context and silently desyncs), but for an addressable target (a file path, a URL, a system fact) still prefer the purpose-built tool even if it is also on screen.** **Every image and list of coordinates has an identity, and every coordinate names the image it was read in.** A `screenshot`, an `elements` listing and a `windows` listing each come back with an `observation_id`, the reply's text leads with it, and every click, move, drag, scroll and inspect must carry the id of the image its x,y were read in — there is no rectangle to copy onto an action, and coordinates read in one image never apply to another. The transform belongs to the helper: it stores it with the image when it makes one and uses it as stored when an action arrives, so nothing re-derives geometry from a number the model echoed. A pointer action that names no image is refused before anything is sent, and the refusal names the one next move. The helper keeps only the last few images and only for about half a minute, and it re-reads the display's geometry before every pointer action, so an id that has been replaced, has aged out, or belongs to a display that moved or changed size is refused rather than clicked: the answer is a fresh screenshot and coordinates read again in it, never the old numbers re-sent. A point outside the image it names is refused too, never clamped onto an edge — a point that does not exist on the image it claims to come from was almost certainly read in a different one. If the helper's own measurements of a display disagree with the picture it captured, every action on it is refused with both sizes as an operator fault, because a wrong transform must never click. For a small or dense target the model zooms: a `screenshot` with a `region` {x,y,w,h} returns a magnified crop as a NEW image, and the model aims in that one. Coordinate integrity is enforced, not just prompted: when a pointer action's x,y are plausible on BOTH live grids (inside the on-screen region box the named image was cropped from, while that image magnifies it) the session refuses with a typed ambiguous-coordinates error that spells out the exact conversion, and the model re-sends with `confirm_grid: true` only after re-reading the image. The images themselves carry grounding aids: every tool screenshot is drawn with edge rulers in its own pixel space (the answer grid is visible in the picture), a post-action check image marks the EXECUTED click point with a ring + its coordinate (so a miss is seen, not inferred), and a `screenshot` with `marks: true` badges the accessibility click targets with numbers — the model then acts with `mark: <id>` plus that image's `observation_id` and the daemon resolves the exact point, no pixel estimation at all (a badge belongs to the image it was drawn on, and a number that image never badged is refused with its live count, never guessed). Element reads target the app that OWNS the window in view — resolved from the window list by stacking order and overlap with the requested region, never from the focused-application query (which is unreliable from the sidecar and, during a voice call, can name the floating voice companion instead of the app on screen). When that app's tree walks to zero elements, the sidecar makes one typed activation attempt (`AXManualAccessibility`, then `AXEnhancedUserInterface` on a typed rejection; cleared again on session end) and re-queries on a short bounded cadence — Chromium builds its tree lazily once an accessibility client starts asking — and every outcome is reported in the result (which app was read, what activation did, how long the tree took) instead of a silently empty list. Full-screen captures are sized by the looser of a long-edge and a pixel-area budget, so an ultrawide display arrives readable rather than as a thin strip. An intent the OS can name — launching an app (`open -a`), a menu item or settings toggle (AppleScript) — is a shell one-liner before it is ever a pixel click. **Every mutating action comes back with its own check, asked for by rule and never by the model, on the action's own reply — one helper call per action.** Anything that went out over the pointer or the keyboard returns the VIEW it acted in — the same crop when the action was aimed in a zoomed image (verification happens in the space the model acted in), the full screen otherwise — captured only once that view has stopped changing, so a control that repaints slowly returns the repainted view rather than the one before it; if it never settles within the helper's short budget the result says the view was still changing when the image was taken, which is an observation about the picture and never a reason to send the input again. That check is itself a new named image the next action aims in, and the model reads it before repeating anything: the image shows what the screen looks like now, never whether the input arrived, so an action is repeated only when the image shows its effect is missing, and a pointer that ended up elsewhere is reported as aim not confirmed rather than as a click that did nothing (a person moving the mouse leaves the same trace). The check also says whether that view differs from the image the model acted on, and when it does not the result says so in plain words — that alone does not mean the action failed and is not a reason to repeat it. **A run of mutating actions that leave the view unchanged is named rather than left to be counted:** at three in a row the result says so and names the ways out (a fresh full screenshot, an element listing, or telling the user). It is a sentence, never a refusal and never a cap — the per-session action budget stays the one hard limit. An action that reached its control through accessibility (`press`, `set_value`) gets a different check: the control is read again — role, label, whether it is enabled, its value where the control exposes one — and the result renders that state in one line. A control that no longer ANSWERS at all is reported as exactly that, which is the most informative answer the re-read has: it usually means the action worked and dismissed the control, and sometimes that the window was rebuilt underneath it, so the next move is to look rather than to press again. The read-back is never described as visual evidence and never upgrades the outcome: a successful press stays performed-and-unverified, because re-reading a control is not proof the press had its effect. The receipts say exactly what is known: when the check itself cannot be obtained after the input has gone out, the result reports the action performed and unverified rather than failed — reporting failure buys a second real click — and it carries the helper's own reason: an operator fault such as a display whose geometry the helper is reading wrongly keeps its own sentence (do not retry, tell the user, here are both measurements) instead of degrading into generic advice, and a check the human's `/pause` cancelled says the input went out, the machine is theirs, and to wait for `/resume` rather than to take a screenshot the paused session would itself refuse — and when the helper stops responding or exits during an action the result says the outcome is unknown and the session was reset, so the next step is a fresh screenshot rather than a blind re-send. Each action's phases (input, settle, capture, encode) are timed and recorded in the trace, so the cost of a check is a measurement rather than a guess. `inspect` (read-only, macOS only) reports the accessibility element under a point — its role and label (e.g. a button titled "Delete") — so the model can confirm the right control before a consequential click; it informs the model's own judgment and is NOT a blocking gate. `elements` and `inspect` expose best-effort accessibility metadata (macOS only): an empty result does not prove visible content rejects pixel interaction. An `elements` or `windows` listing names the image its points were read in, exactly as a screenshot does, so a follow-up action addresses that id; `wait_for_change` blocks until the screen changes and returns the new frame (instead of polling with repeated screenshots); `paste` enters long text via the clipboard (fast and unicode-safe); and key chords include `f1`–`f12`. **Controls can be NAMED, not only aimed at.** An `elements` listing gives each control a short reference (`e1`, `e2`, …) scoped to that listing, beside its role, label, current value, whether it is enabled, what it can do, whether its value can be set, and a short path of ancestor labels so two "Save" buttons are tellable apart — and a disabled control is listed AS disabled rather than dropped, because a model that cannot see the greyed-out button invents a reason it is missing. A control whose own accessibility action list contains press is pressed BY NAME (`press` with its `element_ref` and the listing's `observation_id`): that moves no pointer, needs no aim and cannot miss. A field the control itself reports as settable takes `set_value` the same way, and the helper reads the value back — a read-back that matches is a verified set, anything else (a secure field always reads back masked) is reported as set-but-unconfirmed with the instruction to read the field before relying on it; `type` and `paste` remain for a field that is not settable and for text that must go through real keystrokes. A pointer action may also carry an `element_ref` instead of x,y, and the control's bounds are re-read at that moment, so a control that has shifted since the listing is still hit. Nothing is ever inferred from a role name and nothing is ever switched for the model: a control that offers no press is refused rather than quietly clicked, a disabled one is refused with "work out what enables it" rather than retried, and a reference from a listing that has been replaced or aged out is refused as stale — the answer is a fresh `elements` and the reference from THAT reply. Naming a target twice (a reference together with coordinates or a mark) is refused before anything is dispatched, because guessing which was meant is a click on the wrong thing. A marked screenshot's badges carry references too, so `mark: N` names the badged CONTROL on a press and its point on a click. An accessibility action reports whether it pulled its application to the FRONT, which the reply says plainly because it changes where the next keystroke goes — and when the platform will not say, nothing is claimed either way rather than the front window being described as untouched. An accessibility call that FAILS comes back as a refused action whose sentence follows what the helper says became of the message, not the name of the failure: one that was made and never came back, or that failed after its message had gone out, says the outcome is unknown and to look before repeating rather than repeating; one the accessibility system refused before sending anything says so plainly and names the likely causes (the Accessibility permission, a control that has gone, a platform that does not offer it), with the platform's own error text beside the sentence rather than as it. An element walk that stopped at its element cap, its depth limit or its time budget says so and names the two ways to narrow it (a `region`, or a marked screenshot). It is the most dangerous capability — ambient authority over the live session, no rollback, screenshots are untrusted (treated as external content). It is **registered for the model when `ready?` holds: enabled AND the native sidecar binary installed** — a disabled or uninstalled daemon never advertises it. OS-permission state is a separate diagnostic, not part of `ready?`: `fermix doctor`'s `computer use` check probes the sidecar (non-prompting) and reports macOS Screen Recording and Accessibility distinctly (on Linux, X11 vs the unsupported Wayland). The classic failure is **Accessibility not granted, so synthetic clicks and keystrokes are silently dropped while screenshots still work** — a session probes that grant once at start and REFUSES mutating actions with a typed error naming the fix (read-only actions keep working), so the state is one loud refusal instead of a run of invisible no-ops; the fix the error and the check both name is System Settings → Privacy & Security → Accessibility. On macOS the setup Plugins page also offers a **Grant macOS permissions** button that raises the Screen Recording + Accessibility prompts up front and registers the helper with the OS, so it appears in System Settings as **Fermix** (with the app icon) and can be approved at enable time rather than only on the first screenshot. That single **Fermix** identity is deliberate: the sidecar runs as its own signed, notarized `.app` bundle (a stable identity the grant persists against across upgrades) so every macOS permission Fermix needs shows under one "Fermix" app — the same name the voice companion uses for its Microphone entry. If an upgrade leaves the check reporting a missing grant while the "Fermix" Screen Recording box still looks enabled, a stale grant from an older/pre-release build is shadowing the signed one — tell the user to remove the "Fermix" row under System Settings → Privacy & Security → Screen Recording (or run `tccutil reset ScreenCapture io.tezra.fermix.computer-use`) and grant again; first-time installs are unaffected. Read-only screenshots work without the Accessibility grant, which is why a missing permission informs rather than hides the tool. Within a turn the tool acquires a per-conversation session lazily (the OS-driver process opens on first use and is reused across actions). Safety is the **`access` posture, which is DERIVED 1:1 from `[sandbox] mode`** — there is no separate computer-use knob; an `open` sandbox is an `open` desktop. `strict` = look only (mutating actions refused — the one deterministic floor); `standard` = acts freely but the agent confirms conversationally before anything irreversible (its own judgment — it sees the screen — not a rule table or a blocking gate); `open` = acts autonomously but still pauses to confirm only a TRULY dangerous/catastrophic action (a higher bar than standard). Read-only actions always run. Host sessions additionally start only from an **attended origin** — an interactive chat or `fermix ask`, or the voice pet — and scheduled/cron runs fail closed (a host desktop must have a watching human); `access` governs *what* it does, origin governs *whether an unwatched run may start it at all*. Enabling is two coupled parts: installing the `computer_use_sidecar` helper (a native binary that ships no tools of its own) plus flipping `[fermix_core.computer_use] enabled`; both are needed, and the change applies on the next daemon restart. The OS driver runs as a separate process (not in the BEAM), spawned only while enabled; on session start the daemon performs a version handshake with the sidecar and **refuses to run one whose wire protocol is incompatible** with the running build (e.g. after a partial upgrade left an old binary), failing loud rather than misbehaving — reinstalling the `computer_use_sidecar` helper to match the daemon resolves it. Its `:gui_control` policy class is operator-only and **never delegated to subagents**, and carries no sandbox/path enforcement — all safety is the `access` posture (derived from the sandbox mode) + the attended-origin gate. **Coexistence (so the agent does not fight a present human for the one cursor):** because every action moves the real cursor and types into the focused window, a `courtesy` arbiter yields the seat when the human is actively using the machine — before a *disturbing* action (any click/drag/scroll/`mouse_move`/type/key/paste; note `mouse_move` counts even though it mutates nothing, because it warps the cursor) the daemon checks how long the human has been idle and, if they are active, briefly waits in-turn for them to pause, then either proceeds or holds the action back and tells the user it stepped aside. This never blocks read-only actions (screenshot/inspect/elements/wait) and is a courtesy, not a safety floor: the idle signal is macOS-only, and where it is unavailable the arbiter proceeds (falls back to the pre-coexistence behavior) rather than blocking. The human can also reclaim the machine explicitly with `/pause` (the session refuses actions — at classification and again at execution, so one classified a moment earlier cannot slip through — but stays alive and resumable) and hand it back with `/resume`; an action already handed to the helper cannot be recalled, so `/pause` says whether one is still finishing instead of promising the cursor back immediately, and `/pause`, `/resume` and teardown are answered while an action is under way rather than queueing behind it. **`/pause` reports what the helper confirmed, never what was sent:** it installs a barrier in the helper — which stops a sequence such as a drag part way through and releases what it was holding — and reports back that it is paused, that it is paused with one action still finishing, or, when the helper does not confirm the barrier, that the helper was shut down instead, since a machine that may still be driven must never be described as handed back. `/resume` lifts the barrier the same way. Ending a session gracefully — `/stop`, the end of a conversation, a reset after the helper answered — releases any held key or button before the helper is ended; a helper killed outright releases nothing, which is why the pause barrier rather than the kill is what stops a drag part way through. **The machine's cursor and keyboard are held by one conversation at a time:** a disturbing action from a second conversation is refused as busy with nothing sent (looking is never blocked — two conversations may read the same screen), and the hold lapses once its conversation has dispatched nothing for a minute, so a conversation that went quiet cannot keep the seat. Within one conversation there is one action at a time too: a second action sent while the first is still inside the helper is refused as busy rather than queued, so the answer is to wait, never to re-send. The helper reports on every mutating action whether the input was sent, half sent, or never sent, and that report — not a guess from what the check screenshot happened to show — is what the result's outcome says; a helper that does not report it at all is treated as a broken helper, the outcome is unknown, and the session takes a fresh one. That report rides on a refusal too, so a refused action says whether it refused before sending anything or part way through, rather than the refusal's name being read as proof nothing happened. Config: `[fermix_core.computer_use]` (`enabled`, display sizing, `max_actions` — the per-session action budget that halts a runaway; `courtesy` = `yield` (default) or `off`, and `courtesy_idle_ms` = how much human-quiet counts as idle) — note `access` is NOT a key here (it mirrors `[sandbox] mode`), and there is no `mode` key: computer use is host-only.
