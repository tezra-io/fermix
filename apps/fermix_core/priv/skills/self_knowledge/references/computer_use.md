# Computer use (experimental, off by default)

`computer_use` drives the host desktop: screenshots, mouse and keyboard, or a control acted on by name. It is the only tool that sees and acts on the person's own live screen; `browser` and `shell` run in their own contexts, so a task about their screen or a session they have open needs it. For an addressable target (a file, a URL, a system fact) the purpose-built tool comes first, and an intent the OS can name (launching an app with `open -a`, a menu item or setting through AppleScript) is a `shell` one-liner before it is a click. The tool's own description (`tool_help`) is the operating contract for aiming, zooming, marks and checks. It is the most dangerous capability: ambient authority over the live session, no rollback, and screenshots are untrusted content.

## Turning it on

1. **Mac app**: Settings > Computer > **Computer use** ("Runs as Fermix Computer Use, a separate signed helper."), then **Restart to apply**. In the same pane, **What the helper may do** > **Ask for both rights at once** > **Grant…** raises the Screen Recording and Accessibility prompts (or use the **Screen recording** and **Accessibility** rows).
2. **Linux and dev installs**: browser setup's Plugins tab, **Computer Use** card, **Enable** (and **Grant** on macOS), or `[fermix_core.computer_use] enabled = true`, then restart. With the flag on, the daemon downloads the helper at boot (checked against the sha256 this build pins), so the flag alone is enough, and an upgrade that needs a newer helper fetches it the same way.

- **Platforms**: Apple Silicon macOS; Linux x86_64. Intel Macs and Linux arm64 are not supported. Linux reads controls through the accessibility bus on X11 and Wayland alike. Pixels work on X11; on GNOME Wayland they go through the desktop portal, which asks the person on first use, with no `paste` or `windows`; KDE and other compositors get controls only.
- **What each system offers**: the tool offers only the actions the installed helper lists in its handshake. On macOS that is the pixel actions plus the controls (`elements`, `inspect`, the verbs on a control, `wait_for`). On Linux it is the same without `inspect`, and without the pixel actions the desktop cannot serve; an action not offered cannot be refused.
- The tool is offered only when enabled **and** the helper is installed. OS permissions are a diagnostic, not a gate: without Accessibility, screenshots still work and every mutating action is refused with an error naming System Settings > Privacy & Security > Accessibility (clicks would otherwise be dropped silently).
- The helper runs as its own process only while enabled; a conversation's session opens on first use and is reused. A helper whose protocol does not match the daemon is refused at session start; re-enabling (reinstalling) the helper fixes it.
- `fermix doctor`'s `computer use` row probes the helper without prompting: on Linux whether the desktop serves screen capture and input, with rows for the display server, the accessibility bus, X11 pixels, the desktop portal and a stored screenshot refusal (with the command that resets it); on macOS Screen Recording and Accessibility, separately. The Mac app's Doctor has no computer-use row: its Settings > Computer and Settings > Permissions show the rights.

## Permissions and identity (macOS)

- The helper is a separate signed, notarized app that System Settings lists as **Fermix Computer Use** (bundle id `io.tezra.fermix.computer-use`), so its grants survive upgrades. The Fermix app's own rows (such as Microphone) read **Fermix**.
- **A grant that looks on but the check says missing** is a stale grant from an older build. Remove the **Fermix Computer Use** row under Privacy & Security > Screen Recording (or run `tccutil reset ScreenCapture io.tezra.fermix.computer-use`) and grant again. Removing the plain **Fermix** row resets the app, not the helper.

## Safety

- `access` follows `[sandbox] mode` one to one; there is no separate key. `strict`: look only (mutating actions refused). `standard`: acts, but confirms in chat before anything irreversible (a judgment call, not a rule table). `open`: acts on its own and confirms only a truly dangerous action. Read-only actions always run.
- Operator-only and never delegated to sub-agents. A session starts only from an attended origin: an interactive chat, a `fermix ask` a person ran, or a voice call. Refused: scheduled runs; a prompt on a local socket (`fermix ask`, `fermix acp`, the Mac app's chat socket) sent by a process Fermix started or by a detached one; a coding-run notice on the ACP surface; and every Buzz-wired ACP session, even the owner's (others can post there; the refusal names the app, the owner's own chat or voice). An unattended run cannot drive a session an attended turn left open.
- `inspect` (macOS) names the element under a point, to confirm the right control before a consequential click; it informs judgment and blocks nothing. A verb on a control is input like a click: strict access refuses it, a pause refuses it, and it takes the cursor's seat.

## Sharing the machine

- **Courtesy** (`courtesy = "yield"`, default): before a disturbing action (click, drag, scroll, `mouse_move`, type, key, paste) it checks how long the person has been idle (`courtesy_idle_ms`); if they are active it waits briefly, then goes ahead or steps aside and says so. Read-only actions are never held. The idle signal is macOS-only; elsewhere it goes ahead.
- **One conversation holds the cursor**: a disturbing action from a second conversation is refused as busy with nothing sent (looking is never blocked), and the hold lapses after a minute with no action. Within a conversation, a second action while one is in the helper is refused as busy: wait, never re-send.
- **`/pause`** makes the session refuse actions (checked at classification and again at execution) while staying resumable; **`/resume`** hands it back. `/pause` reports what the helper confirmed: paused, paused with one action still finishing (a sent action cannot be recalled), or that the helper was shut down because it did not confirm. It stops a drag part way and releases held keys and buttons. `/pause`, `/resume` and shutdown are answered while an action is running.
- **`/stop`** cancels turns, not this session: `/pause` is how the owner takes the machine back. Ending the conversation or a helper reset releases held keys and buttons; a helper killed outright releases nothing.

## What an action reports

- A pointer action names the image (`observation_id`) its coordinates were read in. The helper keeps the last few images for about half a minute and re-reads display geometry before each action, so a replaced, expired or foreign id, or a point outside its image, is refused: take a fresh screenshot. A point plausible on both a zoomed image and the full screen is refused as ambiguous until re-sent with `confirm_grid: true`.
- `elements` lists controls one per line: reference (`e1`, `e2`, …), a role named the same on every system (`button`, `textfield`, `checkbox`, …), label, value (never a secure field's, which reads `secure`), enabled, state (on/off, expanded/collapsed, selected, focused), the verbs that control takes, its click point when the system reports one, and the labels it sits under. `scope` reads the window, the app, the focused control, open menus or open dialogs; `query` finds controls by role and name; `skeleton: true` reads three levels and marks each container it cut with `+N inside`, and `root` lists inside one (references outside it stay valid). List an app plainly the first time: only a listing with none of those asks an app that builds its tree late (Chromium, Electron) to expose it, so a narrowed first listing can come back empty, and the reply then says so. `elements` and `inspect` are best-effort: an empty result does not mean pixels will not work.
- **Verbs on a control**: `press`, `set_value`, `focus`, `select`, `toggle` (with `on`), `expand`, `collapse`, `scroll_to`, and `type` with an `element_ref` (inserts at the caret with no keyboard; offered only where the helper reports that it sends input through accessibility, so elsewhere `type` types at the focus). Each acts on a reference without moving the pointer and cannot miss, and each is offered on a control only where it has a route. The state verbs read first and send nothing when the control already holds what was asked (the row's outcome is `already`); every write is read back. `focus` never brings a window forward. A disabled control, a stale or ambiguous reference, a verb the control has no route for, an unreadable state or a target named twice is refused before anything is sent, and a refused verb is never turned into a click.
- **Waiting on the controls**: `wait_for` waits until a condition holds (a control appears, disappears, becomes enabled or holds a value; a window title or some text; a menu opens or closes), at most 25 s, without sending input; `until` on any input action waits for that action's effect in the same call, with its baseline read before the input. Not met by the deadline is an answer, not a failure. An action that sent input also names the dialogs, alerts, menus and popups it left open (by kind and label, with no reference: `elements` with the `scope` it names lists inside them).
- Grounding aids: screenshots carry edge rulers in their own pixel space; a check image rings the executed click point with its coordinate; `marks: true` badges accessibility targets, and `mark: N` with that image's id resolves the exact point (a number the image never badged is refused). Full-screen captures are sized to a long-edge and pixel-area budget, so an ultrawide display stays readable; a `region` crop is a new, magnified image.
- Element reads target the app that owns the window in view, not the focused app. When its tree is empty, the helper makes one activation attempt and re-reads briefly (Chromium builds its tree lazily), and the result says which app was read and what activation did. A walk cut short by its element, depth or time limit says so and suggests a `query`, a `scope`, `skeleton` or a `region`. An accessibility action says whether it pulled its app to the front; a failed accessibility call says whether its message went out (outcome unknown: look before repeating) or was refused before sending (likely the Accessibility permission, a vanished control, or an unsupported platform).
- Every mutating action returns its own check: the view it acted in once settled (a new image to aim in), or, for a verb on a control, the control read again. A check shows the screen now, not whether input arrived: repeat only when the effect is visibly missing. Three unchanged views in a row are named in the result, never refused; `max_actions` is the one hard limit.
- The outcome comes from the helper's own report (sent, half sent, never sent). No check after input went out reads "performed, unverified", never "failed"; a helper that stops mid-action reads "outcome unknown, session reset": take a fresh screenshot before anything else. A display whose measured size disagrees with its capture is an operator fault: stop and tell the person.
- `wait_for_change` waits for the screen to change instead of repeated screenshots; `paste` enters long text through the clipboard (and is the answer when the keyboard layout cannot type the text); keys include `f1`–`f12`.
- Refusals only the Linux helper answers: a desktop's consent prompt declined or unanswered, no single active window for keys, a keyboard not in its plain state or a layout that cannot type the text, pixels this desktop cannot serve, an application whose toolkit publishes no controls (Qt without its accessibility switch, Chromium without an assistive client), and, under X11, a window that cannot be proven to be the one bound (it names no process, or its id now belongs to another window).

## Work inside one window (experimental, off by default)

Settings > Computer > **Work inside one window**, or `background = true`. It is offered only where the helper lists binding: macOS, and Linux under X11, never on Wayland. The model binds one window (`windows`, then `select_target` with its `window_id`; `release_target` gives it back); every look and action then uses that window's own picture, even when covered, in its own coordinates, and `press`/`set_value` act without moving the pointer, so the person keeps working in front. While bound, a mutating action naming no window is refused (`select_target` with `"window_id": "desktop"` means the whole screen) and `wait_for_change` is refused. A panel on screen names the window with Pause and Stop (the same as `/pause` and ending the session); Stop also refuses every further computer-use call in that turn, until the person's next message. On Linux the panel is a badge above the window, binding makes the window repaint once (it may flash where nothing composites), and a GTK 4 window binds without its controls, so work in it is by pixels. With the flag off none of this is offered. `fermix doctor`'s `window binding` row reports the flag, whether the helper can bind a window and whether its panel is present.

## Config

`[fermix_core.computer_use]`: `enabled`, display sizing, `max_actions` (the per-session action budget), `courtesy` (`yield` or `off`), `courtesy_idle_ms`, `background`. No `access` key (it mirrors `[sandbox] mode`) and no `mode` key (host desktop only). Restart to apply.
