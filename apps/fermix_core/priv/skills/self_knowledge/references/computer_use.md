# Computer use (experimental, off by default)

Computer use is **experimental and off by default**, enabled from the setup Plugins page (the `computer_use_sidecar` card) on **Apple Silicon (M-series) macOS and Linux x86_64** — Intel Macs are not supported (install fails loud). Enabling downloads the native helper via the `compux` library (fetched from its GitHub release and verified against a baked sha256 — no cosign, no plugin-catalog tarball) and turns the feature on; the capability registers for the model **only once enabled AND `ready?`** holds (below). It is the most dangerous capability — the rest of this section is its operating model, not a casual toggle.

`computer_use` drives the host desktop GUI by screenshot + mouse/keyboard, one action per call (`screenshot` to see, then click/type/key/scroll/drag in screenshot pixel coordinates). It is host-desktop control only — there is no "browser mode" (web automation is the separate browser tool). **computer_use is the only capability that sees and drives the user's actual screen; the browser and shell tools operate in their own isolated contexts — so a task about the user's live screen or a session they have open must use computer_use (a browser/shell action lands in a different context and silently desyncs), but for an addressable target (a file path, a URL, a system fact) still prefer the purpose-built tool even if it is also on screen.** For a small or dense target the model zooms: a `screenshot` with a `region` {x,y,w,h} returns a magnified crop, and passing the SAME region on the follow-up click/drag maps the coordinates read in the crop back to the real pixel — clicks land far more accurately than raw full-screen pixels. Every mutating action returns a fresh screenshot so the model can verify the result and retry a missed click. `inspect` (read-only, macOS only) reports the accessibility element under a point — its role and label (e.g. a button titled "Delete") — so the model can confirm the right control before a consequential click; it informs the model's own judgment and is NOT a blocking gate. `elements` (read-only, macOS only) lists the interactive accessibility elements each with a click point, so the model targets by element instead of guessing pixels; `wait_for_change` blocks until the screen changes and returns the new frame (instead of polling with repeated screenshots); `paste` enters long text via the clipboard (fast and unicode-safe); and key chords include `f1`–`f12`. It is the most dangerous capability — ambient authority over the live session, no rollback, screenshots are untrusted (treated as external content). It is **registered for the model when `ready?` holds: enabled AND the native sidecar binary installed** — a disabled or uninstalled daemon never advertises it. OS-permission state is a separate diagnostic, not part of `ready?`: `fermix doctor`'s `computer use` check probes the sidecar (non-prompting) and reports macOS Screen Recording and Accessibility distinctly (on Linux, X11 vs the unsupported Wayland). The classic failure is **Accessibility not granted, so synthetic clicks and keystrokes are silently dropped while screenshots still work** — it looks like the tool can only screenshot; the fix the check names is System Settings → Privacy & Security → Accessibility. On macOS the setup Plugins page also offers a **Grant macOS permissions** button that raises the Screen Recording + Accessibility prompts up front and registers the helper with the OS, so it appears in System Settings as **Fermix** (with the app icon) and can be approved at enable time rather than only on the first screenshot. That single **Fermix** identity is deliberate: the sidecar runs as its own signed, notarized `.app` bundle (a stable identity the grant persists against across upgrades) so every macOS permission Fermix needs shows under one "Fermix" app — the same name the voice companion uses for its Microphone entry. If an upgrade leaves the check reporting a missing grant while the "Fermix" Screen Recording box still looks enabled, a stale grant from an older/pre-release build is shadowing the signed one — tell the user to remove the "Fermix" row under System Settings → Privacy & Security → Screen Recording (or run `tccutil reset ScreenCapture io.tezra.fermix.computer-use`) and grant again; first-time installs are unaffected. Read-only screenshots work without the Accessibility grant, which is why a missing permission informs rather than hides the tool. Within a turn the tool acquires a per-conversation session lazily (the OS-driver process opens on first use and is reused across actions). Safety is the **`access` posture, which is DERIVED 1:1 from `[sandbox] mode`** — there is no separate computer-use knob; an `open` sandbox is an `open` desktop. `strict` = look only (mutating actions refused — the one deterministic floor); `standard` = acts freely but the agent confirms conversationally before anything irreversible (its own judgment — it sees the screen — not a rule table or a blocking gate); `open` = acts autonomously but still pauses to confirm only a TRULY dangerous/catastrophic action (a higher bar than standard). Read-only actions always run. Host sessions additionally start only from an **attended origin** — an interactive chat or `fermix ask`, or the voice pet — and scheduled/cron runs fail closed (a host desktop must have a watching human); `access` governs *what* it does, origin governs *whether an unwatched run may start it at all*. Enabling is two coupled parts: installing the `computer_use_sidecar` helper (a native binary that ships no tools of its own) plus flipping `[fermix_core.computer_use] enabled`; both are needed, and the change applies on the next daemon restart. The OS driver runs as a separate process (not in the BEAM), spawned only while enabled; on session start the daemon performs a version handshake with the sidecar and **refuses to run one whose wire protocol is incompatible** with the running build (e.g. after a partial upgrade left an old binary), failing loud rather than misbehaving — reinstalling the `computer_use_sidecar` helper to match the daemon resolves it. Its `:gui_control` policy class is operator-only and **never delegated to subagents**, and carries no sandbox/path enforcement — all safety is the `access` posture (derived from the sandbox mode) + the attended-origin gate. **Coexistence (so the agent does not fight a present human for the one cursor):** because every action moves the real cursor and types into the focused window, a `courtesy` arbiter yields the seat when the human is actively using the machine — before a *disturbing* action (any click/drag/scroll/`mouse_move`/type/key/paste; note `mouse_move` counts even though it mutates nothing, because it warps the cursor) the daemon checks how long the human has been idle and, if they are active, briefly waits in-turn for them to pause, then either proceeds or holds the action back and tells the user it stepped aside. This never blocks read-only actions (screenshot/inspect/elements/wait) and is a courtesy, not a safety floor: the idle signal is macOS-only, and where it is unavailable the arbiter proceeds (falls back to the pre-coexistence behavior) rather than blocking. The human can also reclaim the machine explicitly with `/pause` (the session refuses actions but stays alive and resumable) and hand it back with `/resume`. Config: `[fermix_core.computer_use]` (`enabled`, display sizing, `max_actions` — the per-session action budget that halts a runaway; `courtesy` = `yield` (default) or `off`, and `courtesy_idle_ms` = how much human-quiet counts as idle) — note `access` is NOT a key here (it mirrors `[sandbox] mode`), and `mode` was removed (host-only).
