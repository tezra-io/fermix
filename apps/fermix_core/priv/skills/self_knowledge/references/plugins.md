# Plugins

Plugins are connected integrations that own a surface (an API, a vault) and register their own tools. **Bundled** (always present): Gmail, Google Calendar, Google Drive — Google OAuth plugins. A connected plugin registers all its tools; calling one whose scope wasn't granted returns a graceful "reauthorize" error rather than the tool vanishing. **On an HTTP-rail plugin an expired or rejected credential reaches the agent as a named, actionable tool error — not a bare status code:** an OAuth plugin's 401 says ``<plugin> needs reconnection. Run `fermix plugins auth reauthorize <plugin>` ``, an api_key plugin's 401 points at `fermix plugins auth set <plugin>`, and a not-yet-connected plugin at `fermix plugins auth login <plugin>`; relay that exact fix to the user (or run it, if operator) instead of retrying blindly. Google additionally classifies 403s distinctly (file-permission, organizer-only, rate-limit) so the message says what actually failed. OAuth tokens that lapse from disuse (a provider or plugin left idle until its refresh token expires) surface to the operator as a "Reconnect needed" badge on the setup provider page and in `fermix doctor`'s `auth tokens` check — send the user there when they ask whether their integrations are healthy.

**The agent discovers what's live from the `## Plugins` section of the runtime prompt — there is no agent tool that lists plugins.** Ready plugins list their tool names there: call a listed tool directly (its skill, opened with `skill_view`, documents arguments; deferred schemas resolve via `tool_describe`/`tool_search`), and prefer it over browser/web/shell for that surface. An enabled-but-not-ready plugin instead shows a `status=` (`needs_auth`/`needs_config`/`missing_host_runtime`/`not_installed`) with its fix rather than vanishing — that means not connected, so offer to connect it on the setup page rather than scraping. Enable/disable/logout take effect on the agent's next turn (the reload drops cached runtime context — no restart); calling a disabled plugin's tool refuses with an enable hint, not a generic auth error.

**Additional plugins** come from a signed catalog bundled inside the binary (the only catalog source — new/updated plugins arrive with releases via `fermix upgrade`). They use one of two rails: **http** (declarative templates running in-VM, double-guarded — install-time template validation, https-only with no placeholder/userinfo host, plus a runtime SSRF floor blocking loopback/private/metadata addresses) or **mcp** (a supervised local process inside the daemon whose discovered tools register as `<plugin>_<tool>`; install probes the declared Node/Python runtime, refusing too-old/missing with `missing_host_runtime`). An http plugin authenticates with either an **OAuth** provider (`[fermix_core.oauth.<provider>]` client config; status `needs_auth` until connected) or a static **api_key** the operator sets (`fermix plugins auth set NAME`; status `needs_secret` until set), injected with the manifest's `Authorization` scheme — `Bearer` by default, or `Bot` for a provider like Discord. Which optional plugins exist and whether any are enabled is runtime state, so this skill names none beyond the bundled trio — read the `## Plugins` prompt section or run `fermix plugins catalog`.

Operator CLI: `fermix plugins list | catalog | installed | doctor` inspect; `enable | disable | reload` toggle; `install | upgrade | pin | uninstall | gc` manage the local store under `~/.fermix/plugins/` (install verifies the tarball signature and re-validates the manifest, so a plugin that installs always loads; `enable` auto-installs a missing catalog plugin; bundled plugins can't be uninstalled — disable instead); `auth login|reauthorize|refresh|logout NAME` manages OAuth plugins (tokens/scopes in `~/.fermix/auth.json`); `auth set NAME VALUE` / `auth clear NAME` store/remove the static credential an **api_key** plugin authenticates with (keychained, never plaintext config); `config set NAME KEY VALUE` sets manifest-declared per-plugin values (`[fermix_core.plugins.<name>]`, UPPER_SNAKE, injected into an mcp plugin's process env, surviving disable→enable). The web setup Plugins page mirrors the catalog (install verifies sha256 + cosign; OAuth client id/secret entered via a per-provider-group modal). Distribution ops emit `[:fermix, :plugin, :dist]` telemetry.

For plugin authors, `[fermix_core.plugins] dev_local = "<path>"` points at a directory whose immediate subdirectories are plugin dirs (for a fermix-plugins checkout, its `plugins/` directory). Those load into the registry like installed ones — full manifest validation, skills loaded in place — with no install or tarball step. A missing/unreadable path or a bad manifest fails plugin loading loud, and a dev_local name may not collide with a bundled or installed plugin.
