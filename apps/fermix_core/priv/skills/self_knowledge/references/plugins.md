# Plugins

Plugins are connected integrations that own a surface (an API, a vault) and register their own tools. **Bundled** (always present): Gmail, Google Calendar, Google Drive — Google OAuth plugins. A connected plugin registers all its tools; calling one whose scope wasn't granted returns a graceful "reauthorize" error rather than the tool vanishing. **On an HTTP-rail plugin an expired or rejected credential reaches the agent as a named, actionable tool error — not a bare status code:** an OAuth plugin's 401 says ``<plugin> needs reconnection. Run `fermix plugins auth reauthorize <plugin>` ``, an api_key plugin's 401 points at `fermix plugins auth set <plugin>`, and a not-yet-connected plugin at `fermix plugins auth login <plugin>`; relay that exact fix to the user (or run it, if operator) instead of retrying blindly. Google additionally classifies 403s distinctly (file-permission, organizer-only, rate-limit) so the message says what actually failed. OAuth tokens that lapse from disuse (a provider or plugin left idle until its refresh token expires) surface to the operator as a "Reconnect needed" badge on the setup provider page and in `fermix doctor`'s `auth tokens` check — send the user there when they ask whether their integrations are healthy.

**The agent discovers what's live from the `## Plugins` section of the runtime prompt — there is no agent tool that lists plugins.** Ready plugins list their tool names there: call a listed tool directly (its skill, opened with `skill_view`, documents arguments; deferred schemas resolve via `tool_describe`/`tool_search`), and prefer it over browser/web/shell for that surface. An enabled-but-not-ready plugin instead shows a `status=` (`needs_auth`/`needs_config`/`missing_host_runtime`/`not_installed`) with its fix rather than vanishing — that means not connected, so offer to connect it on the setup page rather than scraping. Enable/disable/logout take effect on the agent's next turn (the reload drops cached runtime context — no restart); calling a disabled plugin's tool refuses with an enable hint, not a generic auth error.

**Additional plugins** come from a signed catalog bundled inside the binary (the only catalog source — new/updated plugins arrive with releases via `fermix upgrade`). They use one of two rails: **http** (declarative templates running in-VM, double-guarded — install-time template validation, https-only with no placeholder/userinfo host, plus a runtime SSRF floor blocking loopback/private/metadata addresses, and redirects are refused rather than followed — a 3xx comes back as a typed error naming the `Location`, because the floor can only vet the URL it was given) or **mcp** (a supervised local process inside the daemon whose discovered tools register as `<plugin>_<tool>`; install probes the declared Node/Python runtime, refusing too-old/missing with `missing_host_runtime`). An http plugin authenticates with either an **OAuth** provider (`[fermix_core.oauth.<provider>]` client config; status `needs_auth` until connected) or a static **api_key** the operator sets (`fermix plugins auth set NAME`; status `needs_secret` until set), injected with the manifest's `Authorization` scheme — `Bearer` by default, or `Bot` for a provider like Discord. Which optional plugins exist and whether any are enabled is runtime state, so this skill names none beyond the bundled trio — read the `## Plugins` prompt section or run `fermix plugins catalog`.

**Remote (hosted) MCP plugins** are the mcp rail's second runtime: instead of a local process, the daemon holds an authenticated HTTPS session to the vendor's own MCP server. Such a plugin **ships no code** — the artifact is a signed manifest plus a skill, with no source, no vendored dependencies, and no install script — so the manifest is an *enforcement boundary*, not a preview. Signed and enforced at connect: the endpoint, the exact set of agent-visible tool names, and each tool's canonical input/output descriptor (its name, input schema, output schema, and annotations, canonicalized and hashed). Anything the upstream advertises that the manifest does not declare is dropped by raw name before its schema is even parsed; every tool the selected profile names must be present; every descriptor hash must match. One missing or changed descriptor registers **none** of that profile's tools — an upstream change fails loudly rather than quietly widening capability — and the fix is a reviewed, re-signed plugin version, never a permissive fallback. A remote plugin may preserve its upstream tool names rather than take the `<plugin>_` prefix; a name that collides with an existing capability or skill fails the whole registration instead of being renamed or dropped. The credential never reaches the process tree: the server spec carries an opaque reference the session resolves inside its own initialization.

Remote status vocabulary — the static install/config/auth ladder first, then the live client: `needs_secret` (no token stored), `needs_workspace` (the token works but no workspace is selected), `insufficient_credential_scope` (the selected profile needs a read/write token and the stored one is read-only), `invalid_remote_config` (profile/workspace/signed runtime is invalid — do not start), `connecting`, `ready` (authenticated **and** the entire signed contract matched — the only state in which its tools exist), `remote_unreachable` (DNS/TLS/transport failed after the bounded startup attempts), `reauthorization_required` (the token was rejected or revoked — replace it), `upstream_contract_mismatch` (a required tool vanished or a descriptor changed — do not call its tools), `capability_conflict` (a name collides locally), `remote_security_blocked` (endpoint/DNS/redirect/TLS policy refused it), `remote_protocol_error` (invalid negotiated version or session state — reconnect or upgrade). "Startable" and "callable" are deliberately different questions: installed + enabled + compatible + credentialed is what starts the client, and only the completed contract check makes it `ready`. That live table lives in the daemon's memory alone, so a one-shot CLI asks the daemon for it — `fermix doctor`'s `plugins` row reports the static install/config/auth result plus "runtime status unavailable — daemon not running" when there is no daemon, and never infers `ready` from a table it cannot see. A refusal is described the same way wherever it appears — the daemon log, the `plugins` row, and the setup UI all render one classified answer as `status/detail (capability)`, for example `upstream_contract_mismatch/missing_tool (eden_get_item_connections)`: the class distinguishes a tool the upstream withdrew from one it reshaped, and the capability names which one, so the question a contract mismatch actually raises is answered on the surface the operator is already looking at. The capability is named only when it is a name Fermix selected from that plugin's own signed manifest; a peer-supplied name and anything derived from a crash are reported by class alone.

**Eden** (a hosted second brain) is the first remote plugin. Connect: paste a personal access token (created under Eden's Settings → Integrations → API access and shown once), then pick exactly one workspace from a setup-only discovery call the agent never sees — every later call is pinned to that workspace, and a model-supplied workspace argument is rejected before any network I/O. The default access profile is **retrieval** (read-only tools; a read-only token is enough); **capture** adds the additive write tools, is an explicit opt-in that requires an Eden read/write token, and never downgrades itself back to retrieval after a permission failure. Eden is a paid hosted cloud service and several actions are metered against its credit balance — semantic workspace search, board reads, and highlight search all refuse with `out_of_credits` once the balance is spent, while literal search, listing, and note reads keep working — so use it interactively and on request, never as a crawl, mirror, or background sync. Three operator actions are deliberately distinct: **Disable** stops the client and hides its tools but keeps the credential for a later re-enable; **Forget local credential** deletes the OS-keychain item and only then drops the config reference, so a failed deletion errors instead of orphaning the secret; **Revoke upstream** is the only one that invalidates the token itself, and only Eden can do it — Fermix links the operator to that page and never claims to have revoked anything. Native Eden OAuth is not available yet: Eden's authorization server requires Dynamic Client Registration, while Fermix's OAuth plugin path expects a known provider with operator-supplied static client config — supporting it means a second OAuth engine, not a config entry.

Operator CLI: `fermix plugins list | catalog | installed | doctor` inspect; `enable | disable | reload` toggle; `install | upgrade | pin | uninstall | gc` manage the local store under `~/.fermix/plugins/` (install verifies the tarball signature and re-validates the manifest, so a plugin that installs always loads; `enable` auto-installs a missing catalog plugin; bundled plugins can't be uninstalled — disable instead); `auth login|reauthorize|refresh|logout NAME` manages OAuth plugins (tokens/scopes in `~/.fermix/auth.json`); `auth set NAME` / `auth clear NAME` store/forget the static credential an **api_key** plugin authenticates with (keychained, never plaintext config). **A secret is never passed as an argument** — `auth set NAME` prompts on the terminal without echoing, and `... | auth set NAME --stdin` reads it from a pipe for scripts; the old positional form exits non-zero and tells the operator to rotate the value they just put in their shell history. `auth clear NAME` is a truthful *forget local credential*: it deletes the OS-keychain item first and only then drops the config reference, so a failed deletion errors with the reference intact instead of orphaning a credential — it does **not** revoke anything upstream, which the user must do with the provider. It is also distinct from `disable`, which stops the plugin but keeps the credential for a later re-enable; `config set NAME KEY VALUE` sets manifest-declared per-plugin values (`[fermix_core.plugins.<name>]`, UPPER_SNAKE, injected into an mcp plugin's process env, surviving disable→enable). The web setup Plugins page mirrors the catalog (install verifies sha256 + cosign; OAuth client id/secret entered via a per-provider-group modal). Distribution ops emit `[:fermix, :plugin, :dist]` telemetry.

For plugin authors, `[fermix_core.plugins] dev_local = "<path>"` points at a directory whose immediate subdirectories are plugin dirs (for a fermix-plugins checkout, its `plugins/` directory). Those load into the registry like installed ones — full manifest validation, skills loaded in place — with no install or tarball step. A missing/unreadable path or a bad manifest fails plugin loading loud, and a dev_local name may not collide with a bundled or installed plugin.
