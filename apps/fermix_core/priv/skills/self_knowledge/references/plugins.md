# Plugins

Plugins are connected integrations that own a surface (an API, a vault) and register their own tools. **Bundled** (always present): Gmail, Google Calendar, Google Drive — Google OAuth plugins. A connected plugin registers all its tools; calling one whose scope wasn't granted returns a graceful "reauthorize" error rather than the tool vanishing. **On an HTTP-rail plugin an expired or rejected credential reaches the agent as a named, actionable tool error — not a bare status code:** an OAuth plugin's 401 says ``<plugin> needs reconnection. Run `fermix plugins auth reauthorize <plugin>` ``, an api_key plugin's 401 points at `fermix plugins auth set <plugin>`, and a not-yet-connected plugin at `fermix plugins auth login <plugin>`; relay that exact fix to the user (or run it, if operator) instead of retrying blindly. Google additionally classifies 403s distinctly (file-permission, organizer-only, rate-limit) so the message says what actually failed. OAuth tokens that lapse from disuse (a provider or plugin left idle until its refresh token expires) surface to the operator as a "Reconnect needed" badge on the setup provider page and in `fermix doctor`'s `auth tokens` check — send the user there when they ask whether their integrations are healthy.

**A refused sign-in client is a different failure from an expired sign-in, and signing in again cannot fix it.** An OAuth plugin authenticates to its provider with the operator's own sign-in client (client ID + secret, saved in setup); when the provider stops accepting that client — typically because the secret was regenerated in the provider's developer console, or saved into a different Fermix home — every sign-in and every refresh is refused. It looks like: X answering 401 `unauthorized_client` "Missing valid authorization header" (the request is correct; the saved secret is stale), Google, Notion or Tesla `invalid_client`, GitHub `incorrect_client_credentials`, Slack `invalid_client_id`/`bad_client_secret`. Fermix names the provider and the one fix on every surface — the setup page's flash and plugin card (with an **Update client** button beside Reauthorize), the macOS app's integration row (which says the saved sign-in client was refused and leads with **Set up the sign-in client**, keeping **Sign in again**), `fermix plugins auth login|refresh`, and the plugin's tool errors: copy the client ID and secret from that provider's developer console into its sign-in client in setup, then sign in again. The quarantined plugin reads as `reauthorization_required`, but neither `fermix auth login` nor a daemon restart helps until the client is updated; a successful sign-in clears it. When the daemon ran the op (the setup page or the macOS app), its log and the `plugin_auth` trace keep the vendor's own error code and description; a CLI `fermix plugins auth` verb runs without the daemon, so it prints the fix to the terminal and leaves no trace row.

**The agent discovers what's live from the `## Plugins` section of the runtime prompt — there is no agent tool that lists plugins.** Ready plugins list their tool names there: call a listed tool directly (its skill, opened with `skill_view`, documents arguments; deferred schemas resolve via `tool_describe`/`tool_search`), and prefer it over browser/web/shell for that surface. An enabled-but-not-ready plugin instead shows a `status=` (`needs_auth`/`needs_config`/`missing_host_runtime`/`not_installed`) with its fix rather than vanishing — that means not connected, so offer to connect it on the setup page rather than scraping. Enable/disable/logout take effect on the agent's next turn (the reload drops cached runtime context — no restart); calling a disabled plugin's tool refuses with an enable hint, not a generic auth error.

**Additional plugins** come from a signed catalog bundled inside the binary (the only catalog source — new/updated plugins arrive with releases via `fermix upgrade`). They use one of two rails: **http** (declarative templates running in-VM, double-guarded — install-time template validation, https-only with no placeholder/userinfo host, plus a runtime SSRF floor blocking loopback/private/metadata addresses, and redirects are refused rather than followed — a 3xx comes back as a typed error naming the `Location`, because the floor can only vet the URL it was given) or **mcp** (a supervised local process inside the daemon whose discovered tools register as `<plugin>_<tool>`; install probes the declared Node/Python runtime, refusing too-old/missing with `missing_host_runtime`). An http plugin authenticates with either an **OAuth** provider (`[fermix_core.oauth.<provider>]` client config — `client_id` + `client_secret`, plus optional `redirect_host`/`redirect_port`; status `needs_auth` until connected. Tesla takes two more keys because its Fleet API is regional and it registers a public https callback rather than a loopback one: `region` is chosen as part of the sign-in client and has **no default** — `na` (North America and Asia-Pacific) or `eu` (Europe, Middle East and Africa) — because it picks the Fleet API base URL the sign-in exchange must name as its audience and the host every tool then calls, and `redirect_uri` is the registered callback, defaulting to the hosted bounce page that forwards to the local listener. A client with no region, or a region Fermix has no base URL for, is refused when it is saved and again at sign-in, never defaulted; China is not offered, because it needs a separate Tesla application. Right after a sign-in Fermix asks Tesla which region the account is actually in: on a mismatch the grant is stored but marked, the plugin reads as `wrong_region`, its row names the account's own region and leads with **Set up the sign-in client**, and no tool call is made at all — so the owner is told to change the region and sign in again instead of every tool answering Tesla's 421 "user out of region") or a static **api_key** the operator sets (`fermix plugins auth set NAME`; status `needs_secret` until set), injected with the manifest's `Authorization` scheme — `Bearer` by default, or `Bot` for a provider like Discord. Which optional plugins exist and whether any are enabled is runtime state, so this skill names none beyond the bundled trio — read the `## Plugins` prompt section or run `fermix plugins catalog`.

**A plugin can be retired.** When a build stops offering a name, an install that already had it is not left running it: the config Fermix reads drops that plugin from `enabled`, drops its `[fermix_core.plugins.<name>]` section and its `[fermix_core.plugin_secrets]` entry, and names it once at warning — so its rail never starts and the next config save writes the file without it. A retired remote-MCP plugin whose upstream has moved on would otherwise log a discovery failure on every boot, which reads as broken rather than gone. The stored credential itself is deliberately untouched: forgetting it locally and revoking it upstream stay two separate operator actions.

**Remote (hosted) MCP plugins** are the mcp rail's second runtime: instead of a local process, the daemon holds an authenticated HTTPS session to the vendor's own MCP server. Such a plugin **ships no code** — the artifact is a signed manifest plus a skill, with no source, no vendored dependencies, and no install script — so the manifest is an *enforcement boundary*, not a preview. Signed and enforced at connect: the endpoint, the exact set of agent-visible tool names, and each tool's canonical input/output descriptor (its name, input schema, output schema, and annotations, canonicalized and hashed). Anything the upstream advertises that the manifest does not declare is dropped by raw name before its schema is even parsed; every tool the selected profile names must be present; every descriptor hash must match. One missing or changed descriptor registers **none** of that profile's tools — an upstream change fails loudly rather than quietly widening capability — and the fix is a reviewed, re-signed plugin version, never a permissive fallback. A remote plugin may preserve its upstream tool names rather than take the `<plugin>_` prefix; a name that collides with an existing capability or skill fails the whole registration instead of being renamed or dropped. The credential never reaches the process tree: the server spec carries an opaque reference the session resolves inside its own initialization. A remote server that announces `notifications/tools/list_changed` is re-discovered in place, so a tool the upstream adds or withdraws appears or disappears on the next turn with no daemon restart; calls arriving while a proxy is suspended mid-reconnect are held and drained on resume, and refused only once the connection is terminally down. A source whose discovery has no callback wired refuses the watch outright rather than registering one that could never fire.

Remote status vocabulary — the static install/config/auth ladder first, then the live client: `needs_secret` (no token stored), `needs_workspace` (the token works but no workspace is selected), `insufficient_credential_scope` (the selected profile needs a read/write token and the stored one is read-only), `invalid_remote_config` (profile/workspace/signed runtime is invalid — do not start), `connecting`, `ready` (authenticated **and** the entire signed contract matched — the only state in which its tools exist), `remote_unreachable` (DNS/TLS/transport failed after the bounded startup attempts), `reauthorization_required` (the token was rejected or revoked — replace it), `upstream_contract_mismatch` (a required tool vanished or a descriptor changed — do not call its tools), `capability_conflict` (a name collides locally), `remote_security_blocked` (endpoint/DNS/redirect/TLS policy refused it), `remote_protocol_error` (invalid negotiated version or session state — reconnect or upgrade). "Startable" and "callable" are deliberately different questions: installed + enabled + compatible + credentialed is what starts the client, and only the completed contract check makes it `ready`. That live table lives in the daemon's memory alone, so a one-shot CLI asks the daemon for it — `fermix doctor`'s `plugins` row reports the static install/config/auth result plus "runtime status unavailable — daemon not running" when there is no daemon, and never infers `ready` from a table it cannot see. A refusal is described the same way wherever it appears — the daemon log, the `plugins` row, and the setup UI all render one classified answer as `status/detail (capability)`, for example `upstream_contract_mismatch/missing_tool (<plugin>_<tool>)`: the class distinguishes a tool the upstream withdrew from one it reshaped, and the capability names which one, so the question a contract mismatch actually raises is answered on the surface the operator is already looking at. The capability is named only when it is a name Fermix selected from that plugin's own signed manifest; a peer-supplied name and anything derived from a crash are reported by class alone.

A remote plugin can be bound to one upstream workspace: once its token is saved, setup runs a discovery call the agent never sees, the operator picks exactly one workspace, every later call is pinned to it, and a model-supplied workspace argument is rejected before any network I/O. Its signed manifest can also define access profiles (for example a read-only one and a write one) with one signed default; the operator picks the profile with the workspace, and a profile the stored token is not scoped for reads as `insufficient_credential_scope` instead of falling back to a narrower one.

Operator CLI: `fermix plugins list | catalog | installed | doctor` inspect; `enable | disable | reload` toggle; `install | upgrade | pin | uninstall | gc` manage the local store under `~/.fermix/plugins/` (install verifies the tarball signature and re-validates the manifest, so a plugin that installs always loads; `enable` auto-installs a missing catalog plugin; bundled plugins can't be uninstalled — disable instead); `auth login|reauthorize|refresh|logout NAME` manages OAuth plugins (tokens/scopes in `~/.fermix/auth.json`); `auth logout NAME` deletes the stored grant, then has a running daemon drop that account's live token and delete its helper's token file at once, so the plugin's tools answer "not connected" from the next call (the plugin list the agent sees catches up at the daemon's next plugin reload), and a daemon that cannot let go fails the verb with a sentence saying the grant is already gone (running it again, with the grant already gone, still reaches the daemon); `auth set NAME` / `auth clear NAME` store/forget the static credential an **api_key** plugin authenticates with (keychained, never plaintext config). **A secret is never passed as an argument** — `auth set NAME` prompts on the terminal without echoing, and `... | auth set NAME --stdin` reads it from a pipe for scripts; the old positional form exits non-zero and tells the operator to rotate the value they just put in their shell history. `auth clear NAME` is a truthful *forget local credential*: it deletes the OS-keychain item first and only then drops the config reference, so a failed deletion errors with the reference intact instead of orphaning a credential — it does **not** revoke anything upstream, which the user must do with the provider. It is also distinct from `disable`, which stops the plugin but keeps the credential for a later re-enable; `config set NAME KEY VALUE` sets manifest-declared per-plugin values (`[fermix_core.plugins.<name>]`, UPPER_SNAKE, injected into an mcp plugin's process env, surviving disable→enable). Each declared setting has a kind — **text** (a free-text field, the default when a manifest declares none) or **boolean** (a switch that takes only `true` or `false`, refusing anything else, and which both the setup page and the macOS app draw as a toggle); boolean is the kind a tool's `requires_setting` consent gate is meant for, since that gate advertises the tool only while its setting reads exactly `true`, so an unset or `false` switch leaves the tool hidden. An **mcp** plugin gates its whole local helper *process* the same way — with the switch off there is simply no child running, though the plugin stays `ready` for its other tools — and when such a helper authenticates as the owner's OAuth account, the daemon (never the helper) keeps the current access token in a private file under `~/.fermix/plugins/run/` and passes only its path in `FERMIX_PLUGIN_TOKEN_FILE`, rewriting it on every refresh and deleting it the moment the switch goes off or the plugin is disabled or signed out, so a plugin process never holds a refresh token or sees another integration's credentials. The web setup Plugins page mirrors the catalog (install verifies sha256 + cosign; OAuth client id/secret entered via a per-provider-group modal). Distribution ops emit `[:fermix, :plugin, :dist]` telemetry; credential ops emit `[:fermix, :plugin, :auth]`, which becomes one `plugin_auth` trace row per op, with its failure class, when the daemon runs the op (the setup page or the macOS app) — the `auth` CLI verbs run without the daemon's trace and leave none.

For plugin authors, `[fermix_core.plugins] dev_local = "<path>"` points at a directory whose immediate subdirectories are plugin dirs (for a fermix-plugins checkout, its `plugins/` directory). Those load into the registry like installed ones — full manifest validation, skills loaded in place — with no install or tarball step. A missing/unreadable path or a bad manifest fails plugin loading loud, and a dev_local name may not collide with a bundled or installed plugin.
