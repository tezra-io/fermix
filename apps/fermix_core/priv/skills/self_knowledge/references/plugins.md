# Plugins

Plugins are connected integrations that own a surface (an API, a vault) and register their own tools. Bundled and always present: Gmail, Google Calendar and Google Drive (Google OAuth). Every other plugin installs from a signed catalog built into the binary; new and updated plugins arrive with Fermix updates. Which ones exist and are enabled is runtime state: read the `## Plugins` section of the runtime prompt, never assume.

## What the agent sees

- A ready plugin lists its tool names under `## Plugins`: call them directly (its skill, via `skill_view`, documents arguments; deferred schemas resolve via `tool_describe`/`tool_search`) and prefer them over browser, web or shell for that surface.
- An enabled plugin that is not ready shows `status=` and a fix instead of vanishing: `needs_auth`, `needs_client_config`, `needs_secret`, `needs_config`, `needs_workspace`, `reauthorization_required`, `wrong_region`, `missing_host_runtime`, `not_installed`, `incompatible`. It is not connected: offer to connect it, never scrape around it.
- The fix text names CLI commands. For a Mac app user translate it to the app: Settings > Integrations > the plugin's row, whose leading button is the fix (**Install…**, **Turn on**, **Sign in**, **Sign in again**, **Add token…**, **Replace the token**, **Set up the sign-in client**). On Linux or dev: browser setup's Plugins page, or the `fermix plugins` verbs below.
- Enable, disable and sign-out reach the agent on its next turn, with no restart. A disabled plugin's tool refuses with an enable hint.
- A connected plugin registers all its tools; one whose scope was not granted answers "reauthorize" rather than disappearing.

## Credential failures

- **HTTP-rail errors name their fix.** An OAuth plugin's 401 says it needs reconnection (`fermix plugins auth reauthorize <plugin>`), an api_key plugin's 401 points at `fermix plugins auth set <plugin>`, a never-connected one at `fermix plugins auth login <plugin>`. Relay that fix (as the app's button for a Mac user) instead of retrying. Google 403s are classified (file permission, organizer-only, rate limit).
- **Lapsed OAuth** (a refresh token that expired from disuse) shows **Reconnect needed** in setup and a warning in `fermix doctor`'s `auth tokens` row.
- **A refused sign-in client** is not an expired sign-in, and signing in again cannot fix it. The owner's own client (ID + secret) was rejected, typically because the secret was regenerated in the provider's console or saved into another Fermix home. Vendor words: X 401 `unauthorized_client` "Missing valid authorization header", Google, Notion or Tesla `invalid_client`, GitHub `incorrect_client_credentials`, Slack `invalid_client_id`/`bad_client_secret`. The plugin reads `reauthorization_required`; the Mac row leads with **Set up the sign-in client** (keeping **Sign in again**), browser setup shows **Update client**. Fix: copy the client ID and secret from the provider's console into that sign-in client, then sign in again. Neither `fermix auth login` nor a restart helps before that. The daemon's log and `plugin_auth` trace keep the vendor's code when the app or setup page ran the sign-in; a CLI `fermix plugins auth` verb prints to the terminal and leaves no trace row.

## Rails and auth

- **http**: declarative templates run inside Fermix. https only; loopback, private and metadata addresses are refused at runtime; a redirect is refused with a typed error naming its `Location`.
- **mcp, local**: a process the daemon supervises; its tools register as `<plugin>_<tool>`. Install probes the declared runtime (Node, Python, or a vendored binary) and refuses a missing or too-old one with `missing_host_runtime`.
- **mcp, remote (hosted)**: an HTTPS session to the vendor's own MCP server; the plugin ships no code, only a signed manifest and a skill (below).
- **OAuth** plugins use `[fermix_core.oauth.<provider>]` (`client_id`, `client_secret` kept in the keychain, optional `redirect_host`/`redirect_port`); `needs_auth` until signed in. Tesla adds `region` (no default: `na` for North America and Asia-Pacific, `eu` for Europe, Middle East and Africa; China is not offered) and `redirect_uri` (default: the hosted bounce page that forwards to the local listener). A client without a valid region is refused on save and at sign-in. After sign-in Fermix asks Tesla for the account's region: on a mismatch the plugin reads `wrong_region`, the row names the account's region and leads with **Set up the sign-in client**, and no tool runs until the region is changed and the owner signs in again.
- **api_key** plugins take a static token (`fermix plugins auth set NAME`, or the app's **Add token…**); `needs_secret` until set; sent with the manifest's scheme (`Bearer` by default, `Bot` for Discord).
- Each Integrations row carries a consent sentence naming where the plugin's code runs (its vendor's servers, this Mac as a separate process, or inside Fermix) and what leaves the Mac.

## Access-sensitive commands

A plugin manifest may mark a local http or mcp tool that changes something (`"read_only": false`) with `"access_sensitive": true` (exactly `true`); read-only tools and remote MCP tools cannot carry it. Marks come from the installed plugin release, not from Fermix. The Tesla plugin marks `tesla_unlock_doors`, `tesla_set_sentry_mode`, `tesla_actuate_trunk` and `tesla_vent_windows`. An install still on an older Tesla release (now withdrawn from the catalog) marks none, so those four never wait for a confirmation until the plugin is updated: `fermix plugins upgrade tesla` (Linux, standalone), which browser setup's Plugins card names beside "Version … was yanked". The Mac app shows no such flag and has no plugin update control yet; say so rather than invent one. Never promise a confirmation Fermix will not ask for.

One daemon gate decides every call to a marked tool, on every path that runs tools (chat and both voice engines):
- **The owner's direct request runs at once**: an attended owner turn that has read nothing from outside is the consent.
- **After outside content, one confirmation.** Outside content: web and browser pages, computer use, mail and every other plugin, games, operator MCP servers, and reports relaying what someone else read (a `subagents` worker, `skill_run`, a coding run, `get_job_run`/`list_job_runs`). The target plugin's own reads (Tesla's vehicle list, status, wake) do not count. A text turn counts what it read before the call; a call batched with a read does not see it. On a Realtime call the need lasts the rest of the call (a shared screen counts); on GPT-Live it is per task.
- **From a Buzz channel, always one confirmation**, even for the owner, with the prompt sent to the owner's own chat, never into the channel. An editor client (Zed) follows the ordinary rule.
- **Where the owner confirms**: one tap on Telegram and Discord; `/confirm TOKEN` on Slack and WhatsApp; an approve/deny card on the companion socket and the mobile channel (neither app is released yet); `fermix ask "/confirm TOKEN"` on the CLI; a spoken yes on a voice call. Fermix cannot receive Signal messages, so a prompt sent to Signal cannot be answered there. From ACP the prompt goes to the owner's Telegram, Signal or WhatsApp DM (one that lands on Signal cannot be answered), and is refused with none. A prompt expires in 60 s; `/deny` discards it; asking again while it waits sends no second prompt.
- **While it waits the asking turn does nothing else**: every other call that turn makes is refused ("already waiting"); on a Realtime call no tool started after the hold runs until the owner answers.
- **Fermix runs exactly the confirmed call**, once, and replies with the outcome (not added to history). The model never sees the token. A plugin that was disabled, stopped marking the command, or signs in under a different profile fails the confirmation with a sentence.
- **Never**: delegated workers (`subagents`, `/ultra`, `skill_run`), `/background` runs, agent-started or detached CLI turns, coding-run and reminder follow-ups, inbound MCP clients, guests.
- **Scheduled jobs** run one only when the job's `allowed_tools` names it; creating, changing, resuming or running-now such a job needs a clean, direct request.
- Every held or refused call is still one tool call in traces, with `access_gate` naming the outcome.

## Remote (hosted) MCP plugins

The signed manifest is an enforcement boundary: the endpoint, the exact tool names and each tool's descriptor hash are checked at connect. An upstream tool the manifest does not declare is dropped; one missing or changed descriptor registers none of that profile's tools (fix: a reviewed, re-signed plugin version). A remote plugin may keep upstream tool names; a name collision fails the whole registration. The credential never reaches a process. A server that announces tool-list changes is re-discovered in place, with no restart.

Statuses: `needs_secret`, `needs_workspace`, `insufficient_credential_scope` (the profile needs a write token, the stored one is read-only), `invalid_remote_config`, `connecting`, `ready` (only state in which tools exist), `remote_unreachable`, `reauthorization_required` (token rejected; replace it), `upstream_contract_mismatch` (a tool vanished or changed; do not call it), `capability_conflict`, `remote_security_blocked`, `remote_protocol_error`. The live status is in daemon memory only: `fermix doctor`'s `plugins` row says "runtime status unavailable — daemon not running" rather than guess. Refusals read `status/detail (capability)` everywhere, e.g. `upstream_contract_mismatch/missing_tool (<plugin>_<tool>)`.

A remote plugin can be bound to one workspace: after the token is saved, setup discovers workspaces, the operator picks one, and every call is pinned to it (a model-supplied workspace argument is rejected). Signed access profiles (for example read-only and write) are chosen with the workspace.

## Operator CLI (Linux, dev, or a standalone binary)

- Inspect: `fermix plugins list | catalog | installed | doctor`. `catalog` prints name, auth and category; `installed` prints each installed version.
- Toggle: `enable | disable | reload`. `enable` installs a missing catalog plugin.
- Manage the store under `~/.fermix/plugins/`: `install | upgrade | pin | uninstall | gc`. Install verifies sha256 and the cosign signature and re-validates the manifest. `upgrade NAME` installs the catalog's newest release. Bundled plugins cannot be uninstalled; disable them.
- OAuth: `auth login | reauthorize | refresh | logout NAME` (tokens in `~/.fermix/auth.json`). Only `logout` reaches a running daemon: it drops the live token and the helper's token file at once (a daemon that cannot let go fails the verb, saying the grant is already gone). The other `auth` verbs (`login`, `reauthorize`, `set`, `clear`) change only the stored credential: restart the daemon afterwards (on a Mac, **Restart Fermix…**).
- api_key: `auth set NAME` prompts without echo (`... | auth set NAME --stdin` for scripts); a secret passed as an argument is refused with advice to rotate it. `auth clear NAME` deletes the keychain item, then the config reference. Neither revokes anything upstream, and the app's **Disconnect** is local too; revoking is done with the provider. `disable` stops a plugin but keeps its credential.
- Settings: `config set NAME KEY VALUE` writes manifest-declared values under `[fermix_core.plugins.<name>]` (UPPER_SNAKE, passed to an mcp plugin's process env, kept across disable/enable). A setting is **text** or **boolean** (a switch; `true`/`false` only). A tool with `requires_setting` is advertised only while that switch is exactly `true`; an mcp helper gated the same way does not run at all while off. A helper that acts as the owner's OAuth account gets only a path to a private token file (`FERMIX_PLUGIN_TOKEN_FILE`, under `~/.fermix/plugins/run/`), rewritten on refresh and deleted when the switch, the plugin or the sign-in goes away.

**Retired plugins.** When a build stops offering a plugin, its `enabled` entry, `[fermix_core.plugins.<name>]` section and `plugin_secrets` entry are dropped from the config Fermix reads (named once in the log); the stored credential is left for the owner to forget and revoke.

**Plugin authors.** `[fermix_core.plugins] dev_local = "<path>"` loads each subdirectory as a plugin with full manifest validation and no install step; a bad path or manifest fails loud, and a name may not collide with a bundled or installed plugin.
