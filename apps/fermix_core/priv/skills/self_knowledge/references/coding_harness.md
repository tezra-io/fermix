# Coding harness

Repo coding work — reviewing PRs, fixing bugs, implementing features, drafting designs inside a codebase — is delegated to a **coding harness run** rather than edited file-by-file. `codex_run` and `claude_code_run` launch the operator's own Codex CLI / Claude Code CLI (`codex exec` / `claude -p`) inside a target repository, speaking each vendor's native streaming protocol (no meta-harness normalization). Fermix is the durable control plane around them: it applies authorization, the workspace sandbox boundary, env isolation, and lifetime limits at the launch boundary, persists the run before any process starts, observes typed vendor events, and reconciles runs across daemon restarts. The feature is **enabled by default** — `[fermix_core.harness] enabled` is the master gate (set it `false` to turn the whole harness off) — but a run tool advertises only when its vendor CLI was detected at boot, so with no CLI installed nothing is offered; the vendor CLIs own their own logins (`~/.codex`, `~/.claude`) — Fermix reads that auth state, never writes it. **Runs are background-only**: the launch returns a run id immediately and the turn ends — there is no wait window and polling a run's status is never the right move. When a **chat-origin** run finishes, Fermix re-enters that conversation on its own with a system-voiced notice carrying the outcome, and the agent takes one turn to either report it or continue the work it was for (launch the next step, screenshot the result). That automatic follow-up is chain-bounded: a run launched from a continuation turn inherits depth+1, and past the depth cap the outcome is delivered as a plain message that says automatic follow-up stopped. A **scheduled/cron** run has no conversation to re-enter, so it keeps plain durable delivery. An **owner halt** never continues either — a run stopped by `/stop`, `cancel_coding_run`, or stop-tracking reports its outcome as a plain message, so a follow-up turn can never relaunch the work the kill switch just ended. **Delivery is durable and at-least-once**: every run becomes terminal, and its terminal message becomes either delivered or durably **dead-lettered and surfaced** — because a crash right after a successful send can duplicate a message, every delivery carries the run id for human dedup. `list_coding_runs` shows runs and their delivery state (dead-letter runs grouped so they get raised to the owner), `get_coding_run` returns one run in full (status, diagnostics tail, usage, artifact paths, delivery), and `cancel_coding_run` stops an active run (owner intent → `cancelled`); a failed/interrupted run's message carries the vendor session id and an exact resume command unless the run was ephemeral/non-resumable. Each run spools its prompt, event stream, and result under a per-run artifacts directory beneath `FERMIX_HOME`; the store is quota-bounded and swept on a retention window. **Authorization is an execute-time gate on every harness tool**: an attended operator turn (a live reply surface, sub-agent depth 0) passes, and a scheduled job passes only when the harness tool is in that job's explicit `allowed_tools` — a worker sub-agent, a guest, or an unattended cron with no allowlist is refused. **First use also needs one-time consent** (separate from `enabled`): `[fermix_core.harness] approved` defaults `false`, and the owner grants it as a **setup decision** — the Coding Agents card in web setup, the wizard step, or that config key. There is no mid-conversation consent prompt and Fermix never grants it itself. Consent also gates *visibility*: on an unapproved machine no run tool is advertised and no delegation steering renders, so Fermix quietly does the repo work with its own file/shell tools (main-agent coding is permitted, merely not preferred — the harness's absence never blocks coding, and nothing is asked of the owner). The tools stay dispatchable by name, where the refusal names the setup toggle and tells the caller to proceed directly. A scheduled/cron run on an unapproved machine is blocked (`blocked/:consent_required`) and the owner hears the same guidance. `/stop` cancels active runs (scheduled jobs and voice are unaffected; harness runs now are). When `default_vendor` is set and both CLIs are present, the runtime prompt steers the unspecified-vendor case toward it — a steer, not a router.

There is also a **cloud rail**, but it is **off in this release** and its tools are not offered or dispatchable: `[fermix_core.harness] cloud_enabled` defaults `false`, so `codex_cloud_run` and `stop_tracking_coding_run` do not seed until an operator sets `cloud_enabled = true` (the cloud lifecycle code stays in the tree, simply never entered). When enabled, `codex_cloud_run` submits a task to a pre-configured Codex cloud environment (`codex cloud exec` against an `env_id`, with optional `branch`/`attempts`) instead of a local checkout — nothing on the machine is touched, and the query rides one argument (no file spillover, so an oversized query is refused rather than truncated). Because that surface has no completion push and no cancel, Fermix tracks the task by **bounded polling** (`codex cloud status`, persisted `next_poll_at`/`poll_deadline` that survive restarts); on the deadline it finalizes `blocked/:poll_deadline` with the task URL. `cancel_coding_run` on a cloud run is refused (`vendor_cancel_unsupported`) and polling continues — to abandon a cloud run use `stop_tracking_coding_run`, which stops Fermix's tracking and delivers the task URL but never claims the vendor task itself stopped (it keeps running on ChatGPT). `/stop` does not touch cloud runs. Terminal cloud messages carry the vendor status, the diff summary, the task URL, and a `codex cloud diff <id>` hint; if the daemon dies mid-submit before the task id is known, restart reconciliation finalizes the run `blocked/:submission_outcome_unknown` with the query/env/timestamp and a `codex cloud list` pointer, and never auto-resubmits.
