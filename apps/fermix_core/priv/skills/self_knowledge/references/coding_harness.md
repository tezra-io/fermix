# Coding harness

Repo coding work (reviewing PRs, fixing bugs, implementing features, drafting designs inside a codebase) is delegated to a **coding harness run** rather than edited file by file, unless the owner asks for it to be done directly. `codex_run` and `claude_code_run` launch the operator's own Codex CLI or Claude Code CLI (`codex exec` / `claude -p`) inside the target repository, each on its vendor's native streaming protocol. Fermix is the durable control plane around them: authorization, the workspace sandbox, env isolation and lifetime limits at launch; the run is persisted before any process starts and reconciled across daemon restarts.

## Turning it on

- `[fermix_core.harness] enabled` (default `true`) is the master switch.
- **First use needs the owner's consent**, `[fermix_core.harness] approved` (default `false`), granted as a setup decision: Mac Settings > Coding agents > **Allow coding agents to run on this Mac**; browser setup's Coding Agents tab; or that key. A restart applies it. Fermix never grants it itself and never asks mid-conversation.
- Until consent, **no harness tool is advertised at all** (neither the run tools nor `list_coding_runs`/`get_coding_run`/`cancel_coding_run`) and no delegation steering renders: the agent does repo work with its own file and shell tools, and asks nothing of the owner. Called by name, a harness tool refuses, naming the setting. A scheduled run on an unapproved machine is `blocked/:consent_required` and the owner is told how to consent.
- Each run tool is advertised only when its vendor CLI was detected at boot. The Mac Coding agents pane shows each CLI's install, version and sign-in state.
- **Preferred tool** (Mac) / `default_vendor`: when both CLIs are present, the unspecified-vendor case is steered to it; when set, only that vendor's run tool is advertised.
- The vendor CLIs own their logins (`~/.codex`, `~/.claude`); Fermix reads that state and never writes it.

## Posture

Omit `sandbox` (codex) or `permission_mode` (claude) and Fermix passes no posture flag: the run inherits what the vendor CLI resolves from the operator's `~/.codex/config.toml` / `~/.claude/settings.json` and, in a trusted repo, its `.codex/config.toml` / `.claude/settings.json` / `.claude/settings.local.json`. That is why runs are autonomous by default. A confining level can be chosen per run (`workspace-write` writes freely inside the admitted directories; claude's `auto` keeps the sandbox with least friction). Codex `danger-full-access` and claude `--dangerously-skip-permissions` / `bypassPermissions` are refused at the tool boundary, under any name: the vendor sandbox is what keeps the child inside the directories Fermix admitted. An operator who wants unconfined runs sets it in their own vendor config.

**Repo-local vendor config is watched.** Fermix fingerprints the files coding agents obey on their own (`.claude/settings.json`, `.claude/settings.local.json`, `.mcp.json`, `.codex/config.toml`, the `.agents/` tree, `.vscode/tasks.json`, `.vscode/settings.json`) in the repo root and every directory down to the run's working directory, at each run's start and end. A run that changed any of them names them in its outcome (an `.agents/` change by directory and file count); name them to the owner, because a coding agent they start there runs them too. The next coding run in that repo waits for one acknowledgement: on a chat surface with `/confirm` the launch becomes a one-tap approval and resumes after `/confirm`; a scheduled job is `blocked/:vendor_config_changed`; ACP gets the same refusal. There is no separate acknowledge command. Reverting or committing the file clears the wait. Claude Code children are also denied edits under `.codex/` and `.agents/`; make those edits with ordinary file tools.

## Runs and delivery

- **Background only**: the launch returns a run id and the turn ends. Never poll.
- When a **chat-origin** run finishes, Fermix re-enters that conversation with a system notice carrying the outcome, and the agent takes one turn to report or continue. A **failed** run's notice leads with the vendor CLI's own error text (such as a not-signed-in message); check the working tree (a killed run may leave partial changes), then rerun if the cause looks transient or do the work directly, and tell the owner what failed and what it needs. Follow-ups are depth-bounded; past the cap the outcome arrives as a plain message.
- A **scheduled** run has no conversation to re-enter and delivers a plain message. An **owner halt** (`/stop`, `cancel_coding_run`, stop-tracking) also reports plainly, so nothing relaunches what the owner stopped.
- Delivery is durable and at least once: every run ends, and its message is delivered or dead-lettered and surfaced. Each message carries the run id for dedup.
- `list_coding_runs` lists runs and delivery state (dead letters grouped); `get_coding_run` returns one run (status, diagnostics tail, a bounded `result_tail`, usage, artifact paths, delivery); `cancel_coding_run` stops an active run (`cancelled`). A failed or interrupted run's message carries the vendor session id and an exact resume command unless non-resumable. An `interrupted` run may have finished just before a restart: read its `result_tail` and the working tree before resuming.
- Each run spools prompt, events and result under a quota-bounded, retention-swept artifacts directory in `FERMIX_HOME`.
- **Authorization** is checked at execute time on every harness tool: an attended operator turn passes; a scheduled job passes only when the tool is in its `allowed_tools`; workers, guests and unattended runs without that allowlist are refused. `/stop` cancels active local runs; scheduled jobs and voice have no harness tools to stop.

## Cloud rail (off by default)

`[fermix_core.harness] cloud_enabled = true` seeds `codex_cloud_run` and `stop_tracking_coding_run`; off, they are neither offered nor dispatchable. `codex_cloud_run` submits to a pre-configured Codex cloud environment (`codex cloud exec`, an `env_id`, optional `branch`/`attempts`); nothing on the machine is touched and an oversized query is refused, not truncated. Fermix tracks the task by bounded polling (`codex cloud status`, surviving restarts) and on the deadline ends it `blocked/:poll_deadline` with the task URL. `cancel_coding_run` on a cloud run is refused (`vendor_cancel_unsupported`); `stop_tracking_coding_run` stops tracking and delivers the URL, but the task keeps running on ChatGPT. `/stop` does not touch cloud runs. Terminal messages carry vendor status, diff summary, task URL and a `codex cloud diff <id>` hint. A daemon that died mid-submit ends the run `blocked/:submission_outcome_unknown` with a `codex cloud list` pointer and never resubmits.
