# Jobs — scheduled agent runs

`schedule_job` creates durable work that runs later and must reason or act; a date that only notifies the owner is an event instead (`events_reminders`).

## Creating

| field | required | default | notes |
| --- | --- | --- | --- |
| `name` | yes | — | non-empty; slugged into the id |
| `schedule` | yes | — | see Schedule grammar |
| `task` | yes | — | non-empty |
| `timezone` | no | the owner's zone | IANA zone; unknown is rejected; UTC only when no owner zone is configured |
| `description` | no | none | for the source catalog |
| `expires_at` | no | none | ISO8601 + offset, future |
| `delivery_mode` | no | config default, else `none` | `none`/`origin`/`channel`/`local` |
| `delivery_target` | no | none | `platform` plus one of `chat_id`, `channel_id`, `recipient`, `target`, `reply_target`; a chat, never this computer (`computer` takes reminders only, so it is refused here, and a configured default target of `computer` serves reminders alone) |
| `allowed_tools` | no | no narrowing | subset of the caller's visible tools |
| `skill_name` | no | none | must name a loaded skill |
| `provider` + `model` | no | cron route | both or neither; provider known |
| `timeout_seconds` | no | 30 minutes | positive integer |
| `inactivity_timeout_seconds` | no | unarmed | positive integer |

No other parameters exist: the iteration cap (100), isolation, the `job:<id>` memory scope, the `[SILENT]` marker and `capability_policy` are fixed.

A job gets at most the tools of the run that creates or changes it, when that run is limited in what it is authorized for: it was given its own `allowed_tools` (a job's run, a skill's worker), its `policy` lacks a class its trust grants, or it runs at guest under the owner (a plugin skill's worker). Its tools are then the ones its trust, `policy` and `allowed_tools` admit. The owner's own turns are never limited: what a voice call or an ACP session leaves out to fit the channel does not count.

- **Creating:** from a limited run, `allowed_tools` naming any other tool is refused, and leaving it out (or `[]`) stores the tools the run can call as the list; the result's `note` says so, and names any tool the run was granted that is unavailable now (a disabled plugin's) and so left out. The stored list is fixed at creation: `update_job` cannot change it.
- **Changing:** a limited run's `update_job` is refused unless the job's tools after the change, its list narrowed by its skill's (the newly bound one when `skill_name` is given), are all the run's own, a tool unavailable now counting when the run was granted it; a job whose list and skill name no tools is bounded only by its trust, so a limited run cannot change it. A run at guest trust (a plugin skill's worker under the owner, or a job bound to a plugin skill) cannot change a job set up at operator trust at all. A watcher's task job cannot be bound to a skill that leaves `cue_history` off its runs (a plugin skill, or one asking only for classes other than `read_only`), and a task already bound to one fails its runs saying so.

**Access-sensitive tools** (a plugin tool its manifest marks `access_sensitive`, such as a car unlock) are reached by a scheduled run only when the job's `allowed_tools` names them; an empty allowlist does not cover them, and a run that calls one anyway gets a refusal (a tool failure in that run). `schedule_job` naming one, and `update_job`, `resume_job` or `run_job_now` on a job that names one, are refused unless the request is the owner's own clean, direct ask (their chat, app or voice, having read nothing from outside this turn, not a delegated worker); jobs that already name one keep running.

**Website sign-ins.** A run signs in to a website with a login the owner saved in the Fermix Mac app (the `browser` tool's `sign_in`) only when the job's `allowed_tools` names `browser`, and then asks no one: naming it on the job was the owner's yes. An empty allowlist does not cover it, a guest's job never signs in, and a page with no saved login is answered with where the owner adds one. Setting up the owner's job that names `browser` (`schedule_job`), and `update_job`, `resume_job` or `run_job_now` on one, are refused unless the request is the owner's own attended turn (their chat, app or voice, whatever the turn read) or comes from a run of a job that itself names `browser`; never a delegated worker, a guest-trust run on the owner's job, a cue run, a background run, a run of a job that does not name it, or a shared channel. A guest's own job is set up and started as before. A run that inherits its own tools into a job (`allowed_tools` left out by a narrowed run) hands on `browser` too, so it names a list without it for a job that does not browse. Jobs that already name `browser` sign in from their next run; a retry or an Auto Heal rerun of one runs as it is, and a change Auto Heal proposes is applied only when the owner approves its card.

`task` is the run's entire brief. It cannot see the conversation that created it, so bake in every value it needs (location, account, recipient) and keep timing in `schedule`/`expires_at`. Ask for a missing detail rather than inventing one; revise with `update_job` rather than recreating.

## Schedule grammar

Exactly one of three forms. Free-form English ("daily at 8am") is rejected.

- Interval: `every N minutes|hours|days`, `N` positive. First run is N from creation.
- Cron: `minute hour day-of-month month day-of-week`. Fields take `*`, a value, a list (`1,15`), a range (`9-17`), or a step (`*/15`, `8-18/4`). Weekday `0` and `7` are Sunday. Day-of-month and day-of-week must both match. Malformed or out-of-range fields are rejected.
- One-off: one ISO8601 instant with an offset, `2035-09-10T16:00:00Z` or `2035-09-10T12:00:00-04:00`. No offset is rejected. A past instant fires on the next tick.

`timezone` affects cron only: `0 9 * * 1` fires 09:00 in the job's zone and tracks DST; without `timezone` that is the owner's zone. Interval and one-off are absolute instants; write a one-off or `expires_at` as ISO 8601 with the owner's UTC offset, which the current-date note states. Pass `timezone` only when the owner named another zone. Each run's message opens with the current time to the minute.

## Delivery

`none` sends nothing, `local` records without a channel send, `origin` replies into the creating conversation, `channel` sends to an explicit `delivery_target`. Delivery resolves once at creation and is snapshotted, so later config edits never retarget a job: an explicit mode wins; a `delivery_target` alone implies `channel`; neither falls to `[fermix_core.jobs] default_delivery_mode`/`default_delivery_target`, else `none`. A job the owner expects to hear from needs an explicit mode. The two defaults are `config.toml` keys only; no settings pane or setup tab writes them.

`channel` with no target and no configured default is rejected, as is a target missing `platform` or a destination key. `origin` derives platform, chat id and thread from the creating chat and is rejected without one; an ACP session and a private GPT-Live call refuse it outright (each one's conversation ends with it), so schedule to an explicit channel there. A task of a call in the chat reports back into the Mac chat. From the Mac app's chat it delivers into the companion timeline, written even while the app is closed and caught up when it reconnects (`companion` reference).

A final response of exactly `[SILENT]` delivers nothing and stores no run summary; the run prompt tells it to answer that way when there is nothing new. Under `origin`/`channel` a run whose tools include `send_attachment` or `generate_image` can also send files (16 media sends max, always to the job's own destination — `images` reference), and its prompt says which it has; under `local`/`none` they refuse first.

## Runs

Each run is a fresh bounded loop with the job prompt, the current date and the task; no chat history.

Trust is stamped from the creating run and never widens: the lower of its person's trust and the run's own, so a plugin skill's worker creates guest jobs. A context carrying no trust cannot create a job. `skill_name` runs the job inside that skill's prompt, never wider than the job: its tools intersected with the job's, the classes the skill declares kept to the job's own grant, at the lower of the job's trust and the skill's. A job bound to a plugin skill therefore runs at guest on what `skill_run` of that skill offers, even when the owner created it: guest tools plus that plugin's own tools within the job's grant (none for a guest job). Only a guest job's grant can leave a skill no class; such a run fails with a sentence saying so (set the job up again from the owner's own turn, bind another skill, or drop `skill_name`). A tool the job's own `allowed_tools` names is one it needs: a run whose trust, or whose skill's trust or classes, leave one out, or that no capability carries now (a plugin that is off), fails before the model is asked, with a sentence naming the tools and why, never running without them; a watcher's task is exempt, since its runs get fewer tools by design. `schedule_job` and `update_job` refuse to bind a skill that would leave one of the job's own tools off its runs. Unpinned runs resolve `[fermix_core.routing] cron_*`, else the primary/fallback chain, at run time.

`timeout_seconds` bounds the run's wall clock and `inactivity_timeout_seconds` fails a loop that stops progressing. `update_job` changes `timeout_seconds` (a positive whole number of seconds, at most 30 minutes for a watcher's job); `inactivity_timeout_seconds` is creation-only. `get_job_run` echoes what a run executed under.

## Lifecycle

A recurring run more than an hour overdue (a fixed window, not a setting) is skipped rather than fired at the wrong wall-clock, and its schedule advances; a one-off never goes stale and runs late instead. `expires_at` marks the job expired.

A schedule or timezone that no longer parses is terminal: the job moves to `disabled` with the reason in `last_error` and is never retried. Fix it with `update_job`, then `resume_job`. The Scheduler's own moves (a stale skip, an expiry, a disable) change a job only while it is still as the Scheduler read it, so a pause, edit or removal made at the same moment stands.

At most four scheduled runs execute at once; a due job over the cap stays `scheduled` until a later tick claims a slot, and `run_job_now` is uncapped. A transient infrastructure failure re-runs the whole loop with bounded backoff only while no tool has executed; afterwards the run fails loudly rather than replaying side effects.

A run of an interval or cron job that failed before it did anything, before its first tool, on a failure waiting can clear (its provider's rate limit, exhausted account, outage, timeout or lost connection, no route to a model, or the run dying with no runner left) is run again quietly, up to three times: 30 seconds after the first such failure in a row, then 2 minutes, then 10 minutes. The run is tagged `retry` (`trigger: "retry"` in `list_job_runs` and `get_job_run`) and the job's `next_run_at` does not move; a retry that would come at or after the next scheduled run is that run. A retried failure sends nothing and leaves the job's memory source as it was, while its run and `last_status` still say it failed. The fourth such failure in a row, a failure after a tool ran, a sign-in failure, the time limit and every other failure are not retried. Pausing, resuming, editing or running the job now clears a pending retry, a retry more than an hour overdue is dropped, and a one-off, a watcher's task and a follow-up are never retried.

A failure of the owner's job that is not retried goes to a heal (**Auto Heal**), and nothing is sent where the job delivers (its run's delivery reads `skipped`, or `none` after a run that ended with nothing left running it). There is one heal per job, or one per provider when the failure is the provider's (a rate limit, an exhausted account, a rejected sign-in or key, an outage, a timeout or lost connection, or no route to a model): every job failing on that provider shares it. Fermix tells the owner once, in their own inbox (the configured default target; else the Fermix app while a phone is paired; else the owner's chat on Telegram, Signal, WhatsApp or iMessage; else, with none of those, the Fermix app's chat on an install with the app or on an Always On server with a computer linked to it, connected or not), chosen once when the heal opens and kept, in a message it writes from its own facts: the job's name, what failed and when, how often lately, and when it runs next or that it is paused; for a provider, which one, its own words, and which jobs since when. What failed is Fermix's own plain sentence for the kind of failure (a time limit in minutes and the tool still running, a missing skill by name, a provider by name), stated, and the same sentence is the run's `error` and the job's `last_error`, except after a run that ended with nothing left running it (Fermix restarted, or the run's process died): those two keep the line the engine wrote then (`reaped: no live runner …` or `runner crashed: …`) while the message states Fermix's sentence; only words someone else wrote are quoted and said to be theirs (a provider's, a tool's, or the text of an error Fermix has no sentence for). In an owner chat, or in the Fermix app's chat, the message is kept in that conversation's history, so the owner can reply to it, without the note from Fermix's look (below), which a model wrote after reading the failure's words: the owner has it in the message, and `get_job_run` on the run the heal took shows it as outside text. A failed send is tried again with growing waits for up to a day. Later failures of the same job or provider join the heal and send nothing. The heal closes on the job's next ok run (unless that run ended without working, below), or an ok run of any job on that provider; one waiting 7 days closes as expired, and the same failure then opens no heal for another 7 days. A job set up by a guest keeps its failure line where it delivers, and a watcher's task reports its failures as before.

Before that message, a job's own heal (never a provider's, and never one for a failure no model can help with, such as a rejected sign-in) gets one short look by a separate Fermix run: it reads the job, its recent runs and the failure's words (treated as text someone else may have written), may read a skill and the job's own runs, and changes nothing itself. It reports one decision and a short note, which the message shows under Fermix's facts as Fermix's reading. Fermix then acts on its own only in three ways: it asks for the job to run once more (once per heal, as `run_job_now` would; if no run can come of the ask, the heal's `rerun` in `list_jobs` says `refused` and the heal waits on the owner instead; if that is not known, it says `unanswered` and the heal keeps watching), raises its time limit (only upward, and never past the 30-minute engine default), or pauses it. A raised limit or a pause is written only if the job is still as Fermix read it before its look: if the owner edited, paused or resumed it meanwhile, even back to what it was, the owner's change stands, Fermix makes no move and the message claims none. Anything else — a different task, schedule, skill, model pin, delivery, or a time limit past the default — is only proposed: stated and stored, never made by Fermix. It never touches a job's tools and never removes a job. A job a watcher wakes or a mandate names gets no proposal and no raised limit. After a rerun or a raised limit the heal watches the job's next run: a clean run closes it with nothing more said, a failure sends one more message saying it is still failing after what Fermix did and closes it, and the same failure then stays quiet for 7 days.

A proposal comes to the owner as an approval card in their inbox, the kind a watcher's proposal uses: what failed, Fermix's reading, one line per field it would change with the new value (a task as its changed part: the words added, removed, or what replaces what), that Fermix has not made the change, and a Details part with each changed field exactly as it is and as it would become. Telegram shows **Approve** and **Deny** buttons; Signal, WhatsApp and iMessage get the card as text ending with how to reply; the local command line chat (a configured `cli` target) gets it as text too. The owner answers with a tap, or `/confirm` or `/deny` typed in the chat the card went to (bare, or with the card's id that a list of several waiting things shows); an answer from any other chat or person changes nothing, and `/always` does not apply. A yes makes exactly the change shown, as an owner's edit, only if the job is still as it was when the change was drawn, and Fermix then watches the next run as after any fix; a no leaves the job and the same failure is quiet for 7 days. The reply, or the tapped card itself, says what was done, or what became of the proposal: already answered, superseded by the owner's own edit, expired, or closed because the job ran cleanly. Only the owner's answer on the card applies a proposal: no reply in chat does, and you never apply one for them. When the owner asks for that change or another in chat, make it as an ordinary edit with `update_job`. A change too long for the card to show whole, or an inbox with no chat an answer could come from (a Slack or Discord target), is not offered: the message is Fermix's facts and its reading, and the owner edits the job themselves. An edit, pause or resume of the job while a proposal waits closes the proposal as superseded; a proposal no one answers closes after 7 days, and the same failure is then quiet for 7 days. A job a watcher wakes or a mandate names never gets one. In the Fermix app the message is a row in the chat, as any other of Fermix's messages, ending with a line that it waits on its card, and beside it the card (the job, each changed field, Details, **Approve** and **Deny**) on the Mac and on a paired phone alike; either one answers it, nothing else does, and a process Fermix started cannot. The card is sent again whenever the app reconnects, after a restart too, for the seven days the proposal waits, and goes away when the proposal ends, however it ends.

A run can end ok without working: a tool it called failed on every call. Fermix counts each tool's calls for the whole run, how many succeeded and how many failed, and when one tool never once succeeded in three runs of a job in a row (whatever started them, a watcher's task aside), it treats the third as a failure that is not retried, reading only whether a call succeeded and never the words. The run itself still reads `ok` with no kind; its heal's `failure_kind` is `tool_never_succeeded`. A tool that also works somewhere in the run, such as a file read that misses once, never counts. When the tool is a plugin's, the heal is the plugin's: every job that plugin refuses shares one heal and one message, which names the plugin, the tool and the jobs, quotes the tool's last error as its own words, and has no separate look by Fermix. Otherwise the heal is the job's and gets the usual look, which sees the tool, its failed calls in each of the three runs and its last error (as text someone else may have written). Such a run closes its provider's heal but never its job's. A heal of this kind is about one tool, so it closes only on an ok run (of any job, for a plugin's) in which that tool works; a run that does not call it changes nothing, and the heal otherwise closes as expired after 7 days. A call to a name no tool of the run has is never counted, and a watcher's task keeps no error words.

## Managing

- `update_job` edits `task`, `schedule`, `description`, `skill_name`, `timeout_seconds`, the route pin and delivery in place; omitted fields are unchanged, so delivery is never silently retargeted and a pin is kept. Switching to `none`/`local` clears the target. `clear_route_pin: true` un-pins to default routing and cannot be combined with `provider`/`model`. An empty patch is rejected.
- `list_jobs` lists jobs with their `task_prompt`, schedule, `timezone`, `next_run_at`, state, pin, delivery and last outcome, and each job's open `heal` (its `state`, `subject` `job`, `provider` with the `provider` or `plugin` with the `plugin`, `failure_kind`, the `tool` for a run that ended ok without working, `since`, how many `runs`, and `owner_told`; once looked at, the `decision` Fermix carried out, `has_note` and `note_run_id` (the run whose `get_job_run` shows the note, as outside text; never the note itself), for a proposal each field's whole new value in `proposal` (exactly what applying it would write), and for a rerun what came of it in `rerun`: `started`, `running`, `refused` or `unanswered`; after the owner's answer, `answer` (`apply` or `leave`), `answered_at` and, when the change was made, `applied_at`), else `null`; and `last_proposal`, the job's latest proposal once it is no longer its open heal, for its 7 quiet days, with the same fields and its `outcome` (`skipped`, `superseded`, `healed`, `still_failing` or `expired`) and `closed_at`; optional `state` filter.
- `pause_job` stops future ticks. `resume_job` recomputes the next run and refuses an expired job or a one-off whose instant has passed.
- `remove_job` deletes the job and tombstones its memory source; it refuses while a run is active.
- `run_job_now` fires one run immediately through the same runner, tagged `manual`: a recurring job keeps its cadence, and a one-off run by hand is done (it does not fire again at its instant); it refuses a paused, disabled, expired or already-running job.
- `list_job_runs` reads history newest first, optional `status` (`queued`/`running`/`ok`/`error`) and `limit` (default 20, max 100). `get_job_run` reads one run in full: the `task_prompt` it executed, prompt snapshot, token usage, final response, error. A just-triggered run can still be `queued`, so re-read before reporting an outcome. A run's `status: ok` means the loop finished, not that the task succeeded: each run row carries `tool_failures`, the number of tool calls that came back as errors, visible in `list_job_runs`, the run's `output.md` and its `job_run_complete` trace event. `get_job_run` also shows the run's `tools`: each tool it called, with its plugin and how many calls `succeeded`, `failed` or never finished (`unfinished`), and never a tool's error text.

## A watcher's jobs

Two kinds of job belong to a watcher and are made only by `manage_watcher`: `schedule_job` has no schedule for either, and the agent never types their kind.

- **A task** (kind `cue`) runs once per item the watcher passes and reads it; `list_jobs` labels it "runs on cues from watcher <name>". `run_job_now` refuses it, since a run of it is the run of one item.
- **A follow-up** (kind `watcher`) is the owner's own job that each passing item sets off, handed nothing from the item; `list_jobs` labels it "runs when watcher <name> passes an item". Its run is a scheduled run (`trigger: "watcher"`): its `allowed_tools` is its grant, bounded when it was set up by the turn that set it up, and its prompt is its instructions plus one line naming the watcher that set it off and when. `run_job_now` runs it by hand on the owner's turn.

Neither has a schedule or an expiry or takes a capability policy, and each reports to the owner. `update_job` on either needs the owner's own request in a private chat in a turn that has read no outside text, and `remove_job` refuses either while its watcher exists. Follow-ups, their cards and Always allow: skill_view(name: "self-knowledge", file: "cues").
