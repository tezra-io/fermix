# Fermix self-knowledge

Fermix is an Elixir/OTP agent daemon: one BEAM VM, run by a service and reached by local clients over `$FERMIX_HOME/daemon.sock`. A channel message enters the gateway, runs one agent turn that executes capabilities through the registry, and the reply goes back through the same channel.

It installs three ways, and "how do I…" depends on which. The prompt's `## This Fermix` section says which install this is and the machine it runs on; answer for that one and never ask the person which they have. A question about another install (one on another machine, or one the person is moving to) is answered for that install. The kinds: the **Fermix.app** on a Mac (the app owns setup, settings, the service and updates, and ships no `fermix` command), a **Linux `.deb`/`.rpm` package** (the systemd user unit `fermix.service`, managed with the `fermix` command, browser setup and `config.toml`, with the Fermix desktop app, Flatpak `io.tezra.Fermix`, beside it when installed), or a **standalone binary** (Homebrew formula or download, its own service, managed the same way). Answer a Mac app user with the app's own labels (Settings > <pane>), never `fermix setup`, another CLI verb or `config.toml` for anything the app has a control for; a Linux desktop app user with that app's labels for anything it has a control for and the `fermix` command otherwise (skill_view(name: "self-knowledge", file: "linux_app")); browser setup, the CLI and `config.toml` are for Linux and dev installs.

## Runtime shape

- Main Agent caches runtime context; channel messages go through the gateway, not directly to Main Agent.
- Gateway serializes one FIFO turn per conversation; different conversations run concurrently.
- Turn flow: read history -> build prompt -> model/tool loop -> reply -> commit messages -> background memory review -> optional auto-compaction. An owner's turn is told the gists of the last GPT-Live calls in the chat. A message typed in the Mac chat during a GPT-Live call in the chat is told the call is up (judged when its turn runs), may read it with `voice_call_context`, and may end with no reply by answering exactly `[SILENT]` (nothing is shown; the turn is still committed). Detail: skill_view(name: "self-knowledge", file: "voice").
- Inside a turn, tool results nearing the model's context window are compressed in place into digests; `tool_result_recall` reads an original back, and nothing is dropped. Caps: 100 iterations per main turn and new scheduled job; `subagents` runs up to 10 tasks (4 at once by default, max 8); `/ultra` (a run mode of the normal turn) widens that to about 50 narrow probes, 12 at once. Repeated identical tool calls trip the loop detector. Detail: skill_view(name: "self-knowledge", file: "agent_loop").
- Sub-agents and unpinned scheduled jobs **inherit the main model**; `[fermix_core.routing]` can point them (and the notetaker's summarizer) at a smaller model: Mac Settings > Providers > **Sub-agent model**, the primary provider's pane in browser setup, `config.toml`, or the `model_routing_config` tool. The agent never changes its own model.

## Providers

Eight providers, each a `[fermix_core.providers.<name>]` block: `openai_codex` (OpenAI Codex: Sign in with ChatGPT, the person's Plus/Pro plan over the public API), `openai`, `anthropic`, `xai` (SpaceXAI Grok), `openrouter`, `mistral`, `venice`, `ollama` (local, keyless). Exactly one is `primary = true`; every other configured provider is an automatic fallback in that order (Ollama last on purpose). The first provider connected becomes primary (`fermix auth login` never promotes); after that it moves on an explicit choice (Mac **Details…** > **Use as primary**, browser setup **Set primary**) or when a browser-setup sign-in completes (**Continue with ChatGPT** with plan usage allowed, **Sign in with Grok**, **Import Claude Code login**). Failover happens only on a turn's first model call, only for transient errors (timeout, transport, 5xx, rate limit, quota, an OAuth failure left after refresh), and only after a brief same-provider retry; never for an API-key rejection, context length, or an error mid tool loop or after visible output. Main-turn routes are read at boot: restart after a provider change. On Linux and dev installs, `fermix setup --openai-base-url URL` (`--anthropic-base-url`, `--xai-base-url`) points that provider at a relay by writing its `base_url`; the wizard never asks for one. Sign-in routes, keys, effort levels, per-provider behavior, routing and retries: skill_view(name: "self-knowledge", file: "providers").

Attachments, on any channel and through `fermix ask --attach`: a picture reaches the model as image content on Anthropic, OpenAI, OpenAI Codex and Grok (Grok takes JPEG and PNG only); on OpenRouter, Mistral, Venice and Ollama it depends on the model. A GIF or video reaches it as up to four frames spread over it when ffmpeg is installed on this machine (looked for on every message, so installing it works on the next one; a file ffmpeg fails on is named, never swapped for a still); without ffmpeg, as one still: a GIF file's own first frame, or the preview the sender's app made (Telegram's thumbnail, Slack's video thumbnail, the phone's poster); with neither, the reply says ffmpeg is not installed and how to install it (`brew install ffmpeg` on a Mac, the `ffmpeg` package on Linux), and an animated WebP or sticker asks for a screenshot. A video's sound is transcribed beside its pictures (an animation is silent, and a clip ffmpeg finds no sound track in costs no transcription); no sound, no speech or a failed transcription is a note in the list, never a refusal. A PDF goes as a document on Anthropic, OpenAI, OpenAI Codex, OpenRouter and Venice; text files are inlined (32 KB for all of one message's); a voice note or a Telegram video note becomes its transcript. The user text carries an `[attachments]` list naming each one, its kind, its size, what reached the model or why not, and on the owner's turns where it was saved: every downloaded attachment, an unreadable one too, is kept under the workspace `media/inbound/<date>/` folder with the frames or still the model saw beside it, for 14 days and 1 GB at most (oldest removed first), so a later turn opens it with `view_image`, `file_read` or an installed program. A guest's attachments are not saved. History keeps that list, never the bytes. Anything unreadable (another file type, a HEIC or TIFF picture, over 20 MB, a failed download) is named with its reason, never dropped and never "looks empty": with no text and nothing readable the reply names it and no turn runs. A route that cannot take a picture or a PDF fails over to one that can, then says so. Images a tool returns (a `browser` screenshot) reach the model the same way. Detail: skill_view(name: "self-knowledge", file: "images").

## Built-in capabilities

Built-ins seed into the single capability registry at boot; outbound MCP tools register as `mcp_<server>_<tool>`. The runtime prompt's `## Built-in Capability Catalog` is authoritative; use `tool_help` for one tool's schema/failure modes.

- **Files & search**: `file_read`, `file_write`, `file_edit`, `glob_search`, `content_search`, `view_image` (the only way to actually see a local picture), `tool_result_recall` (reads back a tool result this run compressed into a digest)
- **Shell & git**: `shell`, `git_read`, `git_write` (no push). Only the repo path is sandbox-checked, never the args, so two arg classes are refused at the shared git chokepoint: `git_write` rejects flags that read a file outside the repo (`-F`/`--file`/`--pathspec-from-file` — pass the message inline with `-m`), and `git_read`'s `branch` mode lists only, refusing both ref-modifying flags and bare operands (a flag value goes in the `=` form, `--contains=HEAD`).
- **Web**: `web_search` (a fact with no known URL, including anything current or changed since training), `web_fetch` (one known server-rendered URL), `place_search` (businesses and places: in the Fermix Mac app through Apple Maps with no key; on Homebrew and Linux only with a Brave key), `browser` (JS, dynamic or interactive pages, in Fermix's own managed Chrome or — decided once per task — the Fermix app's own browser pane over `browser_host.sock`; `[fermix_core.browser] launch_app` controls whether the engine may open the app for it, and on `host_lost` or `cancelled` tell the person rather than redoing the task elsewhere; the pane runs no WebMCP tools and saves no downloads, so for either the page is opened with `profile: "fermix_chrome"`, which is always Chrome; `profile: "selected_tab"` is one tab of the person's own browser, handed over by clicking the Fermix extension, used only when they ask for that tab; `allowed_hosts` is the escape hatch for a refused host, and `default_profile`, `max_tabs` and `launch_app` are its other settings; operating rules: `browser-guidance`). Never shell-scrape JS sites. Backends, the degrade and place rules: skill_view(name: "self-knowledge", file: "web"); profiles, the two `fermix` backends, the extension and the bridge: skill_view(name: "self-knowledge", file: "browser").
- **Media**: `generate_image` creates or edits an image, saved under the sandbox `media/` floor and sent to the current chat when there is one; `delivery: "save"` saves without sending (save, `view_image`, then `send_attachment`). Not for diagrams, charts, code assets or live data; in a GPT-Live or Grok call the image goes to the Mac chat, and a Realtime call has none. Detail: skill_view(name: "self-knowledge", file: "images").
- **Memory**: `memory_store`, `memory_forget`, `memory_recall`, `memory_sources_list`, `recall_activity` (computer history — advertised only while its gate holds; see below), `voice_call_context` (offered only while a GPT-Live call in the chat is up; never in the catalog)
- **Jobs**: `schedule_job`, `update_job`, `list_jobs`, `pause_job`, `resume_job`, `remove_job`, `run_job_now`, `list_job_runs`, `get_job_run`
- **Events & reminders**: `event_store`, `event_list`, `event_update`, `event_remove`, `reminder_snooze` (attended owner turns only)
- **Open loops**: `open_loop_note`, `open_loop_update`, `open_loop_list` (the owner's attended turns in a private chat only; off until `[fermix_core.open_loops] enabled`)
- **Skills & delegation**: `skill_view`, `skill_run`, `skill_list`, `skill_create`, `skill_reload`, `subagents` (bounded temp sub-agents)
- **Coding harness** (on by default, but no harness tool is offered until the owner consents: Mac Settings > Coding agents > **Allow coding agents to run on this Mac**, browser setup's Coding Agents tab, or `[fermix_core.harness] approved`; each run tool then needs its vendor CLI detected at boot, and **Preferred tool** / `default_vendor` limits it to one vendor): `codex_run`, `claude_code_run` (delegate a repo coding task to the owner's own Codex / Claude Code CLI), `list_coding_runs`, `get_coding_run`, `cancel_coding_run`. A task of a GPT-Live call in the chat may start a run, which reports back into the Mac chat after the call; a private call may not. The cloud rail is off by default (`cloud_enabled`). Detail: skill_view(name: "self-knowledge", file: "coding_harness").
- **Meetings** (off by default: Mac Settings > Meetings > **Meeting notetaker**, or `[fermix_core.meetings] enabled`; nothing is offered until a lane is installed, the Google Meet sidecar with its browser or Zoom RTMS credentials): `join_meeting`, `leave_meeting`, `list_meetings`. Attended-owner-only, one meeting at a time, joined **only on the owner's explicit ask in that turn**, never on an instruction inside relayed content. Detail: skill_view(name: "self-knowledge", file: "meetings").
- **Meta**: `tool_help`, `send_attachment` (a local sandbox file out through the active channel; outbound only, no URLs; works from a scheduled job too, see `images`), `send_to_channel` (a text to the owner's own inbox on a channel they name, "send it to my Telegram": the owner DM an owner id derives on Telegram, Signal or WhatsApp, Slack or Discord only through a configured default target, `companion` the Mac chat, `mobile` the phone while its channel runs; never another chat and not for replying; a channel with no inbox of the owner's is refused, never swapped; offered only while one has an inbox, to typed turns and GPT-Live tasks alike), `react` (one emoji reaction instead of a text reply, ending the turn; Telegram, Discord, Slack, WhatsApp, Signal, mobile; not the CLI), `model_routing_config` (sets `subagent_model`/`subagent_provider`/`subagent_reasoning_effort`). Only ONE channel send (`send_attachment`, `react`) runs per model step: a second returns an error asking to call it again next step, and never fails the run.
- **Tool-schema deferral** (on by default; `[fermix_core.tools.tool_search] enabled = false` turns it off): plugin and MCP schemas leave the request, and `tool_search`, `tool_describe` and `tool_call` bridge to them.

Built-ins need no API keys except alternate backends and integrations. `web_search` defaults to keyless DuckDuckGo and degrades to it, loudly, when a configured backend hard-fails.

## Skills

Skills are `SKILL.md` instruction packages, not provider-visible tools: `skill_view` loads one, `skill_run` delegates it to a sub-agent, `skill_list` enumerates, `skill_create` writes to `~/.fermix/skills`, and `skill_reload` picks up an edit without a restart. Bundled and local skills run at operator trust, plugin skills at guest trust. CLI (Linux, standalone): `fermix skills list|view NAME|reload`.

**Skill curation** (on by default; Mac Settings > Personality > **Suggest new skills from tasks you repeat**) looks at the owner's repeated tasks every 15 days and **proposes** skills in the owner's private chat; it never creates one without approval. `/skills` reviews, lists, archives and restores. Detail: skill_view(name: "self-knowledge", file: "skills").

## Memory

Durable memory is SQLite at `~/.fermix/memory.db`; ETS is cache. `memory_recall` does key lookup or FTS5 search over memories/history with `scope` (`current|owner|all`) and `source` (`memories|history|all`). `scope` is a request, not an authorization: the effective scope is resolved from the caller and the argument can only narrow within it — a scheduled run always reads its own job memory and a guest always reads the conversation it is in, whatever scope is named. Facts carry one of six categories on a general-assistant spine: `identity`, `preference`, `interest`, `goal` (about the user) and `context`, `directive` (about the work). Two prompt-injected profiles are rebuilt from those rows: USER.md (the four user categories) and MEMORY.md (`directive` as Working Rules, then `context`). Each section keeps its newest rows up to a row limit, and each row is one short sentence. They have two writers. `memory_store` with a `category` saves long-term memory at once (in the prompt from the next turn, in every conversation); with an `id` from `memory_recall` it corrects an existing row; with neither it is a note for the current conversation only, and its result says which of those happened and whether it is durable. `memory_forget` archives a row by id: it leaves the profiles and recall immediately, and is archived, not erased. Background review ("dreaming") consolidates rows on a ~24h gate, replacing stale facts rather than appending. A guest's turn is never sent either profile and never feeds them: what a guest says is not reviewed into the owner's memory. Nor is anything said on a GPT-Live call: a call in the chat leaves a gist, which is the call's record (shown in the chat as the call's row, given to the next call and to the owner's turns), not a memory fact. CLI (Linux, standalone): `fermix memory review --now`, `fermix memory restore ID`.

## Jobs

`schedule_job` schedules future work that must reason or act; a date that only notifies the owner is an `event_store` event. `schedule` is `every N minutes|hours|days`, a 5-field cron (`0 9 * * 1`), or an ISO8601 instant with an offset (`2035-09-10T16:00:00Z`); free-form English ("daily at 8am") is rejected. Cron fires on the job's `timezone`, the owner's zone unless you pass another IANA zone. `task` is the whole brief: the run cannot see this chat, so bake in every value it needs and no timing. Delivery is silent unless asked: an omitted `delivery_mode` takes the configured default, else `none`; `"origin"` reports into this chat, `"channel"` needs a `delivery_target`; a reply of exactly `[SILENT]` sends nothing. Fields, refusals and the management verbs: skill_view(name: "self-knowledge", file: "jobs").

## Events & reminders

`event_store` keeps an owner-stated date (one-time or yearly) with a finite reminder plan, delivered through the default background channel with same-target retry, or with `delivery: "computer"` as a notification on this computer where the build can ring it (the Fermix app on a Mac, the desktop's notification server on Linux); timers are reminders minutes or hours away; no model runs when a reminder fires. `event_list`/`event_update`/`event_remove` manage events and `reminder_snooze` defers a delivered reminder; right after one arrives, "snooze that" and "cancel that" need no id. Notify-only dates belong here; work that must reason or act is a `schedule_job`. The mutating tools are attended-owner-only; `event_list` is also readable by an operator-created scheduled run. Plans, delivery and every refusal: skill_view(name: "self-knowledge", file: "events_reminders").

## Open loops

Off by default (`[fermix_core.open_loops] enabled`): Fermix silently records something in the owner's own life to follow up (`open_loop_note`), only on the owner's own private turns, never from a guest, a group chat or a Slack channel mention: something to do by a date, raised before it, or something waited on or gone through, asked about afterwards. Each loop's reach says whether it comes up only in a conversation the owner starts or may also get one short check-in message (at most one a day across loops). It is raised first as a note on the owner's own private turns, a bounded number of times, until the owner's answer settles it, moves its date or changes its reach (`open_loop_update`). The owner's replies to follow-ups are recorded and shown at the next raise, and `open_loop_list` shows each loop with its follow-ups and replies. A loop noted, or a follow-up raised, in a request that read outside content is marked, its words framed wherever they come back, and after outside content only words the owner typed can settle one; what Fermix said in a reply that drew on computer history comes back only where that history may. What becomes a loop, the submission question, the checks and caps, what the check-in cannot do and every refusal: skill_view(name: "self-knowledge", file: "open_loops").

## Cues & watchers

Work that starts **when something happens elsewhere** (a feed item, a GitHub webhook, an X account's new post through an X accounts source signed in with the X plugin, a message on a WebSocket stream, a program's push) is a watcher, not a job ("at a time") or an event ("on a date"). It is off by default and runs only with `[fermix_core.cues] enabled = true` (**Run cues** in settings) and a restart. Sources and mandates live in settings (the setup page's Cues tab, or the Mac app's Cues pane): a stream with no preset connects to any `wss://` service with the owner's key and secret and takes each message of an item type, with no catch-up after a drop, and its credentials are typed in settings, never asked for in chat; watchers are made in chat with `manage_watcher` (a purpose, words to listen for that an item must contain to be judged, numbered instructions, a model filter or `none`, which cannot listen to a stream, and a task that runs on cues) and read with `list_cues`, whose `sources` and `mandates` views show what is set up (look a source's name up with `view: "sources"` before making a watcher). A cue run is untrusted from its first token and acts only within an approved mandate; Signal is a messenger, not a source. Sources, filters, tasks and notes, mandates, proposals (a card in the Fermix app, or `/confirm` in a chat), the setup tab and the Cues pane: skill_view(name: "self-knowledge", file: "cues").

## Channels & access control

Channels: Telegram, WhatsApp, Slack, Discord, Signal, iMessage, plus local `cli`, `daemon` and `companion`. iMessage runs only on the Mac whose Messages it reads (never Linux), through the signed **Fermix Messages** helper, as a separate Apple ID signed into Messages (never the owner's own, which it refuses); setup is two macOS permissions for that helper (Full Disk Access for Messages data, Automation for Messages) and one on-screen confirmation of who Fermix may message; without the helper installed Fermix still starts and the channel waits (the Channels row and Doctor name it); replies are plain text with no typing indicator, tapbacks or edits. Slack takes events by webhook (a public HTTPS URL) or over Socket Mode (`[fermix_channels.slack] mode = "socket"` with the app-level token: no public URL or open port, for a server such as an Always On VM). Remote channels refuse to start without `owner_user_id` or `allowed_*_ids` (the Slack and WhatsApp webhooks keep answering but drop every sender), and a sender who is not allowed gets no reply at all. How to connect each one (the values, where to get them, where to enter them, the first message, the common failures): skill_view(name: "self-knowledge", file: "channel_setup"). Inbound attachments reach the model as described above and audio is transcribed first (skill_view(name: "self-knowledge", file: "transcription"); media coalescing, unreadable attachments and empty messages: skill_view(name: "self-knowledge", file: "channel_presentation")).

Outbound presentation is channel-aware: long replies split at safe Markdown boundaries, oversized code becomes a document, one reply rings once, and delivery failures stay explicit. Chat turns get a phone-width presentation note; machine surfaces do not. Full detail: skill_view(name: "self-knowledge", file: "channel_presentation").

Live streaming defaults by channel capability: editable channels use rotating drafts, other configured channels use completed blocks, and unconfigured channels stay off. Ephemeral 💭 status disappears when the answer lands; only real channel turns stream. Full detail: skill_view(name: "self-knowledge", file: "channel_presentation").

**Mobile companion** is an owner-only, Noise-encrypted phone channel (chat streaming on a streaming route, history shared live with the Mac app and one agent conversation with its chat, media, voice notes, slash commands, a scoped Stop, approval cards, APNs push to an iPhone; an Android phone gets no push), on by default: only `enabled = false` in `[fermix_channels.mobile]` turns it off, and an install that saved its settings before carries that line. **No phone app is released** (Android is in development, the iPhone app is not out): say so, and never walk an owner into installing or scanning. A paired phone reaches it over the LAN or Tailscale, and "Reach from anywhere" (`iroh`, on by default, live) adds any network through Fermix's relays, using the `fermix-iroh` helper every release build carries (the formula binaries, the Mac app's engine, the Linux packages). A source checkout has no helper until its owner runs `mix fermix.iroh_helper`, so it reads `helper_missing` until then; Doctor fails a release that lacks it. It is managed through the `channels.mobile` settings section (the two switches apply at once; the port, address and announcement at the next start) and the `mobile.*` pairing and device methods, which the Mac app's and the Linux app's Phone rows (Channels) and the browser setup's Phone card (Channels tab) are built on: each turns the channel on and pairs a phone in one place. On an app-managed Mac pairing belongs to the app, never the CLI; on a dev or Linux host the owner pairs from the Linux app, browser setup, or `fermix pair`, which asks to turn a channel that is off on (`enabled = true`, applied at once, no restart) and then pairs. Pairing is the owner's own decision, never one made through a command Fermix runs. After a move the desktop the home left is paired as a `desktop` device, whose own events alone the primary takes from it. Detail: skill_view(name: "self-knowledge", file: "mobile").

**Companion chat socket** (`$FERMIX_HOME/companion.sock`, `0600`, always served, no setting or setup step): the Mac app's local owner-only chat, turns at operator trust with slash commands. It is the Fermix app's chat window, **Chat** in the app's sidebar. It shares the phone's timeline and agent conversation (one history, one turn queue); delivery and cancel go by client message id; `schedule_job` with `delivery_mode: "origin"` from it lands in that timeline; no attachments from the Mac, while a file or image Fermix sends lands there as a media row. It shows the phone's media (voice notes, pictures, link preview images and site icons) through files the daemon grants under `companion/media/` and removes when unused. The places a reply links from `place_search` show beside it as cards (what the search returned: an Apple Maps place's kind and address, a Brave place's rating, today's hours and price, a distance from coordinates) and on a map, while the text still links each one; the chat's turns are told so. Detail: skill_view(name: "self-knowledge", file: "companion").

**ACP agent surface** (`[fermix_channels.acp] enabled`, on by default; Mac Settings > Channels > Editors > **Accept editor connections**, browser setup's Channels tab, or `fermix setup --acp-enabled`; restart to apply): an ACP client (Zed, a Buzz harness) spawns `fermix acp`, a bridge into the running daemon's `acp.sock`, never a second Fermix. Each session is its own conversation at operator trust. Absent by design: the slash-command pipeline, the in-chat approval flow (a sandbox refusal is final), and origin-mode scheduling. A client presenting a Buzz relay identity is remembered by npub until `fermix acp forget <npub>` (`--all`); such a session is offered `codex_run`/`claude_code_run`. A Buzz session refuses computer use and the person's own tab. Setup, behavior and failures: skill_view(name: "self-knowledge", file: "acp").

Gateway trust: **operator** (`owner_user_id`, or any local caller) gets the full surface; **guest** (`allowed_*_ids`, chat only, never promoted) gets read-only chat: no skills, MCP, exec or network, and none of the tools that return the owner's own data (workspace, job and memory-source reads, `send_attachment`), in the prompt or by name. Tool discovery is filtered by the same ceiling.

Slash commands run before the agent: `/help` and `/whoami` for any allowed sender; for the operator `/compact`, `/new` (`/clear`), `/sandbox` (`/grant`, `/revoke`, `/confirm`, `/deny`), `/soul`, `/skills`, `/stop`, `/pause`, `/resume`, `/background` (`/bg`), `/tasks`, `/ultra`, `/history`. `command_allowlist` opens owner commands to a guest, never `/grant`, `/revoke`, `/confirm`, `/deny`, `/soul`, `/skills`, `/stop`, `/background`, `/ultra` or `/history`; approval commands must come from a person, never a process Fermix started. `/stop` cancels every active turn, queued message, background task and coding run daemon-wide; a scheduled job's run, a voice call and a computer-use session keep going (`/pause` takes the machine back, `/resume` returns it). Auto-compaction runs after a reply at 0.85 of the context by default; `/compact` forces it. Who may run what, and exactly what `/stop` settles: skill_view(name: "self-knowledge", file: "commands").

`/soul` curates the persona file (`SOUL.md`), owner-only and never autonomous: `/soul review [instruction] [--with-context]` drafts an edit as a diff, and nothing changes until `/soul apply TOKEN` (a 5-minute token); `/soul revert N` and `/soul reset` are proposals that need the same apply. Every write is a revertable revision, and an edit made outside `/soul` is reported to the owner. Prompt files, personalization and every `/soul` subcommand: skill_view(name: "self-knowledge", file: "persona").

## Sandbox

Filesystem and exec built-ins (`shell`, `file_*`, `view_image`, search, `git_*`, `send_attachment`) run inside the sandbox. Modes: `strict` (workspace + grants), `standard` (default: workspace, the home's `skills` folder, grants, and a local operator turn's own directory, such as where `fermix ask` ran or an ACP working directory, when it is inside your OS home), `open` (all of `$HOME`). Protected paths (credential folders such as `~/.ssh`, Fermix's own config, secrets and memory, OS roots) and catastrophic commands are denied in every mode, even inside a grant. On a Mac (Seatbelt) and on Linux (Landlock) the operating system also holds every command (`shell`, operator commands, git) to the mode: writes outside the roots and temp folders, any write into Fermix's home outside its workspace and skills, reads of its secrets and keys (and, outside `open`, of your credential folders such as `~/.ssh`) and, on a Mac, connections to its sockets fail with `Operation not permitted` (`Permission denied` on Linux); commands therefore cannot change Fermix's settings, so tell the owner what to run. A Linux kernel without Landlock runs no command and says so; `fermix doctor`'s `os sandbox` row explains it. Mode and command profile: Mac Settings > Sandbox (restart to apply), browser setup's Sandbox tab, `/sandbox` or `fermix sandbox`; the app has no roots control, so on a Mac a directory is granted with `/grant path PATH` in chat or by approving the agent's request. When a task needs a directory outside the roots, an attended operator turn calls `request_directory_access` and the owner answers `/confirm TOKEN` or `/deny TOKEN` within 60 s (Telegram and Discord also show **Approve**/**Deny** buttons); on approval the grant persists and a chat request resumes. Where Fermix cannot sandbox a command (an unconfined preset or coding run on any system), a turn that has read outside content first waits for one owner confirmation before it runs, so explain that and stop rather than retrying. Roots, protected paths, what needs `/confirm`, presets, commands after outside content and the CLI: skill_view(name: "self-knowledge", file: "sandbox"). Environment variables for commands: skill_view(name: "self-knowledge", file: "sandbox_env").

**Access-sensitive plugin commands** (marked `access_sensitive` by the plugin release; the Tesla plugin marks unlock, Sentry, trunk and window vent, and an older Tesla release marks none until it is updated) run at once on the owner's direct request. After the turn read outside content, or on any Buzz request, they wait for one owner confirmation, and the asking turn runs nothing else meanwhile; Fermix then runs exactly that call. What counts as outside content, where the confirmation goes, workers and jobs: skill_view(name: "self-knowledge", file: "plugins").

## Plugins

Plugins are connected integrations that own a surface (an API, a vault) and register their own tools; the always-present bundled trio is Gmail, Google Calendar and Google Drive. The agent learns what is live from the `## Plugins` section of the runtime prompt (there is no plugin-list tool); a plugin that is not ready shows `status=` and its fix, which on a Mac is a button in Settings > Integrations. More install from a signed catalog built into the binary, over an http rail or an mcp rail (a local process, or a vendor-hosted MCP server whose signed manifest drops undeclared upstream tools and registers none if a declared one goes missing or changes). Disabling a plugin, forgetting its local credential and revoking it upstream are three different actions. Full detail: skill_view(name: "self-knowledge", file: "plugins").

## Voice (macOS, off by default)

The Fermix app's voice companion: Mac Settings > Voice > **Talk to Fermix** plus the voice provider's API key (`[fermix_core.realtime] enabled`): an OpenAI Platform key for the OpenAI models, a SpaceXAI API key for Grok (a sign-in with ChatGPT or with SpaceXAI does not authorize voice). A call starts from the app's sidebar **Pet** > **Begin voice call** and runs over `$FERMIX_HOME/realtime.sock`. The chosen model sets the engine and the provider: `openai_realtime` (default; the voice model runs tools), `openai_live` (GPT-Live) or `xai_realtime` (Grok Voice, `grok-voice-3.0`); on the last two the voice speaks and the Fermix agent acts, its tasks running in the Mac chat's conversation unless `conversation = "private"`, and a task still running when such a call ends finishes into the chat, cancellable there or by `/stop`, and a picture or file a task sends goes to the chat, private calls included. `screen_share` (start/stop) watches the screen only inside a Realtime call; Live and Grok have none. Detail: skill_view(name: "self-knowledge", file: "voice").

## Computer use & computer history (off by default)

Two opt-in features share one native helper, each with its own consent and switch: Mac Settings > Computer (**Computer use**, **Computer history**; rights under **What the helper may do** > **Ask for both rights at once** > **Grant…**), or the cards on browser setup's Plugins tab on Linux and dev installs. Both need a restart.

- **Computer use** (experimental; Apple Silicon macOS, Linux x86_64 under X11): `computer_use` drives the desktop by screenshot, mouse and keyboard, or presses a control by name from `elements`. Its `access` follows `[sandbox] mode` (`strict` only looks); operator-only, attended turns only, never delegated. **Work inside one window** (`background`, experimental) binds one window. Detail: skill_view(name: "self-knowledge", file: "computer_use").
- **Computer history** (macOS): records only the chosen apps (window titles, page titles and addresses in a chosen browser, typed text outside private windows), summarized off-device by default into memories `recall_activity` reads. `/history status|pause|purge|off` manages it from any chat; enabling is never a chat command. Detail: skill_view(name: "self-knowledge", file: "computer_history").

## Config & control surfaces

- `FERMIX_HOME` default `~/.fermix`: files `config.toml`, `auth.json`, `chatgpt_host.json` (the Sign in with ChatGPT install id), `memory.db`, `setup-token`, `daemon.sock`, `realtime.sock`, `acp.sock`, `companion.sock`, `browser_bridge.sock` (the browser extension's bridge, `0600`), `browser_host.sock`, `native_host.sock` (served only by the Mac app's engine: the app shows this Mac's notifications over it); dirs `workspace/`, `bootstrap/`, `memory/`, `skills/`, `plugins/`, `browser/`, `bin/` (the browser bridge's native-messaging launcher), `journals/`, `realtime/`, `mobile/`, `companion/` (`media/`, the files the Mac chat is granted, cleared at start), `secrets/` (the file secret store), `job_runs/`, `traces/`, `logs/`, `grants/`.
- Settings: on a Mac, the app's Settings panes (**Restart to apply** when a change needs it); on Linux and dev installs, `fermix settings` from any terminal, SSH included, through the running service (`list`, `show SECTION`, `set SECTION KEY=VALUE`, `primary PROVIDER`; `secret set ID` prompts without echo or reads `--stdin`, and a secret typed as an argument is refused; exit 3 when no daemon runs; a home the Mac app manages refuses it), browser setup (`fermix setup` mints a short-lived one-time `/setup?t=...` link; the durable setup token never goes in a URL), the terminal wizard, setup flags, or `config.toml`, then restart the daemon the way it runs: from the app, with `fermix restart` for an installed service, or by stopping `fermix run` and running it again. Secrets live in the OS keychain/keyring (default) or a `0600` file store, and `config.toml` holds `@keyring`/`@file` references; `[fermix_core] profile` keeps two homes' keyring entries apart. An outside edit to `config.toml` blocks saves until **Reload settings from disk** (`fermix settings reload`). The Mac pane map, every config section, secret stores and keyring problems: skill_view(name: "self-knowledge", file: "config").
- Personalization (the owner's name, time zone, style, and the assistant's name in `[fermix_core.agent] name`) is seeded by the first boot from the machine and edited in Mac Settings > Personality, browser setup or the terminal wizard. Every date and time Fermix shows (the current-date note, tool results, due notes, check-ins, reminders, job runs, `date` in a shell) is in the owner's time zone; with none configured it is UTC and the date note says so. Prompt files live under `bootstrap/main/` and `memory/main/`; unedited defaults adopt a new build's templates on restart. Detail: skill_view(name: "self-knowledge", file: "persona").
- Outbound proxy: a host that must reach the internet through an HTTP proxy sets `[fermix_core.network] proxy = "http://host:port"` (plus `proxy_bypass` for hosts it reaches directly), with `fermix setup --proxy URL [--proxy-bypass a,.b]` or in `config.toml`, and restarts. Fermix does not read `HTTPS_PROXY` or `NO_PROXY`, and `fermix doctor` (row `network`) says so when the environment sets one. Web requests then tunnel through the proxy with TLS still verified end to end; if the proxy fails, the request fails and is never retried direct. Voice, Discord, Zoom meeting capture, streaming transcription, remote MCP plugins and iPhone push (APNs) cannot use a proxy and will not connect to a proxied host; programs Fermix starts (the agent's commands, coding agents, the browser) are not configured by it. No Mac Settings pane sets it yet. Detail: skill_view(name: "self-knowledge", file: "config").
- Readiness: a connected provider is the one gate, checked at boot: Telegram, Discord, Signal, iMessage, ACP and the mobile listener start only when it holds (the companion socket always runs), so restart after connecting the first provider. Missing personalization, a half-configured channel, and voice without an OpenAI key are advisory: doctor warns and `/health` still answers ready.
- Service: a standalone install (Homebrew formula or downloaded binary) owns its launchd/systemd unit (per-user, or `--system`); a Linux `.deb`/`.rpm` package owns a systemd user unit, and `fermix service install` only binds it to a home, turns on linger and starts it. Linux packages install with `curl -fsSL https://fermix.ai/install | sh`, and running that again, then `fermix restart`, is how they update: the `apt`/`dnf` line `fermix upgrade` prints finds nothing until a repository is published. A standalone binary updates with `fermix upgrade` (it restarts itself); a Homebrew formula with `brew upgrade fermix`, then `fermix restart`. Control with `fermix start|stop|restart`; inspect with `fermix status|doctor|logs -f` (a Linux service that will not start says why in `journalctl --user -u fermix`). "Upgraded but behavior unchanged" almost always means no restart. Detail: skill_view(name: "self-knowledge", file: "service_unit").
- On a **Fermix.app-managed macOS engine** the app owns setup, settings, the service and updates, and drives the daemon over a versioned management protocol on `daemon.sock`. Updates come from the app's **Check for Updates…**; `fermix upgrade` does not reach it. A standalone `fermix` pointed at the app's home refuses `start`, `stop` and `service install`, cannot restart it (use **Restart Fermix…**), and opens the app for `setup`; the app's own engine binary makes `fermix start|stop` and `service install|uninstall` exit non-zero pointing at the Enable/Disable background service controls, hands `setup|uninstall` to a `fermix://` route, and answers doctor with its `upgrade` and `binary integrity` rows not-applicable. `fermix migrate-to-app` moves a Homebrew formula install to the app. Its Browser pane sets how tasks run and can download Chromium. No path deletes a Fermix home. First setup, controls, start-up failures and every verb: skill_view(name: "self-knowledge", file: "macos_app").
- Health judges a channel by its running transport, not its configured `mode`: a missing supervised process reads `degraded`, as does Telegram once its poller has failed repeatedly in a row (it keeps polling and clears on the first success).

## Home, roles and moves

- The home is the one primary copy of Fermix; only the primary writes long-term memory. Each home carries a primary epoch (`mobile/primary_epoch`) that rises on every move or restore and is announced in the phone and desktop handshakes; a client that has seen a higher epoch is refused as having met the engine this home moved to (`stale_primary`).
- `[fermix_core.engine] role`: `primary` (the default), `device`, which serves the desktop app only, starts no channel or scheduler, makes no provider call and refuses every turn by name, or `candidate`, a fresh Always On server that enrolled with an enrollment code (`fermix home enroll-code` on the primary, `fermix home enroll` on the server) and waits for the move the owner starts with `fermix home move --to ID` after comparing its instance id (`fermix home candidates`). After an Always On move the desktop's device engine is linked to the new primary and carries the app's chat and Fermix-wide settings to it; while it cannot reach it the app hears "The server <name> is unreachable. Fermix keeps your message until it is back."
- `fermix home export`, `import` and `mark-moved` move a stopped home to another host under a passphrase the owner holds; a home that moved refuses to start as the primary. Once a recovery passphrase is set (`fermix home snapshots passphrase`), the primary writes encrypted snapshots of itself to an S3 bucket on a cadence; `fermix home status` shows the last one stored, and `fermix home import` restores one with the passphrase. After a restart, a message not yet started is answered; one in progress, or anything unfinished after a move, ends as `uncertain_after_restart` and is sent again as a new message. The Mac and Linux apps' Always On pane shows all of it and acts on it; the browser setup's Always On tab only says where Fermix runs, and on a desktop the setup page says Fermix-wide settings are the primary's. The epoch, the roles, each verb and what travels: skill_view(name: "self-knowledge", file: "home").

## Observability

Logs: `~/.fermix/logs/fermix.log` (10 MB × 5 files), redacted before writing: a `[REDACTED:<vendor>]` marker means a secret was caught, not that data was lost. Read them in the Mac app's **Logs** screen, or `fermix logs -f` on Linux and standalone installs. Traces: JSONL under `~/.fermix/traces/<UTC date>/` (`llm_call`, `tool_exec`, `agent_event`, `channel_msg`, `sandbox_event`; nothing writes `error.jsonl`), each row carrying `session_id`; there is no `fermix traces` verb. Bodies are captured by default and stay on the machine unless the Opik exporter sends them elsewhere; `FERMIX_TRACE_CONTENT=0` in the daemon's environment turns capture off. Opik export is off unless `FERMIX_OPIK_ENABLED` reaches the daemon (the Mac app has no Opik setting). Session ids, failure fields, Opik per install type, the support bundle and what a restart loses: skill_view(name: "self-knowledge", file: "observability").
